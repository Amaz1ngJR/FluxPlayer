# FluxPlayer v0.5.1 状态控制收尾与并发加固方案

> **状态：已实现（2026-06-12）**。本文五类并发加固已全部落地并通过 CMake 构建，
> 改动文件见第三章。下文除标注外保留方案视角的论述（问题定位 + 设计依据），便于
> 回溯「为什么这么改」；具体落点以代码为准。

> 承接 v0.5.0：核心解码管线已拆成「demux 线程 + 独立 video/audio 解码线程 +
> PacketQueue」，但**状态控制还没有完全跟着拆开**。Player 仍同时承担打开媒体、
> 线程生命周期、seek、DASH、录制、字幕、音频回调、渲染调度、UI 回调等职责，
> 很多线程边界靠「即时 flush + 超时兜底 + 注释约定」维持。本方案聚焦把这几处
> 不稳的边界收紧，消除偶发卡死/偶发崩溃的结构性诱因。
>
> **范围**：本方案只做五类优先级最高的并发加固，**不含**把 Player 拆成
> PlaybackSession / DemuxWorker / DecodeWorker / ClockController / RenderPipeline /
> RecordingService 的大重构，也不含命令队列/控制线程模型。后者作为 v0.6.0
> 独立方案，本文末尾只给方向，本轮未落地。

---

## 一、问题总览

v0.5.0 把**数据流**拆开了（packet 队列解耦 demux 与 decode），但**控制流/状态**
仍以 Player 的成员变量散布在多个线程间，靠人工约定维持安全。审阅定位到五个
最该优先收紧的点（按风险排序）：

| # | 问题 | 风险 | 现状维持手段 |
|---|------|------|------------|
| 1 | **FrameQueue 生命周期契约** | 音频回调/渲染读到被 unref 的 AVFrame 数据 → 偶发崩溃 | 锁只保护取指针，数据访问在锁外，靠"flush 不会刚好并发"侥幸 |
| 2 | **seekTargetStartTime_ 数据竞争** | 跨线程读写普通 `double` → UB（撕裂读、可见性） | 头文件注释"仅在解码线程读写"，但实际三线程读写 |
| 3 | **EOF 停泊 vs decode 线程退出冲突** | "EOF 后 seek 恢复"路径不完整 → seek 卡死/无响应 | demux 能恢复，但 decode 线程已退出，无人消费新包 |
| 4 | **录制器锁未贯穿所有访问** | start/stop 与 demux 线程 writePacket 并发 → 录制器半构造态崩溃 | 只有 writePacket 进锁，start/stop/query 没进 |
| 5 | **AVSync 非原子跨线程状态** | `externalClockBase_` / `pauseStartTime_` / `clockType_` 撕裂读 → 时钟跳变/UB | 部分已原子化（audioClockUpdateNs_），其余仍是裸成员 |

## 二、逐项方案

### 2.1 FrameQueue 生命周期契约：引用持有模型

> 命名说明：下文消费者持有的独立引用以局部 `Frame leased;` 体现，**不新增**
> `FrameLease` 类型——复用现有 `Frame`（已是 AVFrame 的 RAII 封装）即可，避免无谓
> 的新类。"引用持有"指的是这套契约，不是某个类名。

#### 问题定位

```
FrameQueue::peek()        // src/core/FrameQueue.cpp:57
  └─ lock_guard 取锁 → 返回 &queue_[idx] → 解锁    ← 返回裸指针后锁已释放

Player::audioOutputCallback()  // src/core/Player.cpp:2220
  └─ Frame* audioFrame = audioQueue_->peek();        ← 拿到裸指针
     ... avFrame->data[0] 上做 memcpy ...            ← 锁外访问数据

FrameQueue::flush()       // src/core/FrameQueue.cpp:98
  └─ 对所有槽位 unreference()                         ← 别的线程（seek/serial flush）并发释放
```

**竞态**：seek / serial flush 在 audio decode 线程触发 `audioQueue_->flush()`，
而平台音频回调线程此刻正握着 `peek()` 返回的裸 `Frame*` 在 `avFrame->data[0]`
上 memcpy。flush 的 `av_frame_unref` 与 memcpy 并发 → 读到已释放/正在释放的
buffer。视频侧 `renderVideoFrame`（render 线程 peek）与 decode 线程 flush 同理。

当前的"边界保护"（Player.cpp:2244 的 `frameOffset >= frameDataSize` 检查）只能
防越界，**防不住 buffer 本身被 unref**。

#### 设计：消费者持有独立引用

核心思想（对标 ffplay 用 `av_frame_move_ref` 把帧交给消费者，使队列与消费者
不再共享同一份 buffer 生命周期）：**消费者不再借用队列槽位的指针，而是在锁内
对该槽位的 AVFrame 做一次 `av_frame_ref`，得到一份独立引用**。此后即便 producer
flush/unreference 了队列那一份，底层 buffer 的引用计数仍 > 0，消费者手里的数据
在它自己释放前始终有效。

新增/改动 API：

```cpp
// Frame.h —— 新增：从另一个 Frame 增引用并拷贝全部元数据
//   内部：先 unreference() 自身释放旧引用 → av_frame_ref(m_frame, src.m_frame)
//   增持 src 的 buffer 引用 → 拷贝全部元数据字段：
//       m_pts / m_duration / m_type / m_ptsEstimated
//   （后续若 Frame 新增元数据如 serial，必须一并在此拷贝，否则截图/字幕/
//    估算帧判断会丢信息）
void Frame::refFrom(const Frame& src);

// FrameQueue.h —— 取代裸指针 peek()/peekLast()
//   在 mutex_ 锁内调用 out.refFrom(queue_[idx])，消费者拿到独立引用。
//   返回 true：out 已填充有效帧。
//   返回 false：队列空——**此时必须 out.unreference()**，把 out 清成空帧，
//   不能保留上一次 lease 的旧帧（否则调用方误用陈旧数据）。语义固定，不二选一。
bool FrameQueue::peekRef(Frame& out);       // 取代 peek()
bool FrameQueue::peekLastRef(Frame& out);   // 取代 peekLast()

// FrameQueue.h —— 视频 render 路径的"消费一帧"原子操作
//   收敛现有 next()+dup-peek+再 next() 那套靠裸指针相等判断的脆弱逻辑，
//   一次锁内完成 keep-last 状态推进（精确算法见下）。
void FrameQueue::consume();
```

删除裸 `peek()` / `peekLast()`，杜绝"锁外持裸指针"的误用入口。

#### consume() 的 keep-last 精确算法

keep-last 模式（视频队列）下，`consume()` 必须按 `rindexShown_` 两种状态分别处理，
否则会少释放（内存膨胀/槽位泄漏）或多释放（unref 还在用的帧）：

```cpp
void FrameQueue::consume() {
    {
        std::lock_guard<std::mutex> lock(mutex_);
        if (keepLast_ && !rindexShown_) {
            // 状态 A：当前 rindex 帧首次被显示
            //   只标记 shown，不释放槽、不前进 rindex、size 不减。
            //   该帧成为 keep-last 保留帧，供 peekLastRef/暂停重绘使用。
            rindexShown_ = true;
            return;                    // 注意：此分支不 notify 生产者（未腾出空位）
        }
        // 状态 B：keepLast && rindexShown_（或非 keep-last 队列）
        //   当前显示的是逻辑上的"下一帧"，需释放旧的 rindex 帧、前进、
        //   并把新落到 rindex 的帧标记为 shown（它就是刚显示的这帧）。
        queue_[rindex_].unreference();
        rindex_ = (rindex_ + 1) % maxSize_;
        --size_;
        if (keepLast_) {
            rindexShown_ = true;       // 新 rindex 帧 = 刚显示帧，保持 shown
        }
    }
    notFull_.notify_one();             // 腾出一个槽，唤醒等待的生产者
}
```

> 与现有 `next()` 的区别：`next()` 在 keep-last 第二次调用时把新 rindex 标记为
> **未** shown（`rindexShown_ = false`），需要再配合一次 dup-peek+next 才能正确前进
> ——这正是 render 路径里那段脆弱代码的来源。`consume()` 把"显示一帧"建模为单次
> 原子操作：调用一次 = 推进一帧并始终保留刚显示的那帧作为 keep-last。`next()` 保留
> 给音频队列（keepLast=false，走状态 B 的纯前进语义）。

#### 消费者改造

**音频回调**（Player.cpp:2189 `audioOutputCallback`）：
```cpp
Frame leased;                              // 栈上，复用一份消费者持有的 Frame
while (inputFilled < inputNeeded) {
    if (!audioQueue_->peekRef(leased)) {   // 锁内 av_frame_ref；false 时已清空 leased
        // underrun
        break;
    }
    AVFrame* avFrame = leased.getAVFrame(); // 这份引用 producer flush 也动不了
    // ... 现有 offset / memcpy 逻辑不变，全部基于 leased ...
    if (整帧消费完) {
        audioQueue_->next();               // 释放队列那一份；leased 仍持有直到下次 refFrom
        pendingAudioOffset_.store(0);
    } else {
        pendingAudioOffset_.store(...);     // 部分消费，下次 peekRef 取回同一队头
        break;
    }
}
```
`pendingAudioOffset_` 的语义不变：部分消费时不 `next()`，下次 `peekRef` 仍返回
同一队头帧（leased 重新 ref 同一槽）。flush 在回调间隙发生时，下次 `peekRef`
要么返回新队头要么返回空（空时 leased 被清空），**不会再让旧 offset 落到已释放
buffer 上**。

**视频渲染**（Player.cpp:771 `renderVideoFrame`）：
```cpp
Frame leased;
if (videoQueue_->peekRef(leased)) {        // 不消费，仅取引用看 PTS
    double nextPTS = leased.getPTS();
    if (nextPTS <= masterClock + 0.005) {
        // 用 leased 渲染（renderer_->renderFrame 读 leased.getAVFrame()->data）
        // leased 是独立引用，渲染期间 decode 线程 flush 也不影响
        videoQueue_->consume();            // 原子推进读索引 + keep-last 维护
        ... 渲染 leased ...
    } else { /* sleep 等显示时间 */ }
}
```
原来 `next()` + `peek()` 比较 `dup == frame` 的指针相等技巧不再需要——`consume()`
在锁内一次完成 keep-last 维护，render 线程拿的是 `leased` 这份独立引用，与队列
槽位身份解耦。

**截图**（Player.cpp:2077 `GLFW_KEY_P`）：
```cpp
Frame leased;
if (videoQueue_ && videoQueue_->peekLastRef(leased)) {
    Screenshot::saveFrame(&leased, cfg.screenshotDir, cfg.screenshotFormat);
}
```

#### 为什么不选"flush 改 serial 标记由消费者丢旧帧"

审阅给了两个备选。引用持有比"serial 标记"更彻底：serial 方案下消费者仍持有
槽位裸指针，producer 重用该槽（windex 追上）时数据仍可能被覆盖，需要额外的
"消费者完成前 producer 不重用"约定——这正是现在脆弱的根源。引用持有让
**生命周期由引用计数自动管理**，无需任何跨线程时序约定，是更优雅的契约。

#### 开销评估

每次 `peekRef` 多一次 `av_frame_ref`（只增引用计数 + 拷贝 AVFrame 结构体，**不
拷贝像素/采样数据**）。音频回调 ~10–20ms 一次、视频帧 ~16ms 一次，相对回调内
已有的 `std::vector<uint8_t> inputBuf` 分配可忽略。

### 2.2 seekTargetStartTime_ 改原子纳秒

#### 问题定位

```cpp
// Player.h:532 —— 注释"仅在解码线程读写"，类型是普通 double
double seekTargetStartTime_{0.0};
```
实际读写者：
- **UI 线程写**：`seek()` Player.cpp:642
- **demux 线程写**：`processSeekRequest()` Player.cpp:1521、`restartDashMerger()` Player.cpp:1610
- **video decode 线程读**：Player.cpp:1309、enqueue 超时 Player.cpp:1726
- **audio decode 线程读**：Player.cpp:1374

跨线程读写非原子 `double` 是数据竞争（UB）。

#### 方案

```cpp
// Player.h —— 改为原子纳秒计数（steady_clock）
std::atomic<int64_t> seekTargetStartNs_{0};
```
写：`seekTargetStartNs_.store(steadyNowNs(), std::memory_order_release);`
读：
```cpp
double elapsed = (steadyNowNs() - seekTargetStartNs_.load(std::memory_order_acquire))
                 / 1'000'000'000.0;
```
`steadyNowNs()` 抽到一个公共内联 helper（AVSync.cpp 里已有同名局部函数，提到
共享头或各自保留）。所有读写站点统一替换。

### 2.3 EOF worker 生命周期：让 EOF 成为播放状态

#### 问题定位

```
demux 线程 EOF（本地文件）  Player.cpp:1261
  └─ 投 null 包 → 进入「停泊」循环，轮询 seek，可恢复读取

video decode 线程  Player.cpp:1353
  └─ 取到 null 包 → drain → break 退出线程         ← 退出了！
audio decode 线程  Player.cpp:1420
  └─ 同上 → 退出
```

**矛盾**：demux 设计成 EOF 后停泊、可被 seek 唤醒恢复读取；但 decode 线程拿到
null 包就 drain 完退出。于是"EOF 后 seek 恢复"这条路只走了一半：demux 恢复读包，
**decode 线程却已经没了**，新包堆在 packet 队列无人消费 → seek 后画面/声音不恢复。

#### 方案：decode 线程也"停泊"，不退出

让 EOF 成为播放状态（对标 ffplay：EOF 是状态，不是线程终点）。

1. **decode 线程读到 null 包**：drain 解码器、推完残留帧后，**不 break**，设
   `videoDrainedEof_` / `audioDrainedEof_` 标志，回到循环顶部 `get(block=true)`
   停泊（队列空则阻塞，等新包或 abort）。

2. **seek 发生**：packet 队列 flush → serial 自增 + `cond_.notify_all()`。
   decode 线程从 `get(block=true)` 被唤醒，但**此时队列仍空**（flush 刚清空），
   `get` 会继续阻塞等待；真正恢复消费要等 demux seek 后**第一个新 packet 到达**，
   带着新 serial 入队唤醒 `get`。decode 线程取到该包，发现 `serial != lastSerial`
   → flush 解码器/帧队列 → **清除 drainedEof 标志** → 正常恢复。
   （即：flush 的 notify 只是让阻塞的 get 重新检查 abort/队列；serial 变化是
   随新包一起被观察到的，不是 flush 当下立即观察到。）

3. **run() 结束判定**：原来用 `videoDecodeFinished_`（线程已退出）判断 EOF。
   改为用 `*DrainedEof_`（线程已 drain 但仍存活）+ 帧队列 `numReadable()==0`：
   ```cpp
   bool videoDone = !hasVideoStream_ ||
       (videoDrainedEof_.load() && (!videoQueue_ || videoQueue_->numReadable()==0));
   // audio 同理
   if (demuxFinished_.load() && videoDone && audioDone) {
       shouldQuit_.store(true);  // 真正播放完毕 → 退出主循环
       break;
   }
   ```
   注意：暂停在 EOF（队列里还有帧、render 停止消费）时 `numReadable()!=0`，
   不会误判结束，用户此时仍可 seek 唤醒停泊的三线程。

4. **线程退出靠显式 abort，不靠 shouldQuit_**：这是本方案最易错的一点。
   停泊的 decode 线程阻塞在 `PacketQueue::get(block=true)` 的 `cond_.wait` 上，
   而 `get` 内循环只检查 `abort_`，**不检查 `shouldQuit_`**。所以仅
   `shouldQuit_.store(true)` 不会唤醒它们——必须调用 `pktQueue->abort()`
   （`joinWorkerThreads(abortQueues=true)` 内部已做）才能让 `get` 返回 0、线程退出。
   demux 线程同理：它停泊在 `sleep(kEofParkWaitMs)` 轮询循环里，靠 `shouldQuit_`
   退出（这一路 `shouldQuit_` 有效，因为它是主动轮询而非阻塞在 cond 上）。

5. **自然 EOF（非 loop）退出路径必须自洽 abort/join，不依赖外层 close**：
   改造后 decode 线程 EOF 不再自然退出而是停泊在 `get()`，仅 `shouldQuit_` 无法
   唤醒它们。方案**不依赖"调用方会顺手 `player.close()`"** 来收尾——run() 在退出
   主循环、判定不 loop 后，**主动调用一个 `shutdownWorkersForEof()`** 把停泊的三
   线程 abort 并 join，使 EOF 退出路径自身闭合：
   ```cpp
   // run() 主循环外、handleLoopRestart() 返回 false 的分支：
   if (!handleLoopRestart()) {
       shutdownWorkersForEof();   // 新增：内部 joinWorkerThreads(abortQueues=true)
       shouldLoop = false;        // 三线程已 abort+join，后续 close() 再 join 幂等
   }
   ```
   `shutdownWorkersForEof()` 内部即 `joinWorkerThreads(abortQueues=true)`：
   ```
   videoPktQueue_->abort() / audioPktQueue_->abort()   ← 唤醒停泊在 get() 的 decode 线程
   （demux 线程靠 shouldQuit_ 退出其 sleep 轮询停泊循环）
   join 三线程 → reset 线程对象
   ```
   这样即使调用方忘记 `close()`，worker 线程也不会泄漏/悬挂。后续 `close()` →
   `cleanup()` → `joinWorkerThreads(true)` 对已 reset 的线程对象幂等（joinable
   检查为假，跳过）。

   **通用规则**：改造后所有 join 停泊 worker 的路径都必须 `abortQueues=true`。
   审计点：`stop()`、`cleanup()`、`handleLoopRestart()`、新增的
   `shutdownWorkersForEof()`。任何一处漏 abort，停泊的 decode 线程会永久阻塞在
   `get()`，join 时死锁。
6. **demux 线程**：EOF 投一次 null 包后进停泊轮询循环（保留现有 seek 轮询恢复
   逻辑）。`demuxFinished_` 在投 null 包时置位、seek 恢复时清零——与 decode 的
   drainedEof 配套，run() 三者皆"done"才结束。

7. **handleLoopRestart / startWorkerThreads**：drainedEof 标志在
   `startWorkerThreads` 里随其它结束标志一起初始化（不存在的流标记为已 drained，
   避免 EOF 判定空等）。**loop restart 路径改为 `joinWorkerThreads(abortQueues=true)`**：
   改造后 decode 线程 EOF 不再自然退出而是停泊，故必须 abort 唤醒后才能 join
   （这是对现状 `abortQueues=false` 的必要修正，否则 loop 重启时 join 死锁）。

#### 标志重命名对照

| 旧（线程已退出语义） | 新（线程已 drain 但存活） |
|---|---|
| `videoDecodeFinished_` | `videoDrainedEof_` |
| `audioDecodeFinished_` | `audioDrainedEof_` |

`demuxFinished_` 保留语义（demux 已投 null 包，seek 恢复时清零）。

### 2.4 录制器锁贯穿所有访问

#### 问题定位

```cpp
// 写包进锁    Player.cpp:1171 / 1180
{ std::lock_guard<std::mutex> lock(recorderMutex_); if (videoRecorder_ ...) writePacket; }

// 但 start/stop/query 没进锁：
Player::startVideoRecording()  Player.cpp:2304   // 直接 videoRecorder_ = make_unique...
Player::stopVideoRecording()   Player.cpp:2351   // 直接 videoRecorder_->stop()
Player::isVideoRecording()     Player.cpp:2399   // 直接读 videoRecorder_
```
与 Player.h:626 的注释"用此锁保护录制器的创建/销毁与 writePacket 并发"**不一致**。
start 在 UI 线程把 `videoRecorder_` 置为半构造态时，demux 线程可能正读它
writePacket → 崩溃。

#### 方案

所有 `videoRecorder_` / `audioRecorder_` 访问都进 `recorderMutex_`：
- `startVideoRecording` / `startAudioRecording`：构造 + start 全程持锁
  （demuxer 只读取 formatContext/streamIndex，这些在播放期间稳定）。
- `stopVideoRecording` / `stopAudioRecording`：持锁 stop。
- `isVideoRecording` / `isAudioRecording` / `getVideoRecordingTime` /
  `getAudioRecordingTime` / `getVideoRecordingSize` / `getAudioRecordingSize`：
  const 查询，持锁读 → `recorderMutex_` 改 `mutable`。

> 更彻底的做法（审阅备选）是把录制 start/stop 也投递到 demux/control 线程串行
> 执行，彻底消除锁。但那依赖尚未引入的命令队列（v0.6.0），本轮先用锁覆盖到位，
> 保证正确性。

### 2.5 AVSync 跨线程时钟状态收紧（clockType 原子 + external clock 互斥）

#### 问题定位

`audioClockUpdateNs_` 已是原子（v0.4.0 修过），但仍有裸成员被跨线程访问：

```cpp
// AVSync.h
ClockType clockType_;                                  // setClockType 写 / getMasterClock 读
std::chrono::steady_clock::time_point externalClockBase_;  // pause/resume/seek/rate 写 / getExternalClock 读
std::chrono::steady_clock::time_point videoClockUpdateTime_; // updateVideoClock 写 / （潜在）读
double pauseStartTime_;                                // pause 写 / resume 读
```
`getExternalClock()`（AVSync.cpp:72）在 render/UI 线程读 `externalClockBase_`，而
`pause/resume/setPlaybackRate/seekTo` 在 UI 线程写——`time_point` 非原子，撕裂读
导致外部时钟瞬时跳变；`clockType_` 跨线程读写同理。

**关键风险点**：external clock 由 `base`（起算时刻）+ `offset`（起算时的时钟值）
两个量组合算出。若把它们拆成两个独立原子，读侧可能读到「新 base + 旧 offset」或
「旧 base + 新 offset」的错配组合。这个跳变**没有天然上限**：external clock 从 0
跑了很久后，offset 可能已是几千秒，一次 `seekTo`/`setPlaybackRate` 更新中途被读到
错配，跳变量接近整个播放时长——比 `audioClockUpdateNs_ + audioClock_` 那组严重得多
（后者有 `kMaxAudioClockInterpolationSec = 0.1s` 的外推封顶，错配影响被夹到 0.1s 内）。
因此这里**不能**沿用"两个独立原子 + 靠下一帧自愈"的思路。

#### 方案：内部 mutex 保护 external clock 状态组

`clockType_` 是独立标量，跨线程读写无组合一致性问题，直接 `std::atomic<ClockType>`。

external clock 的 `base / offset / rate / paused` 是**必须一起读、一起写**的状态组。
本轮用 **AVSync 内部一把 `mutex`** 把这组读写打包，保证组合一致性。

> **为什么不用 seqlock**：seqlock 的被保护字段若是普通成员（`int64_t` / `double`），
> 读线程与写线程并发访问这些非原子成员，按 C++ 内存模型即为 **data race（UB）**
> —— 外层的版本号 `atomic` 和 `fence` 只约束**可见性顺序**，并不能把非原子访问
> 本身变成 well-defined，TSan 会如实报告，且不同编译器/架构下行为不保证。要正确
> 写 seqlock，被保护字段也必须是 `std::atomic`（用 relaxed load/store，仅靠版本号
> 定序），实现复杂、易错。`getExternalClock` 只是渲染帧率级调用（~60Hz），mutex
> 临界区是几条赋值，加锁成本完全可接受——**正确性优先，本轮用 mutex**。seqlock
> 留给 v0.6.0 ClockController 在确有性能需求时再评估。

```cpp
// AVSync.h
std::atomic<ClockType> clockType_;        // 独立标量，直接原子

mutable std::mutex extClockMutex_;        // 保护下面这组 external clock 状态
int64_t  externalClockBaseNs_{0};         // 起算时刻（steady ns）
double   externalClockOffset_{0.0};       // 起算时的时钟值
double   extClockRate_{1.0};              // external clock 视角的速率快照
bool     extClockPaused_{false};          // 该组自己的 paused 快照（不与 paused_ 混用，见下）
```

**写**（pause/resume/seekTo/setPlaybackRate/resetExternalClock，UI 线程低频）：
```cpp
// 所有更新都在锁内一次性写齐这组字段，例如 seekTo：
{
    std::lock_guard<std::mutex> lk(extClockMutex_);
    externalClockBaseNs_ = steadyNowNs();
    externalClockOffset_ = seekTime;
    extClockRate_        = playbackRate_.load();
    extClockPaused_      = false;
}
```

**读**（getExternalClock，render/UI）：
```cpp
double AVSync::getExternalClock() const {
    int64_t baseNs; double offset, rate; bool paused;
    {
        std::lock_guard<std::mutex> lk(extClockMutex_);
        baseNs = externalClockBaseNs_;
        offset = externalClockOffset_;
        rate   = extClockRate_;
        paused = extClockPaused_;          // ← paused 来自同一快照，不读 paused_
    }
    if (paused) return offset;
    double elapsed = (steadyNowNs() - baseNs) / 1e9;
    return offset + elapsed * rate;
}
```

**paused 必须纳入同一把锁保护的快照**：external clock 的暂停判定只读
`extClockPaused_`（与 base/offset 在同一临界区写齐），**不读全局 `paused_`**。否则
仍可能读到"新 paused + 旧 offset"的错配。`paused_` 这个全局原子保留给
`isPaused()`、`computeFrameDelay`/`shouldDropFrame` 等不参与 external clock 组合计算
的路径使用，两个来源互不混用。

`videoClock_` / `audioClock_` / `audioClockUpdateNs_` 仍保持独立原子：它们要么是
单标量（无组合读问题），要么错配影响有界（audioClock 有 0.1s 外推封顶），不纳入
`extClockMutex_`。`videoClockUpdateTime_`（time_point，仅 updateVideoClock 写、
getVideoClock 当前并不依赖它推算）改为 `std::atomic<int64_t>` steady ns 即可。

## 四、验证计划

CMake + xmake 双构建（见 [[dual-build-sync]]），本方案纯逻辑改动，无 install 资源
变化。**CMake 构建已通过**（无新增告警）；以下回归场景为**待手动验证**项：

1. **本地文件**：正常播放到 EOF → 自然结束；EOF 暂停后 seek 回中段 → 恢复播放
   （验证 2.3 decode 停泊恢复）。
2. **拖动进度条快速连续 seek**（前向/后向）：无崩溃、进度条不跳回（验证 2.1/2.2）。
3. **网络流 / DASH**：seek 重启上游期间反复操作 → 无崩溃。
4. **录制中 seek / 切画质 / stop**：start/stop 与 demux writePacket 并发无崩溃
   （验证 2.4）。
5. **暂停/恢复/变速**反复切换：进度条与音画同步无跳变（验证 2.5）。
   **专项**：长时间播放（external clock offset 累积到几百~几千秒）后，连续
   `seekTo` / 变速 / resume，进度条**不出现接近整段时长的瞬时跳变**（验证
   external clock 的 base/offset/paused 组合读一致）。无音频流（走 EXTERNAL_CLOCK）
   的视频最易复现。
6. **ThreadSanitizer**（可选）：`-fsanitize=thread` 跑一遍上述场景，确认
   `seekTargetStartNs_` / AVSync external clock 字段无 data race 报告。本轮 2.5 用
   mutex，预期 TSan 干净（不存在 seqlock 普通成员的 benign-race 噪声）。

## 五、后续（v0.6.0，不在本轮范围）

本方案把**线程边界的正确性**补齐，但 Player 仍是 2500+ 行的多职责巨类。下一步
按审阅建议引入命令队列 + 控制线程模型，把"UI 先 flush、demux 稍后处理"的双阶段
逻辑收敛：

- **PlaybackSession**：统一生命周期与状态机。
- **DemuxWorker**：只负责 open/read/seek/reopen/packet 分发。
- **DecodeWorker**：video/audio 各自独立，只消费 packet 队列。
- **ClockController**：封装 AVSync + seek 状态。
- **RenderPipeline**：只关心 FrameQueue → GLRenderer。
- **RecordingService**：录制 start/stop/write 线程归属独立化。
- **命令队列**：UI 只投递 `SeekCommand` / `StopCommand` / `SwitchQualityCommand` /
  `StartRecordingCommand`，由控制线程串行执行——彻底消除本方案 2.4 末尾提到的锁
  和 2.3 的双阶段 seek 时序。

中低优先级（可穿插）：
- `waitForPacketSpace()` sleep 轮询 → `condition_variable`，由 `PacketQueue::get()`
  消费后通知。
- 变速音频最近邻重采样 → 接 swr 重采样链路或独立 time-stretch。
- `Player::open()` 网络源 demux open 阻塞 UI → 纳入 OpeningScreen worker。
- 给 PacketQueue / PTSNormalizer / seek 状态机补单元测试。
