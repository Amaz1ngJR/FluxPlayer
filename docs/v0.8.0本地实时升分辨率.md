# FluxPlayer v0.8.0 本地实时升分辨率技术方案

> 版本目标：v0.8.0｜状态：设计阶段
>
> 核心路径：硬解码 GPU surface → GPU 缩放到 720p/1080p → 直接渲染
>
> 本方案遵循 `docs/AI开发守则.md`：不引入无关依赖，平台 SDK 隔离在 `.cpp/.mm`，
> 跨线程状态有明确所有者，新增源文件同步加入 CMake/xmake，代码统一使用中文注释。
>
> 后续互斥功能参见 [`v0.9.0高倍数播放.md`](v0.9.0高倍数播放.md)。

---

## 一、需求定义

### 1.1 功能目标

播放低分辨率本地视频时，如果实际硬件能力满足要求，在播放器现有“画质/分辨率”按钮中
提供以下输出选项：

```text
Original
720p
1080p
```

用户切换后不导出文件、不生成临时文件、不重新打开媒体，也不改变原始压缩码流。每一帧
都沿以下路径实时处理：

```text
本地压缩 packet
    -> 硬件解码器
    -> GPU 解码 surface（NV12/P010）
    -> GPU 视频处理器或缩放 shader
    -> 720p/1080p GPU 输出纹理
    -> OpenGL 直接渲染
```

### 1.2 显示入口的严格条件

本地分辨率选择框仅在以下条件全部满足时显示：

1. 当前来源是本地普通视频文件。
2. 当前媒体含视频流，不是纯音频、图片或损坏媒体。
3. 硬件解码已经实际启用，不是仅配置了 `hwaccel=true`。
4. 当前硬件 surface 能与渲染后端互操作，探测结果为 `Ready`。
5. GPU 能成功创建目标缩放资源。
6. 当前播放倍率 `<= 2.0x`。
7. 当前未进入 v0.9.0 的 4x/8x/16x 高倍数模式。
8. 源分辨率低于至少一个可选目标分辨率。

Windows 和 macOS 都是 v0.8.0 首版必须交付的平台：

- Windows：D3D11VA GPU surface → D3D11 Video Processor → WGL/OpenGL。
- macOS：VideoToolbox GPU frame → IOSurface-backed CVPixelBuffer →
  `CGLTexImageIOSurface2D` 双平面纹理 → OpenGL shader/FBO。

不能以“Windows 已实现、macOS 后续补充”作为 v0.8.0 完成状态。

统一判定：

```cpp
canShowLocalResolutionSelector =
    sourceKind == MediaSourceKind::LocalFile &&
    hasVideoStream &&
    hardwareDecodeActive &&
    gpuInteropStatus == GpuInteropStatus::Ready &&
    playbackRate <= 2.0 &&
    !highSpeedMode &&
    hasUpscaleTarget(sourceDisplaySize);
```

入口必须依据“运行时能力”显示，不能只依据配置文件、显卡型号或硬件解码初始化日志。

### 1.3 与 v0.9.0 高倍数播放互斥

| 场景 | 本地升分辨率 | v0.9.0 高倍数 |
|------|--------------|----------------|
| 本地文件，0.5x～2.0x，硬件互操作可用 | 可用 | 关闭 |
| 本地文件，4x/8x/16x | 强制关闭并隐藏 | 可用 |
| 本地文件，软件解码 | 隐藏 | 可按 v0.9.0 软件降载策略运行 |
| RTSP/RTMP/HTTP 直播 | 隐藏 | 可处理高倍速推流 |
| 网页视频 | 不提供本地升分辨率；保留网络画质列表 | 按 v0.9.0 来源规则处理 |

从 `<=2x` 切到 `>=4x` 时，必须先退出升分辨率模式并恢复 `Original`，再启动高倍数策略。
从高倍数切回 `<=2x` 后，入口可以重新出现，但默认保持 `Original`，不自动恢复之前的
720p/1080p，避免一次切速同时触发高成本 GPU 资源重建。

## 二、这里不需要视频编码器

需求描述中的“重新编码成 720/1080”如果只是用于当前窗口播放，不应真的执行
H.264/H.265 编码：

```text
错误路径：
硬解码 -> GPU 缩放 -> 硬编码 -> 硬解码 -> 渲染
```

这条路径会引入：

- 一次硬件编码和第二次硬件解码；
- GOP/编码缓冲带来的额外延迟；
- 二次有损压缩；
- 更多显存 surface；
- 编码器会话数限制；
- 完全无用的中间压缩码流。

本功能没有文件或网络输出，因此正确路径是：

```text
硬解码 -> GPU 缩放 -> 直接渲染
```

GPU 缩放会写入一张新的目标纹理，这是产生 720p/1080p 像素所必需的计算，不属于
CPU 往返拷贝。本文“零拷贝”的准确含义是：

1. 解码像素不执行 GPU → CPU 下载。
2. 不在 CPU 上执行 `sws_scale`。
3. 不通过 `glTexSubImage2D` 把整帧 CPU 像素重新上传 GPU。
4. GPU surface、缩放目标和显示纹理始终留在同一块 GPU/同一适配器。

## 三、已完成的零拷贝基础与升分辨率缺口

端到端零 CPU 拷贝基础链路已经完成：

```text
Windows:
AV_PIX_FMT_D3D11
    -> D3D11 Video Processor（GPU 内 YUV -> BGRA）
    -> GPU Copy 到独立互操作纹理
    -> WGL_NV_DX_interop2 renderbuffer
    -> OpenGL texture

macOS:
AV_PIX_FMT_VIDEOTOOLBOX
    -> IOSurface-backed CVPixelBuffer
    -> CGLTexImageIOSurface2D 映射 Y/UV plane
    -> OpenGL rectangle texture + shader
```

`VideoDecoder::prepareFrame()` 对硬件帧只执行 `av_frame_ref()`，队列持有原始 GPU
surface；渲染器不调用 `av_hwframe_transfer_data()`，也不读取硬件帧的 CPU plane。
若原生互操作初始化失败，播放器会在 worker 启动前把解码器重建为软件模式，避免形成
GPU 下载后再上传 OpenGL 的“伪零拷贝”路径。

当前基础链路仍按源尺寸创建渲染资源。v0.8.0 后续需要补齐：

1. Original/720p/1080p 输出资源和切换命令。
2. 本地文件、硬件能力与 `<= 2x` 的 UI 门禁。
3. Windows D3D11 Video Processor 目标尺寸切换。
4. macOS 缩放 FBO、质量策略和双缓冲。
5. 仅在用户触发截图时执行的显式 GPU readback。
6. 升分辨率专用性能计数与失败降级状态机。

软件解码和不支持互操作的硬件后端继续使用 CPU 帧上传路径，不显示分辨率入口。

## 四、总体架构

### 4.1 数据流

```text
DemuxWorker
    |
    v
VideoDecoder（D3D11VA / VideoToolbox 等）
    |
    | AVFrame 持有 GPU surface 引用
    v
FrameQueue（小容量硬件 surface 队列）
    |
    v
GpuVideoPipeline
    +-- 导入解码 surface
    +-- GPU 色彩转换与缩放
    +-- 输出 1280x720 / 1920x1080 纹理
    |
    v
GLRenderer::renderExternalTexture()
    |
    v
窗口 / 全屏
```

### 4.2 新增组件

```text
include/FluxPlayer/video/GpuVideoPipeline.h
src/video/GpuVideoPipeline.cpp
src/video/GpuVideoPipeline_win.cpp
src/renderer/HardwareFrameInterop.cpp
```

`GpuVideoPipeline` 使用 pImpl 隔离 D3D11、WGL、CoreVideo 等平台类型。

职责：

1. 探测硬件 surface 与 OpenGL 的互操作能力。
2. 导入当前 GPU frame。
3. 创建并维护 720p/1080p 输出 surface/texture。
4. 在 GPU 上完成缩放、色彩转换和宽高比适配。
5. 向 `GLRenderer` 提供可直接采样的 OpenGL 纹理。
6. 发生设备丢失或导入失败时触发安全降级。

不负责：

- 不读 packet；
- 不控制播放时钟；
- 不管理解码线程；
- 不编码视频；
- 不修改 UI 状态。

### 4.3 能力模型

```cpp
enum class GpuInteropBackend {
    None,
    D3D11Wgl,
    CudaOpenGL,
    VideoToolboxOpenGL,
    VaapiEgl
};

enum class GpuInteropStatus {
    Unavailable,
    Probing,
    Ready,
    Failed
};

struct GpuScaleCapabilities {
    bool hardwareDecodeActive = false;
    bool zeroCpuCopy = false;
    bool supports720p = false;
    bool supports1080p = false;
    int maxOutputWidth = 0;
    int maxOutputHeight = 0;
    GpuInteropBackend backend = GpuInteropBackend::None;
    GpuInteropStatus status = GpuInteropStatus::Unavailable;
};
```

`hwaccel=true` 只是用户意图，`hardwareDecodeActive=true` 只表示解码器在 GPU 上运行，
只有 `status=Ready && zeroCpuCopy=true` 才允许显示本地分辨率选项。

## 五、平台实现

### 5.1 Windows 首选路径：D3D11VA + D3D11 Video Processor + WGL

Windows v0.8.0 首选 D3D11VA，因为 FFmpeg 解码 surface、D3D11 Video Processor 和
Windows OpenGL 互操作可以留在同一 D3D11 设备上：

```text
FFmpeg AV_PIX_FMT_D3D11
    -> ID3D11Texture2D 解码 surface
    -> ID3D11VideoProcessorInputView
    -> VideoProcessorBlt（缩放 + NV12/P010 到 BGRA）
    -> 共享 ID3D11Texture2D 输出
    -> WGL_NV_DX_interop2 注册为 OpenGL texture
    -> GLRenderer 直接采样
```

实现要求：

1. 从 FFmpeg `AVHWDeviceContext` 取得解码所用 D3D11 device，不能另建不同适配器的设备。
2. 正确处理 D3D11 texture array slice；FFmpeg D3D11 frame 可能共享同一纹理数组。
3. 输出纹理使用可共享、可作为 render target 的格式和 bind flags。
4. WGL 注册、lock/unlock 必须在拥有 OpenGL context 的渲染线程执行。
5. D3D11 device lost、WGL extension 缺失或共享纹理创建失败时不显示入口。

现有 Windows 硬件后端优先尝试 CUDA。为保证本功能可用，后端选择应改为能力驱动：

```text
本地文件且请求零拷贝能力：
    D3D11VA interop Ready -> 优先 D3D11VA
    CUDA-OpenGL interop Ready -> 可选 CUDA
    其他硬件解码 -> 仅普通播放，不显示本地分辨率

其他场景：
    沿用现有硬件后端优先级
```

不能仅为了显示按钮就从一个已经工作的解码器中途切换硬件后端。探测和后端选择应在
打开媒体时完成。

### 5.2 Windows CUDA 路径

CUDA/NVDEC 可通过 CUDA-OpenGL interop 将输出 GL texture 注册给 CUDA，再由 GPU kernel
把 NV12/P010 surface 缩放和转换到该纹理。

该路径必须满足：

- FFmpeg CUDA device 与 OpenGL context 位于同一 NVIDIA GPU；
- 构建环境具备所需 CUDA interop API；
- 不把 CUDA surface 下载到 host；
- kernel/interop 初始化失败时回退，而不是影响正常 CUDA 硬解码。

如果当前 MinGW/SDK 环境无法稳定编译 CUDA interop，v0.8.0 首版可以只把 D3D11VA 作为
Windows 的本地升分辨率后端。此时 CUDA 仍可用于普通硬解码，但分辨率入口隐藏。

### 5.3 macOS：VideoToolbox + IOSurface/CGL

```text
AV_PIX_FMT_VIDEOTOOLBOX
    -> IOSurface-backed CVPixelBufferRef
    -> CGLTexImageIOSurface2D 映射 Y plane texture
    -> CGLTexImageIOSurface2D 映射 UV plane texture
    -> OpenGL shader 在 GPU 上做 NV12 -> RGB + bicubic/Lanczos 缩放
    -> 720p/1080p RGBA FBO 双缓冲
    -> 直接显示
```

macOS 与 Windows 一样是首版完整功能，不是只有接口的占位实现。

#### 5.3.1 surface 获取与能力探测

1. FFmpeg 必须实际输出 `AV_PIX_FMT_VIDEOTOOLBOX`，软件 fallback 不算硬件资源可用。
2. 从硬件 `AVFrame` 取得 `CVPixelBufferRef`，只增持引用，不读取 plane base address。
3. `CVPixelBuffer` 必须由 IOSurface 承载，并具有 OpenGL 可导入的像素格式。
4. v0.8.0 基线必须支持双平面 8-bit NV12；P010/10-bit 只有在纹理格式和 shader
   均通过探测时才开放，不能静默降精度。
5. 使用 `CGLTexImageIOSurface2D` 成功映射一张测试 frame 的 Y/UV 两个 plane 后，
   capability 才能从 `Probing` 变为 `Ready`。

严禁为了探测或渲染调用：

```text
av_hwframe_transfer_data()
CVPixelBufferLockBaseAddress()
CVPixelBufferGetBaseAddressOfPlane()
glTexSubImage2D() 上传视频 plane
```

这些调用会重新引入 GPU/IOSurface → CPU → OpenGL 的往返路径。

#### 5.3.2 双平面纹理导入

渲染线程从 `CVPixelBufferGetIOSurface()` 取得 IOSurface，再使用
`CGLTexImageIOSurface2D()` 分别把 NV12/P010 两个 plane 映射到
`GL_TEXTURE_RECTANGLE` 纹理：

```text
plane 0：Y  -> 单通道纹理
plane 1：UV -> 双通道纹理
```

随后复用现有 NV12 色彩矩阵语义，在一个 GPU pass 内完成：

1. 按源纹理坐标采样 Y/UV。
2. 根据 BT.601/709/2020 和 full/limited range 转 RGB。
3. 用 bicubic/Lanczos 放大到目标内容区域。
4. 写入固定 720p/1080p RGBA FBO。
5. 将输出纹理交给 `GLRenderer::renderExternalTexture()`。

不先生成 CPU NV12，也不创建中间 YUV420P。

#### 5.3.3 生命周期与同步

- `CVPixelBufferRef` 跟随队列中的 `AVFrame` 引用，直到当前 GPU draw 已提交。
- CGL 纹理只能由持有 OpenGL context 的渲染线程创建、重绑和释放。
- draw 后插入 `glFenceSync`；fence 完成前保留对应 pixel buffer/texture view，防止
  VideoToolbox 过早复用 surface。
- 720p/1080p 输出继续使用双缓冲，避免同一纹理被 shader 写入和窗口读取。
- seek、切换文件、切回 Original 或关闭时，先等待/清理 fence，再释放纹理和
  `AVFrame`/`CVPixelBuffer` 引用，最后释放 decoder context。
- 两组 CGL 纹理槽循环复用；重绑某一槽前只等待该槽的 fence，不能每帧 `glFinish()`。

#### 5.3.4 macOS 构建要求

当前互操作只调用 CoreVideo、IOSurface 和 CGL 的 C API，因此实现放在
`HardwareFrameInterop.cpp` 的 `__APPLE__` 分支，无需引入 Objective-C 对象或 ARC。
CMake 和 xmake 必须同步链接：

```text
OpenGL
CoreVideo
VideoToolbox
CoreMedia
IOSurface
CoreFoundation
```

平台 SDK 头文件只允许出现在平台实现的条件编译分支中，公共头文件继续使用抽象接口
和不透明 GPU 纹理名称。

#### 5.3.5 Mac 硬件范围

- Apple Silicon：VideoToolbox + IOSurface + CGL plane mapping 必测。
- Intel Mac：硬件和系统允许时走同一路径；互操作探测失败则保持普通播放并隐藏入口。
- macOS 已将 OpenGL 标记为 deprecated，但当前播放器渲染后端就是 OpenGL，因此
  v0.8.0 使用 CoreVideo/OpenGL 互操作；迁移 Metal 属于独立后续重构，不能成为本功能
  缺失 macOS 支持的理由。

### 5.4 Linux

当前项目没有完整 VAAPI 硬解码路径。未来可使用：

```text
VAAPI surface -> DRM PRIME / DMA-BUF -> EGLImage -> OpenGL texture
```

在 VAAPI + DMA-BUF + EGLImage 全部实现并通过探测前，Linux 不显示本地升分辨率入口，
继续使用现有软件/CPU 上传路径。

## 六、GPU surface 生命周期与队列

### 6.1 硬件帧不能立即下载

`VideoDecoder::prepareFrame()` 已按实际帧类型选择存储方式：

```cpp
if (format == AV_PIX_FMT_D3D11 ||
    format == AV_PIX_FMT_VIDEOTOOLBOX) {
    // 保留 GPU AVFrame 引用，不下载像素
    av_frame_ref(dst, srcHardwareFrame);
} else {
    // 软件 YUV420P 直接引用，其他 CPU 格式按需转换
}
```

当互操作探测成功时：

```cpp
av_frame_unref(dst);
av_frame_ref(dst, srcHardwareFrame);
dstFrame.setStorage(FrameStorage::GpuSurface);
```

`FrameQueue` 仍通过 FFmpeg 引用计数管理所有权，不暴露裸 surface 生命周期。

### 6.2 必须缩小硬件帧队列

当前 CPU frame 队列可以较深，因为解码 surface 在下载后会较快释放。真正零拷贝后，
每个排队 `AVFrame` 都会占住一个硬件 decode surface。若仍保留 20～25 帧队列，再叠加
FFmpeg 参考帧和线程帧，很容易超过 NVDEC/D3D11 surface 上限。

建议：

```cpp
constexpr int kGpuSurfaceQueueSize = 4;
constexpr int kGpuSurfaceKeepLast = 1;
```

原则：

- 本地零拷贝模式视频 frame 队列最大 4～6 帧。
- 解码器线程数继续保持受控，不为 2x 播放盲目加线程。
- 队列满时 decode 线程等待渲染释放 surface，不能额外下载到 CPU 绕过背压。
- seek/stop/switch 时先停止渲染引用，再 flush 队列和 decoder。

最终 surface 数量必须根据 codec reference frames、FFmpeg backend 和 frame queue 一起计算，
并保证不超过硬件后端安全上限。

### 6.3 keep-last

暂停和 UI 重绘需要保留最后一帧。硬件模式下 keep-last 持有的是：

- 一份解码 surface 引用；或
- 已缩放完成的 720p/1080p 输出纹理。

优先保留输出纹理并尽快释放解码 surface，可以减少 decode surface 占用。暂停时直接重绘
缓存输出纹理，不重复执行缩放。

## 七、分辨率配置与缩放规则

### 7.1 输出档位

```cpp
enum class LocalOutputResolution {
    Original,
    P720,
    P1080
};
```

标准输出画布：

| 档位 | 横屏画布 | 竖屏画布 |
|------|----------|----------|
| 720p | 1280 × 720 | 720 × 1280 |
| 1080p | 1920 × 1080 | 1080 × 1920 |

### 7.2 只提供升分辨率

每个目标档位都通过 `hasUpscaleTarget()` 独立判断：旋转后的源显示尺寸必须能完整放入
目标画布，并且至少一个维度小于目标内容区域。这样不会把 2048×858 之类的超宽视频
误判为“低于 1080p”，然后先缩小宽度再补高。

典型横屏视频：

- 源尺寸不超过 1280×720 且不是原生 720p：显示 `Original / 720p / 1080p`。
- 源尺寸超过 720p但能完整放入 1920×1080：显示 `Original / 1080p`。
- 源尺寸不能完整放入 1920×1080：不显示本地升分辨率入口。
- 不把 1080p 或更高视频缩小成 720p；这不是本功能目标。

对于旋转视频，以应用 rotation 后的显示宽高判断横屏/竖屏。

### 7.3 宽高比

缩放必须保留：

- 显示宽高比；
- sample aspect ratio；
- rotation；
- crop 元数据；
- 偶数宽高，保证 NV12/P010 对齐。

内容按 `contain` 放入固定目标画布，剩余区域填黑，不拉伸人物或画面。

### 7.4 缩放质量

优先级：

1. Windows D3D11 Video Processor 的高质量硬件滤镜。
2. macOS/GL 路径使用 GPU bicubic 或 Lanczos shader。
3. GPU 压力过高时可降为 bilinear，但必须记录一次限频 WARN。

v0.8.0 是传统 GPU 插值升分辨率，不是 AI 超分辨率，不会凭空恢复源视频不存在的纹理、
文字或人脸细节。

### 7.5 色彩

GPU pipeline 必须继续尊重现有色彩元数据：

- BT.601 / BT.709 / BT.2020；
- limited/full range；
- 8-bit NV12；
- 后端支持时处理 10-bit P010。

缩放不能改变原视频色域语义。输出到普通 OpenGL BGRA/RGBA 纹理时，转换矩阵和 range
必须与当前 `video.frag` 行为一致。

## 八、复用网络画质按钮

### 8.1 统一 UI 模型

现有 `Controller::QualityItem` 和 `renderQualityButton()` 仅服务网页画质，建议重构为
通用分辨率选项：

```cpp
enum class ResolutionOptionKind {
    NetworkFormat,
    LocalGpuOutput
};

struct ResolutionItem {
    ResolutionOptionKind kind;
    std::string id;
    std::string label;
    int width = 0;
    int height = 0;
};
```

按钮仍只有一个，位置和样式完全复用：

```text
网页视频：
    [1080P] -> 网络 formatId 列表 -> switchQuality()

本地硬件升分辨率：
    [Original] -> Original / 720p / 1080p -> setLocalOutputResolution()

其他场景：
    不显示按钮
```

本地文件和网页视频来源互斥，因此不会在同一个菜单混合“服务端画质”和“本地 GPU 输出”。

### 8.2 显示时机

硬件解码器初始化成功不代表 surface 一定能导入 OpenGL。为避免按钮先出现、点击后又失败：

1. 打开本地媒体时状态为 `Probing`，不显示按钮。
2. 第一张硬件 frame 成功通过 interop 导入并完成一次测试缩放后，状态改为 `Ready`。
3. Controller 下一帧读取能力快照并生成本地分辨率列表。
4. 如果运行时发生设备丢失或连续导入失败，立即恢复 Original 并隐藏按钮。

### 8.3 切换行为

点击 720p/1080p 后通过命令队列进入控制线程：

```cpp
player.setLocalOutputResolution(LocalOutputResolution::P1080);
```

切换不执行：

- 不 seek；
- 不重启 demux；
- 不重建 video decoder；
- 不 flush packet/frame 队列；
- 不改变音频或时钟。

只在渲染线程创建新的目标 surface/FBO；创建成功后原子切换到新输出，旧资源延迟到当前帧
结束后释放。创建失败则保持旧档位，并在 UI 中恢复原选择。

### 8.4 窗口尺寸

切换输出分辨率不自动放大播放器窗口，避免 360p -> 1080p 时窗口突然占满桌面。输出纹理
按当前窗口或全屏 viewport 显示；用户进入全屏后才能完整观察 1080p 输出效果。

媒体信息面板同时展示：

```text
Source     : 640 x 360
GPU Output : 1920 x 1080
```

## 九、运行状态与互斥控制

### 9.1 状态机

```text
Unavailable
  | 本地文件 + 硬解码 + interop 探测
  v
Probing
  | 首帧导入与测试缩放成功
  v
ReadyOriginal
  | 用户选择 720p/1080p
  v
Upscaling
  | 用户选择 Original
  +-------------------------> ReadyOriginal

ReadyOriginal / Upscaling
  | speed > 2x、来源变化、硬件失败
  v
Disabling
  | 释放输出纹理和互操作句柄
  v
Unavailable
```

### 9.2 速度切换顺序

未来 v0.9.0 从 2x 切入 4x/8x/16x：

```text
SetSpeedCommand
    -> 检查本地升分辨率是否启用
    -> 在渲染线程切回 Original
    -> 等待本帧释放共享纹理锁
    -> 销毁 720p/1080p 输出资源
    -> 更新 capability：高倍模式下不可用
    -> 启动 v0.9.0 高倍数时钟与降载策略
```

不能先进入高倍模式再异步释放升分辨率资源，否则 decode surface、缩放 surface 和高倍队列
可能同时占用显存。

从高倍模式切回 `<=2x`：

```text
退出高倍模式
    -> 重建普通完整参考链
    -> interop 重新探测
    -> 成功后显示按钮，默认 Original
```

### 9.3 来源变化

切换文件、切换网络画质或返回主页时：

1. 隐藏本地分辨率菜单；
2. 结束当前 GL/D3D/CV texture 使用；
3. 释放输出 FBO 和共享句柄；
4. flush GPU frame queue；
5. 最后释放 decoder device/context。

资源销毁顺序不能反过来，否则共享纹理可能引用已经释放的硬件设备。


实际切换由控制线程的 `setLocalOutputResolutionInternal()` 完成。

### 10.2 `VideoDecoder`

新增能力：

```cpp
bool isHardwareDecodeActive() const;
HardwareBackend getHardwareBackend() const;
void setFrameOutputMode(FrameOutputMode mode);
GpuDecoderContext getGpuInteropContext() const;
```

`GpuDecoderContext` 是不透明 RAII 句柄，头文件不暴露 `ID3D11Device*`、`CVPixelBufferRef`
或 CUDA 类型。

### 10.3 `Frame`

增加存储类型：

```cpp
enum class FrameStorage {
    CpuPlanes,
    GpuSurface
};
```

GPU surface 仍由 `AVFrame`/`AVBufferRef` 管理，`FrameStorage` 只让下游选择渲染路径，不再
创建第二套裸指针所有权系统。

### 10.4 `GLRenderer`

新增：

```cpp
void renderExternalTexture(unsigned int textureId,
                           int textureWidth,
                           int textureHeight,
                           int contentX,
                           int contentY,
                           int contentWidth,
                           int contentHeight);
```

`unsigned int` 隔离 `GLuint`，保持头文件不依赖平台 OpenGL SDK。

现有 CPU YUV/NV12 `renderFrame()` 保留，作为软件解码和互操作失败后的回退路径。

### 10.5 `Controller`

将内部画质菜单改为统一 resolution 模型，但保留网络接口兼容：

```cpp
void setNetworkQualities(...);
void setLocalResolutionOptions(...);
void clearResolutionOptions();
```

点击时按 `ResolutionOptionKind` 分发到 `switchQuality()` 或
`setLocalOutputResolution()`。

## 十一、线程安全与资源所有权

| 资源/状态 | 所有线程 | 约束 |
|-----------|----------|------|
| `AVCodecContext` | video decode 线程 | 其他线程不得修改 |
| 硬件 `AVFrame` 引用 | FrameQueue 转移 | 用 FFmpeg 引用计数跨线程 |
| OpenGL texture/FBO | render/control 线程 | 仅持有当前 GL context 的线程创建销毁 |
| D3D11 Video Processor | render线程 | 与 GL interop lock/unlock 同线程串行 |
| capability snapshot | 控制线程写、UI 线程读 | mutex 下整体复制或原子版本号 |
| resolution command | UI 投递、控制线程执行 | 不从 UI 回调直接改 GPU 资源 |

### 11.1 每帧互操作顺序

Windows D3D11/WGL 示例：

```text
FrameQueue::peekRef() 持有 surface
    -> 创建/复用 D3D input view
    -> VideoProcessorBlt 到共享输出 texture
    -> flush/同步 D3D 命令
    -> wglDXLockObjectsNV
    -> OpenGL 采样输出 texture
    -> wglDXUnlockObjectsNV
    -> 释放本帧 surface 引用
```

不能在持有 WGL interop lock 时等待 FrameQueue、seek 或 join worker，避免跨 API 死锁。

### 11.2 双缓冲

720p/1080p 输出使用两张 GPU texture：

- 一张供 D3D/缩放 pass 写入；
- 一张供 OpenGL 当前帧读取；
- 帧边界交换。

双缓冲用于避免 GPU read/write hazard，不意味着 CPU 像素拷贝。

## 十二、失败与降级

### 12.1 打开阶段失败

以下任一项失败时：

- 硬件设备创建失败；
- 实际输出变成软件像素格式；
- D3D/CUDA/CoreVideo 与 OpenGL 不在同一 GPU；
- WGL/EGL/CoreVideo interop 缺失；
- 720p/1080p 输出纹理分配失败；
- 测试帧导入失败；

处理：

1. 保持现有普通播放路径。
2. 不显示本地分辨率入口。
3. 记录一条包含 backend 和原因的 WARN。
4. 不把“升分辨率不可用”升级为播放器错误。

### 12.2 运行时失败

连续导入或缩放失败达到阈值后：

1. 当前坏帧跳过，不阻塞主循环。
2. capability 改为 `Failed`。
3. UI 隐藏本地分辨率入口。
4. 控制线程停止 worker，并在安全边界重建为软件解码器。
5. 清空旧硬件帧队列后恢复普通 CPU frame 上传播放。

降级后不允许继续保留硬件解码再下载帧，否则会重新引入被本方案禁止的
GPU→CPU→GPU 路径。

### 12.3 显存不足

- 1080p 创建失败但 720p 成功：只显示 Original/720p。
- 两个目标都失败：隐藏入口。
- 不能通过缩短解码器必要 surface 池来强行分配缩放纹理。
- 重复切换分辨率必须复用资源，不能每帧创建 texture/FBO。

## 十三、截图、字幕和录制

### 13.1 截图

- 当前零拷贝基础实现会拒绝直接读取 D3D11/VideoToolbox 硬件 `AVFrame`，避免把
  GPU 句柄误当作 CPU plane；在显式 GPU readback 接入前，硬件播放截图会跳过并记录 WARN。
- PNG/JPEG 截图默认捕获最终 GPU 输出，因此选择 1080p 时截图为 1920×1080。
- 原始 YUV/NV12 截图仍表示源解码帧，保持原始分辨率和像素格式。
- GPU 输出截图若必须回读 CPU，只在用户按截图时发生，不破坏正常播放零拷贝承诺。

### 13.2 字幕

字幕属于 UI 合成层，应在升分辨率视频纹理显示之后按窗口坐标绘制：

```text
GPU 视频缩放 -> 输出纹理 -> 窗口适配 -> ImGui 字幕/UI
```

这样切换 720p/1080p 不会改变字幕字体大小或把字幕烘焙进视频纹理。

### 13.3 录像

本功能不改变录像语义：

- 现有 packet 转封装录像继续记录原始分辨率。
- 不把 720p/1080p GPU 输出重新编码进录像。
- 如果未来需要“录制升分辨率结果”，应作为独立的硬件编码功能设计，不能混入本播放链路。

## 十四、统计与可观测性

当前按 `S` 打开的统计面板已经提供硬件链路基础诊断：

```text
Decoder   : HARDWARE / SOFTWARE
Backend   : D3D11VA / VideoToolbox / Software
Device    : 实际 DXGI 显卡名称 / macOS GL_RENDERER / CPU
Zero-copy : ACTIVE / INACTIVE
Path      : 当前平台互操作路径
```

其中 `hardwareInteropReady` 表示平台链路已成功初始化，`hardwareFrameActive` 表示当前
缓存画面确实来自硬件 surface。两者分开记录，确保软件帧回退后不会继续误报零拷贝。
Windows 设备名称从 FFmpeg 实际使用的 D3D11 device 反查 DXGI adapter，不能另行显示
系统枚举到的第一块显卡。

升分辨率功能后续新增统计：

```cpp
struct GpuVideoStats {
    bool hardwareDecodeActive;
    bool zeroCopyInteropActive;
    GpuInteropBackend interopBackend;
    int sourceWidth;
    int sourceHeight;
    int outputWidth;
    int outputHeight;
    double gpuScaleTimeMs;
    uint64_t hwFrameDownloadCount;
    uint64_t cpuVideoUploadBytes;
    uint64_t interopFailureCount;
};
```

真正 GPU 零拷贝模式的关键验收值：

```text
hwFrameDownloadCount = 0
cpuVideoUploadBytes  = 0
```

日志：

- interop 探测成功/失败各打印一次。
- 分辨率切换打印旧档位、新档位和 backend。
- 不逐帧打印缩放日志。
- 每秒状态日志可附加 `GPUScale` 和输出尺寸。

## 十五、性能目标

### 15.1 帧预算

60 FPS 每帧预算约 16.67 ms，30 FPS 每帧预算约 33.33 ms。

目标：

| 场景 | GPU 缩放目标耗时 |
|------|------------------|
| 360p -> 720p | `< 1.0 ms` |
| 360p/480p -> 1080p | `< 2.0 ms` |
| 720p -> 1080p | `< 1.5 ms` |

具体值受 GPU 和驱动影响，功能门禁不以固定型号判断，而以资源创建和运行稳定性判断。

### 15.2 显存估算

1080p BGRA 单纹理约：

```text
1920 * 1080 * 4 ≈ 7.9 MiB
```

双缓冲约 15.8 MiB，加上 D3D view 或 CoreVideo texture view/FBO 元数据。解码 surface
通常远大于这部分，因此重点是限制 GPU frame queue，而不是省掉必要的输出双缓冲。

### 15.3 2x 播放

升分辨率功能必须在 2x 下保持：

- 音视频时钟沿用现有普通倍速逻辑；
- 解码队列不因 surface 不足死锁；
- UI/关闭操作保持响应；
- GPU 缩放不触发 CPU fallback；
- 若设备无法同时承担 2x 解码和 1080p 缩放，可降级到 720p 或 Original。

降级只影响分辨率，不得擅自改变用户选择的播放速度。

### 16.2 功能测试

1. 播放中在 Original/720p/1080p 间反复切换 100 次。
2. 切换期间不 seek，PTS、AClock、VClock 均保持单调。
3. 暂停后切换分辨率，恢复时显示正确目标纹理。

### 16.3 零拷贝验证

1. GPU 模式的调用图中不存在 `av_hwframe_transfer_data()`。

1. 连续播放 2 小时，显存、句柄、AVFrame 引用数量稳定。
2. 频繁 seek/暂停/切速/关闭无资源泄漏和死锁。
3. 模拟 device lost/interop 失败后可降级普通播放。
4. 窗口关闭顺序不让 WGL/D3D 共享资源引用已销毁 device。
5. macOS 关闭顺序不让 GL fence、CGL texture 或 `CVPixelBufferRef`
   引用已销毁的 IOSurface/VideoToolbox session。

### 16.5 macOS 专项测试

1. Apple Silicon 上分别验证 H.264/HEVC 的 VideoToolbox 硬件 frame。
2. 可用 Intel Mac 上验证同一 VideoToolbox/CoreVideo/OpenGL 链路。
3. Instruments/Metal System Trace 确认播放期间没有持续 CPU frame download。
4. 反复切换 720p/1080p 后 CGL 纹理槽和 IOSurface 引用数量稳定。
5. Retina 与非 Retina viewport 下输出尺寸、内容比例和字幕坐标正确。
6. CMake 和 xmake 两套构建都能编译平台互操作实现并链接全部系统 framework。

### 16.6 与 v0.9.0 联合测试

```text
1x + 1080p upscale
    -> 切 4x
    -> 自动 Original、入口隐藏、高倍模式启动
```

## 十九、完成标准

v0.8.0 只有同时满足以下条件才视为完成：

1. 低分辨率本地文件在实际硬件互操作可用时显示 Original/720p/1080p。
2. 软件解码、网络地址、纯音频、图片和大于 2x 的场景不显示该入口。
3. 切换分辨率不 seek、不重启媒体、不产生临时文件。
4. 视频像素路径不执行 GPU→CPU 下载和 CPU→GPU 每帧上传。
5. GPU 缩放保持宽高比、rotation、色彩空间和量化范围。
6. 2x 下可稳定播放；能力不足时降级分辨率而不是卡住。
7. 运行时互操作失败可回退普通播放。
8. 网页视频原有网络画质切换无回归。
9. 与 v0.9.0 高倍数模式严格互斥，切换顺序和资源释放正确。
10. Windows 和 macOS 均完成真实零 CPU 拷贝链路，不允许任一平台保留占位实现。
11. Windows CMake/xmake 构建通过；macOS CMake/xmake 构建及目标机器播放验证通过。
12. README、硬件加速文档和相关配置说明同步更新。
