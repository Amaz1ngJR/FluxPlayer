# FluxPlayer v0.9.0 高倍数播放技术方案

> 版本目标：v0.9.0｜状态：设计阶段
>
> 本方案遵循 `docs/AI开发守则.md`：不引入新依赖，跨线程状态使用原子变量或明确的锁，
> 新增源文件同步加入 CMake/xmake，代码使用中文注释，功能完成后同步 README 与配置模板。
>
> 前置互斥功能参见 [`v0.8.0本地实时升分辨率.md`](v0.8.0本地实时升分辨率.md)。

---

## 一、需求与边界

### 1.1 功能目标

1. 本地视频支持 `4.0x`、`8.0x`、`16.0x` 播放。
2. `4.0x` 及以上统一定义为“高倍数模式”，允许不播放音频。
3. 播放 RTSP 等实时网络地址时，如果上游按 4x/8x/16x 速度推送媒体数据，
   播放器必须持续读取和快速处理，不能因为仍按 1x 消费而让网络、packet 队列和
   frame 队列不断积压。
4. 解码能力不足时允许降低画面采样密度，但必须保持：
   - 播放进度持续向前；
   - UI 和关闭操作保持响应；
   - 内存占用有界；
   - 实时流最终回到直播边缘附近。
5. 从普通倍速切入高倍数、在高倍数之间切换、再切回普通倍速时，不得出现时钟倒退、
   画面永久冻结、旧音频重新播放或线程无法退出。

### 1.2 非目标

- v0.9.0 不为 4x/8x/16x 提供保调音频。
- v0.9.0 高倍数模式与 v0.8.0 本地实时升分辨率互斥。进入 4x/8x/16x 前必须
  关闭 GPU 升分辨率并恢复 `Original` 输出；高倍模式中不显示本地分辨率切换入口。
- 不保证显示源视频的每一帧。30 FPS 视频以 16x 播放时，每秒需要处理 480 个媒体帧，
  普通 60 Hz 显示器本身也无法逐帧呈现。
- 不对服务端进行倍速控制；播放器只消费已经到达的 RTSP 数据。
- 不实现 RTSP 时移缓冲。实时流只能追赶直播边缘，不能在没有缓存的情况下主动播放
  尚未到达的数据。
- 不改变 0.5x～2.0x 的现有音频变速行为。

## 二、必须区分的两类“RTSP 4 倍速”

“4 倍速推流”可能代表两种完全不同的时间戳语义，播放器不能仅凭画面运动快慢判断。

### 2.1 内容已经加速，但时间戳仍按墙钟推进

例如服务端先把视频做成快动作，再以普通 30 FPS、每秒 1 秒 PTS 的节奏推送。

```text
1 秒墙钟时间 -> 收到约 1 秒媒体 PTS
```

从播放器角度看它仍是普通 1x 实时流。画面内容虽然快，但网络吞吐、解码吞吐和时钟都
不需要特殊处理，不应误判为高倍数输入。

### 2.2 原始媒体时间以 4 倍墙钟速度到达

例如 1 秒墙钟时间内，上游发送了原视频连续 4 秒的 packet，packet PTS 也前进约 4 秒。

```text
1 秒墙钟时间 -> 收到约 4 秒媒体 PTS
```

这才是本方案所称的“4x 高倍数推流”。如果播放器仍让主时钟每秒只推进 1 秒，数据会以
“生产 4、消费 1”的速度积压，最终触发背压、网络接收延迟和画面冻结。

### 2.3 统一术语

| 名称 | 含义 |
|------|------|
| `requestedRate` | 用户对本地/点播文件选择的播放倍速 |
| `sourceRate` | 实时流的媒体 PTS 相对墙钟时间的到达速率 |
| `effectiveRate` | 当前调度器实际采用的媒体时钟速率 |
| 普通模式 | `effectiveRate < 4.0`，沿用现有音视频播放链路 |
| 高倍数模式 | `effectiveRate >= 4.0`，视频优先、音频关闭、允许分级降载 |

规则如下：

```text
本地文件或可 seek 点播流：
    effectiveRate = requestedRate

RTSP/RTMP 等真正实时流：
    effectiveRate = sourceRate
    requestedRate 不用于“凭空加速”尚未到达的数据
```

如果服务端重写时间戳、PTS 缺失或网络抖动导致自动检测不可靠，使用会话级
`Auto / 1x / 4x / 8x / 16x` 手动来源速率作为兜底。

## 三、当前实现的不足

现有 `docs/播放速度技术方案.md` 面向 0.5x～2.0x，直接扩展倍率列表会有以下问题。

| 当前行为 | 高倍数下的问题 |
|----------|----------------|
| `audioOutputCallback()` 按倍率多取音频并重采样 | 8x/16x 会显著增加回调工作量，音频队列容易欠载，且声音不可用 |
| 视频帧完整解码后才在 `renderVideoFrame()` 概率丢弃 | 已经支付了解码和 GPU/CPU 传输成本，无法解决解码吞吐瓶颈 |
| 每次渲染循环最多消费一个视频帧 | 60 Hz 主循环最多消费约 60 帧/秒，无法清空 16x 输入产生的数百帧 |
| 实时流外部时钟默认按 1x 推进 | 4x PTS 输入会持续堆积，播放器越来越落后于直播边缘 |
| demux 软背压通过等待队列释放空间 | 实时高倍流中等待会把积压转移到 FFmpeg/系统 socket，延迟仍会增长 |
| 统计只记录最终显示阶段的 `Dropped` | 无法区分显示采样、解码器丢弃和直播 GOP 追赶 |
| 普通模式以音频时钟参与同步 | 高倍模式关闭音频后必须显式切换到外部视频时钟 |

因此，高倍数播放必须是独立策略，而不是把当前最大值从 2 改成 16。

## 四、总体设计

### 4.1 数据流

```text
用户选择 4x/8x/16x，或检测到 RTSP sourceRate >= 4
                            |
                            v
                 HighSpeedController
          +-----------------+------------------+
          |                 |                  |
          v                 v                  v
    DemuxWorker        DecodeWorker       Player::render
    丢弃播放音频包      设置 FFmpeg         批量消费到期帧
    监测来源速率        discard 策略        只渲染最新候选帧
    实时流 GOP 追赶      统计解码压力        外部时钟按有效倍率推进
          |                 |                  |
          +-----------------+------------------+
                            |
                            v
                 有界队列、单调进度、可响应 UI
```

### 4.2 新增组件

新增 `HighSpeedController`，避免继续把速率检测、降载决策和直播追赶状态堆入 `Player`。

```text
include/FluxPlayer/core/HighSpeedController.h
src/core/HighSpeedController.cpp
```

职责：

1. 保存当前高倍数策略快照。
2. 估算 RTSP 输入 `sourceRate`。
3. 根据倍率、队列延迟和解码压力选择丢帧级别。
4. 决定实时流是否进入“等待下一个关键帧追赶”状态。
5. 汇总高倍数统计数据。

不负责：

- 不直接读写 FFmpeg 解码器；
- 不操作 OpenGL；
- 不创建或销毁 worker；
- 不直接更新 UI。

这些副作用仍由各自所有者线程执行。

### 4.3 策略快照

```cpp
enum class SourceRateMode {
    Auto,
    X1,
    X4,
    X8,
    X16
};

enum class DecodeDiscardLevel {
    Default,   // 正常解码
    NonRef,    // 优先跳过非参考帧
    Bidir,     // 跳过双向预测帧
    NonKey     // 只保留关键帧
};

struct HighSpeedSnapshot {
    bool enabled = false;
    bool liveSource = false;
    bool suppressAudio = false;
    double requestedRate = 1.0;
    double sourceRate = 1.0;
    double effectiveRate = 1.0;
    DecodeDiscardLevel discardLevel = DecodeDiscardLevel::Default;
    bool catchUpToKeyframe = false;
};
```

`HighSpeedController` 内部用 mutex 更新完整状态，并向 demux、decode、render 线程返回值拷贝
快照。各线程不得长期保存内部引用，避免切速时读取到一半新、一半旧的策略。

## 五、本地文件高倍数播放

### 5.1 时钟

本地文件继续使用 `AVSync` 的外部时钟，但高倍模式强制选择 `EXTERNAL_CLOCK`：

```text
mediaClock = anchorMediaPTS + wallElapsed * effectiveRate
```

切速前先结算旧时钟，再更新 anchor 和 rate，保证时钟连续。现有
`AVSync::setPlaybackRate()` 已具备连续切速基础，但需要补充：

1. 高倍模式不能再让静音后的 AClock 成为主时钟。
2. 从高倍模式切回普通模式时，音频恢复完成前仍使用外部时钟。
3. 收到第一段有效新音频后，再平滑切回普通模式配置的主时钟。

### 5.2 显示阶段改为确定性采样

现有概率丢帧会造成显示节奏不稳定。高倍模式改成“批量消费、只显示最新到期帧”：

```cpp
Frame latestDueFrame;
while (videoQueue->peekRef(candidate)) {
    if (candidate.pts > masterClock + kScheduleToleranceSec) {
        break;
    }
    latestDueFrame = candidate;
    videoQueue->consume();
    ++presentationConsumed;
}

if (latestDueFrame.valid()) {
    render(latestDueFrame);
    presentationDropped += presentationConsumed - 1;
}
```

这样一次 VSync 可以跳过任意数量的过期帧，不再受“每次循环只消费一帧”的 60 FPS 上限
约束。丢弃是按 PTS 决定的，结果可重复，也不会因为帧计数随机取模产生抖动。

目标显示帧率默认不超过显示器刷新率，并建议控制在 30 FPS 左右。高倍数表示媒体时间
推进更快，不表示必须让窗口以 240/480 FPS 刷新。

### 5.3 解码阶段降载

仅在显示阶段丢帧无法节省解码成本，因此由视频 decode 线程在 packet 边界应用
FFmpeg `skip_frame` 策略：

| 倍率 | 初始策略 | 压力升高后的策略 | 最低保障 |
|------|----------|------------------|----------|
| 4x | `AVDISCARD_NONREF` | `AVDISCARD_BIDIR` | 保留关键帧和必要参考链 |
| 8x | `AVDISCARD_BIDIR` | `AVDISCARD_NONINTRA` | 至少显示帧内编码帧 |
| 16x | `AVDISCARD_NONINTRA` | `AVDISCARD_NONKEY` | 关键帧预览 |

注意：

- 具体 codec/hardware backend 可能不完全执行 `skip_frame`，不能把它作为唯一保护。
- 软件解码在 8x/16x 可同步设置 `skip_loop_filter`，减少不会显示帧的后处理成本。
- 不提高硬件解码线程数。NVDEC 等后端的 surface 数量有上限，盲目增加线程会再次触发
  “Using more than 32 decode surfaces”一类初始化失败。
- 降低丢弃级别时，当前参考链可能不完整。必须先 flush 解码器并等待下一个关键帧，
  不能直接从 `NONKEY` 切回普通解码。

### 5.4 16x 的 packet 快速路径

当策略已经降级到 `NonKey` 时，demux 可以在入视频 packet 队列前直接跳过非关键包：

```text
普通路径：demux -> 所有视频 packet -> decoder -> 部分帧输出
16x 降级：demux -> 仅关键 packet -> decoder -> 关键帧输出
```

只有 `NonKey` 模式允许在解码前这样丢包。4x/8x 不能随意丢 P 帧，因为后续参考帧可能
依赖它们。所有 recording 写包必须发生在播放丢弃判断之前，保证录像保留原始流内容。

## 六、高倍模式的音频策略

### 6.1 固定规则

v0.9.0 中只要 `effectiveRate >= 4.0`：

1. 停止并释放 `AudioOutput`，不持续向声卡提交静音 buffer。
2. demux 仍先把音频 packet 交给录制模块，然后不再放入播放用 audio packet 队列。
3. 停止 audio decode worker，flush audio packet/frame 队列。
4. `audioDrainedEof_` 对播放结束判断视为已完成。
5. 主时钟强制使用外部时钟，不允许读取停止推进的 AClock。

这不是简单把音量设为 0。只静音仍会消耗音频解码、重采样和设备回调资源，达不到高倍数
降载目的。

### 6.2 从普通模式进入高倍模式

控制线程按以下顺序执行：

```text
设置 suppressAudio=true，阻止 demux 再投递播放音频
    -> 停止 AudioOutput，等待回调线程退出
    -> abort 并 join audio decode worker
    -> flush audio packet/frame 队列和 AudioDecoder
    -> 标记 audioDrainedEof=true
    -> 切换外部主时钟
```

音频 worker 的单独停止需要为 `QueueManager` 增加按流的
`abortAudio()/startAudio()/flushAudio()`，不能调用 `abortAll()` 影响仍在工作的画面链路。

### 6.3 从高倍模式返回普通模式

本地文件返回 0.5x～2.0x 时：

1. 以 `lastRenderedPTS_` 为恢复目标。
2. 在控制线程发起一次内部 seek，重新建立完整视频参考链和音频位置。
3. 重建 audio 队列、AudioDecoder worker 和 AudioOutput。
4. 至少缓存规定数量的音频帧后启动设备。
5. 第一段有效音频到达后再切换主时钟，禁止播放高倍模式之前残留的旧音频。

允许此次切换产生一次短暂重缓冲，但不能让 AClock 倒退或画面停住。

对于本身仍以 4x/8x/16x 到达的实时流，即使 UI 默认倍速是 1x，也继续关闭音频；没有时移
缓冲就无法把 4x 到达的实时音频无损降为 1x。

## 七、RTSP 高倍数推流

### 7.1 来源速率检测

在 `DemuxWorker` 中对视频 packet 的有效 PTS/DTS 和 `steady_clock` 到达时间采样：

```text
sampleRate = (latestMediaPTS - windowStartMediaPTS)
             / (latestArrivalTime - windowStartArrivalTime)
```

检测规则：

1. 使用 1.5～2.0 秒滑动窗口，避免 RTP 短时突发导致误判。
2. 忽略 `AV_NOPTS_VALUE`、负跨度、零跨度和明显 discontinuity。
3. 将样本限制在合理范围后做 EWMA 平滑。
4. 只有连续 3 个窗口落在档位容差内才切换：
   - `0.8～1.3` -> 1x
   - `3.2～5.0` -> 4x
   - `6.4～10.0` -> 8x
   - `12.8～20.0` -> 16x
5. 降档需要更多连续窗口，形成迟滞，避免网络抖动时在 1x/4x 间反复切换。
6. seek、PTS 回绕、RTSP reconnect、stream serial 变化时重置检测窗口。

自动检测只判断“媒体 PTS 的到达速度”，不会分析画面内容。

### 7.2 手动来源速率

网络 URL 输入区增加会话级来源速率选择：

```text
Source rate: [ Auto | 1x | 4x | 8x | 16x ]
```

- 默认 `Auto`。
- 手动值立即覆盖检测结果。
- 该值只对本次打开的 URL 生效，不写入全局 `playbackSpeed`，避免播放下一个普通 RTSP
  地址时误用 4x。
- 现有 `Player::open()` 保持兼容，通过带默认参数的 `OpenOptions` 传入：

```cpp
struct OpenOptions {
    SourceRateMode sourceRateMode = SourceRateMode::Auto;
};
```

### 7.3 实时流队列策略

普通实时流的软背压可以短暂等待，高倍实时流则必须优先保持 socket 持续读取：

```text
普通 RTSP：
    packet 队列偏满 -> demux 短暂等待

高倍 RTSP：
    packet 队列偏满 -> 提升解码丢弃级别
                    -> 超过硬延迟阈值时追赶到下一个关键帧
                    -> demux 不在软阈值上长期睡眠
```

仍保留现有 64 MB 总硬上限和单路硬上限。任何情况下都不能用“无限扩容”换取不丢帧。

### 7.4 直播延迟定义

不能直接用媒体秒数判断直播是否落后，因为 4x 输入的 4 秒媒体时间只对应 1 秒墙钟。

```text
packetLagWall =
    videoPacketQueue.durationMediaSeconds / sourceRate

decodedLagWall =
    (lastEnqueuedVideoPTS - lastRenderedPTS) / sourceRate

liveLagWall = max(packetLagWall, decodedLagWall)
```

建议阈值：

| 状态 | 墙钟延迟 | 动作 |
|------|----------|------|
| 正常 | `< 0.5s` | 使用当前倍率的初始 discard 策略 |
| 压力 | `0.5～1.5s` | 提升一级 discard，渲染端批量跳过到期帧 |
| 严重落后 | `> 1.5s` | 进入 GOP 追赶 |
| 恢复 | 连续 2 秒 `< 0.3s` | 逐级降低 discard，禁止一次跳回 Default |

阈值均定义为具名常量，后续根据测试数据调整，不作为首版用户配置项。

### 7.5 GOP 追赶

当高倍 RTSP 严重落后时，继续解码旧 GOP 没有价值：

```text
进入 CatchUpToKeyframe
    -> 继续从 RTSP socket 读取，丢弃播放用视频 packet
    -> 录制模块仍先接收原始 packet
    -> 遇到下一个关键 packet
    -> flush video packet queue，并递增 serial
    -> 将该关键 packet 作为新 serial 的第一包入队
    -> decode 线程观察 serial 变化后 flush decoder/frame queue
    -> 外部时钟重新锚定到新关键帧 PTS
    -> 退出追赶状态
```

该流程从关键帧重新建立参考链，不会像任意删除 P 帧那样造成连续花屏。

保护规则：

- 两次 GOP 追赶之间设置最小冷却时间，避免频繁 flush。
- 等待关键帧超过 2 秒墙钟时记录一次限频警告。
- 超过 5 秒仍无关键帧，RTSP 执行一次完整 reconnect，请求服务端重新发送可解码起点。
- reconnect 失败沿用现有指数退避，不在新模块中复制网络重试逻辑。

### 7.6 直播时钟跟随

检测或手动指定 `sourceRate=4` 后，外部时钟以 4x 推进。为抵抗网络抖动，不能每收到一个
packet 就硬跳时钟，而应使用小范围追赶：

```text
targetMediaPTS = latestDecodedPTS - targetLatencyWall * sourceRate
clockError     = targetMediaPTS - externalClock

小误差：在 sourceRate 附近做有限比例微调
大误差：不加速扫完整个旧队列，直接走 GOP 追赶
```

外部时钟必须单调。任何自动检测降档、reconnect 或 PTS 重置都通过重新锚定完成，不允许
把时钟写回更小值。

### 7.7 暂停与恢复

高倍实时流暂停时不能无限缓存：

- 暂停期间继续读取网络，但丢弃播放 packet，仅保留最新直播状态。
- 恢复时进入 `CatchUpToKeyframe`，从下一个关键帧重新起播。
- 本地文件暂停保持现有语义，不读取或丢弃额外内容。

## 八、自适应降载状态机

```text
Normal
  | effectiveRate >= 4
  v
EnteringHighSpeed
  | 音频停止、外部时钟就绪
  v
HighSpeedSteady
  | 队列延迟超过硬阈值
  v
CatchUpToKeyframe
  | 收到关键帧并完成 serial 切换
  +--------------------------> HighSpeedSteady

HighSpeedSteady
  | effectiveRate < 4
  v
LeavingHighSpeedWaitKeyframe
  | 本地 seek / 实时流新关键帧建立完整参考链
  v
AudioRebuffering
  | 第一段有效音频到达
  v
Normal
```

状态转换由控制线程发起。demux/decode 线程只能发布观测值或完成事件，不能直接创建、
销毁其他线程拥有的组件。

特殊处理：

- 4x -> 8x -> 16x：可以立即提高 discard 等级。
- 16x -> 8x/4x：需要等待关键帧后降低 discard，避免使用不完整参考链。
- 高倍模式 seek：seek serial 优先，清空追赶状态并从目标关键帧重新评估策略。
- 循环播放：回到 0 秒后重置速率检测，但保留用户选择的本地 `requestedRate`。
- 关闭播放：沿用统一的 `shouldQuit_ -> stop audio -> abort queues -> join workers` 顺序。

## 九、模块接口与修改点

### 9.1 `Player`

保留现有公开接口：

```cpp
void setPlaybackSpeed(double speed);
double getPlaybackSpeed() const;
```

新增或拆分私有职责：

```cpp
void enterHighSpeedMode(const HighSpeedSnapshot& policy);
void leaveHighSpeedMode(double resumePTS);
void applyClockPolicy(const HighSpeedSnapshot& policy);
bool selectLatestDueVideoFrame(Frame& selected);
```

`setPlaybackSpeedInternal()` 只负责控制线程上的状态转换，不直接操作 demux/decode 线程内部
对象。跨线程策略通过 `HighSpeedController` 快照传递。

### 9.2 `DemuxWorker`

新增：

- 对 RTSP 视频 packet 采样来源速率；
- 高倍模式下丢弃播放音频包；
- `NonKey` 快速路径；
- 实时流软背压替换为 GOP 追赶；
- recording 写包始终先于播放丢弃。

### 9.3 `DecodeWorker` / `VideoDecoder`

`DecodeWorker` 在自己线程中检测策略版本变化，再调用：

```cpp
void VideoDecoder::setDiscardLevel(DecodeDiscardLevel level);
```

`VideoDecoder` 负责把项目枚举映射为 FFmpeg 的 `AVDiscard`，所有
`AVCodecContext` 修改都留在视频 decode 线程，避免与 `sendPacket()/receiveFrame()` 并发。

### 9.4 `QueueManager`

增加按流生命周期接口：

```cpp
void abortAudio();
void startAudio();
void flushAudio();
void flushVideo();
```

用于高倍模式只关闭音频链路，以及 GOP 追赶只重置视频链路。

### 9.5 `AVSync`

需要支持：

- 高倍模式强制外部主时钟；
- 单调地重新锚定外部时钟；
- 实时流在 `sourceRate` 附近做有限速率修正；
- 普通模式音频恢复后平滑切回原主时钟。

### 9.6 UI 与打开参数

- 本地/点播倍速列表增加 `4x / 8x / 16x`。
- 4x 及以上显示静音状态，但不弹阻塞式确认框。
- 网络 URL 区增加来源速率选项，默认 Auto。
- 统计面板增加高倍数诊断字段。

## 十、配置与兼容性

### 10.1 `playbackSpeed`

扩展现有配置范围：

```ini
# 说明：本地文件和可点播媒体的默认播放速度倍率；4x 及以上自动关闭音频
# 取值：0.5 / 0.75 / 1.0 / 1.25 / 1.5 / 2.0 / 4.0 / 8.0 / 16.0
# 默认：1.0
playbackSpeed=1.0
```

`Config::load()` 的校验不能只改成 `0.5 <= value <= 16`，还要验证值属于允许档位，避免
异常配置写入 13.7x 等未测试倍率。

### 10.2 网络来源速率

首版采用会话级 `OpenOptions::sourceRateMode`，不写入 `fluxplayer.ini`：

- 普通用户保持 Auto，无需新增全局配置。
- 已知固定 4x 推流的调用方可显式指定 4x。
- 不污染下一个不同 URL 的播放行为。

### 10.3 公开接口兼容

现有 `open(path)`、`open(path, externalWindow)` 继续可用；新增 options 使用默认参数或新
重载，CLI 和现有 UI 调用无需立即修改。

## 十一、统计与日志

### 11.1 新增统计

```cpp
struct HighSpeedStats {
    double requestedRate;
    double detectedSourceRate;
    double effectiveRate;
    double liveLagWallSec;
    double decodeFPS;
    uint64_t presentationDropped;
    uint64_t decoderDiscarded;
    uint64_t packetDiscarded;
    uint64_t gopCatchups;
};
```

原有 `Dropped` 拆分展示，避免把正常的高倍采样误认为解码错误。

### 11.2 日志原则

- 每次模式切换打印一条 INFO，包含旧/新倍率、来源类型和音频策略。
- 自动来源速率只有档位稳定变化时打印 INFO。
- GOP 追赶打印开始/结束及追赶前延迟。
- 丢帧只进入计数器，每秒状态日志汇总，不逐帧写日志。
- PTS 无效、长时间无关键帧、reconnect 才打印限频 WARN。

状态日志示例：

```text
HighSpeed - Req: 8x | Source: 1x | Effective: 8x | Audio: off |
DecodeFPS: 142 | PresentDrop: 316 | DecodeDrop: 204 | Lag: 0.08s
```

## 十二、性能与资源目标

### 12.1 本地文件

- 在目标机器解码能力允许时，播放完成墙钟时间应接近：

```text
expectedWallDuration = mediaDuration / requestedRate
```

- 如果 16x 无法完整解码，允许自动降为关键帧预览，但进度和结束时间仍按 16x 推进。
- packet/frame 队列保持现有有界结构，不因倍率扩大容量。
- UI 输入、暂停和关闭事件在 100 ms 内得到处理。

### 12.2 RTSP

- 4x 输入稳定运行 30 分钟，内存不随时间线性增长。
- 稳态 `liveLagWall < 0.5s`；网络抖动恢复后 3 秒内回到 1 秒以内。
- demux 不因 soft backpressure 长时间停止读取 RTSP socket。
- 解码跟不上时允许画面稀疏，但不能持续播放越来越旧的画面。

## 十三、测试方案

### 13.1 单元测试

`HighSpeedController` 使用纯数值输入，便于增加不依赖 FFmpeg/GL 的单元测试：

1. 稳定 1x/4x/8x/16x PTS 到达序列能识别正确档位。
2. RTP 突发、200 ms 抖动不会把 1x 误判为 4x。
3. PTS 回绕、负跳变、reconnect 后检测窗口会重置。
4. 连续窗口和降档迟滞符合预期。
5. `liveLagWall` 会按 `sourceRate` 正确换算。
6. discard 升级立即生效，降级必须经过关键帧边界。

### 13.2 本地集成测试

测试组合：

| 维度 | 用例 |
|------|------|
| 倍率 | 2x -> 4x -> 8x -> 16x -> 1x |
| 编码 | H.264、H.265，含/不含 B 帧 |
| 解码 | 硬件开启、强制软件解码 |
| 分辨率 | 720p、1080p、4K |
| GOP | 1 秒、2 秒、5 秒 |
| 媒体 | 有音频、无音频、VFR、异常 PTS |

检查：

- 高倍模式无声音、无 audio underrun 刷屏；
- AClock 不再驱动画面，VClock/进度单调；
- 每个倍率的完成时间在目标值允许误差内；
- 16x 降级到关键帧时仍能正常 seek、暂停、恢复和关闭；
- 切回 1x 后音频从当前画面附近恢复，不播放旧位置音频。

### 13.3 RTSP 集成测试

可使用支持发布的本地 RTSP 服务，并让 FFmpeg 以 4 倍读取速率推送测试文件：

```powershell
ffmpeg -stream_loop -1 -readrate 4 -i sample.mp4 `
  -map 0:v:0 -map 0:a? -c copy -f rtsp -rtsp_transport tcp `
  rtsp://127.0.0.1:8554/fast4x
```

如果输入格式不适合直接转封装，改为 H.264 重编码并设置较短 GOP：

```powershell
ffmpeg -stream_loop -1 -readrate 4 -i sample.mp4 `
  -an -c:v libx264 -preset veryfast -g 60 `
  -f rtsp -rtsp_transport tcp rtsp://127.0.0.1:8554/fast4x
```

测试：

1. Auto 能在稳定窗口后识别约 4x。
2. 手动 4x 可跳过检测等待并立即进入高倍策略。
3. 注入网络抖动后队列延迟有界，并能触发/退出 GOP 追赶。
4. 长 GOP 时不会任意从 P 帧恢复导致持续花屏。
5. RTSP reconnect 后来源速率重新检测，时钟不倒退。
6. 开启录像时，播放可以丢帧/静音，但录制文件仍包含收到的原始音视频包。
7. 连续运行 30 分钟，内存、句柄和线程数量稳定。

## 十五、风险与降级

| 风险 | 处理 |
|------|------|
| 16x 解码吞吐不足 | 逐级提升 discard，最低降为关键帧预览 |
| 硬件后端忽略 `skip_frame` | 渲染批量消费兜底；实时流使用 GOP 追赶 |
| RTSP PTS 缺失或被重写 | Auto 保持 1x，并提供手动来源速率 |
| 网络突发导致来源速率误判 | 滑动窗口、EWMA、连续窗口确认和升降档迟滞 |
| 长 GOP 导致追赶等待过久 | 限频告警，超时后 reconnect 请求新解码起点 |
| 从 16x 降档后参考链不完整 | flush decoder，等待下一关键帧再降低 discard |
| 高倍切回 1x 播放旧音频 | 以当前画面 PTS 重建音频链路，旧队列全部 flush |
| 实时流暂停导致无限积压 | 暂停时持续读取并丢弃，恢复时追赶到关键帧 |
| 播放丢包影响录像完整性 | recording 写包必须位于播放丢弃判断之前 |

## 十六、完成标准

v0.9.0 只有同时满足以下条件才视为完成：

1. UI 和配置支持本地 4x/8x/16x。
2. 高倍模式不创建或持续运行无意义的音频播放链路。
3. 本地文件能按目标媒体时钟推进，解码不足时自动降载而不是卡住。
4. 4x RTSP 加速输入能够自动或手动识别，并在有界延迟、内存下持续播放。
5. GOP 追赶不会破坏解码参考链，录像路径不受播放丢弃影响。
6. 高倍与普通模式往返切换后时钟单调、音频位置正确。
7. 播放中暂停、seek、循环、关闭均可正常完成。
8. CMake 与 xmake 构建均通过，README、配置模板和相关技术文档同步完成。
9. 进入高倍数前会关闭 v0.8.0 本地 GPU 升分辨率并恢复 Original；高倍模式中不显示
   本地分辨率选项。
