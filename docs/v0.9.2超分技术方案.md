## 1. 目标与边界

用户从首页进入独立的 **VIDEO SUPER RESOLUTION** 工具，选择一个本地视频、增强模型及最终输出尺寸，后台逐帧增强并保存完整视频。入口与 Merge Videos 同级，保存目录共用 `Config::recordDir`。

### 1.1 必须保持的约束

- 只做独立本地离线导出，不恢复实时播放 SR 开关、暂停增强、FrameQueue 旁路或增强录像链路。
- 不调用线上超分 API、不上传帧、不在播放时自动下载模型。
- 每个正常解码的选定视频帧均输出增强画面，保留源时间顺序；不跳帧、近似复制上一帧、混入原画或改帧率制造成功。连续帧转换后的 RGB 逐字节相同时允许复用确定性模型结果，仍分别编码每帧及其 PTS。
- 单个本地普通文件输入，不支持 URL、直播、DASH、纯音频、多文件批处理、剪辑及断点恢复。
- 模型输出不保证真实细节或无损修复；更大分辨率不等于更好画质。
- 不改写 Player、AVSync、DecodeWorker、FrameQueue 或原包录像行为，不把工具嵌入播放循环。
- 共用增强算法面向 macOS 与 Windows GPU 设备，不把 CoreML 专用路径等同于完整功能。当前真实运行验收主要在 Mac，Windows CUDA 运行库、部署和 GPU 性能仍需独立交付；本轮不自行下载大依赖或引入 Git LFS。
- 超分运行时和设计稿可见文案使用英文；中文代码注释、用户文件名和路径保留原样。

### 1.2 模型倍率与最终画布独立

模型原生倍率决定中间图像尺寸，最终尺寸由独立缩放阶段决定：

```text
源图像 → 原生2x/4x模型增强 → 等比缩放及补边 → H.264编码
```

默认原生 2x、保持原分辨率。最终尺寸可选保持源尺寸、模型原生尺寸、720p、1080p、4K、自定义宽高。4x 增强后缩小不能称为“原生2x模型”；超出模型原生尺寸的普通插值不能称为额外 AI 重建。

不未经确认先缩小输入以节省推理成本。仅降低最终输出尺寸通常不会减少当前推理分块数。超出原生尺寸的 UI 警告目前按画布宽高比较，结合 SAR/黑边判断实际内容是否放大仍待完善。

### 2.1 流水线和线程所有权

```text
SuperResolutionScreen / CLI
    ↓ 复制任务配置
VideoSuperResolutionExporter Worker
    ├─ 独立FFmpeg解复用与软件解码
    ├─ 源属性验证 → RGB
    ├─ RealESRGAN逐块推理
    ├─ 目标画布缩放/补边 → 编码像素格式
    ├─ libx264视频编码
    ├─ 默认保留原音轨；仅显式选择时转AAC
    └─ 同一个MP4/MKV muxer → 独占临时文件 → 不覆盖提交
```

采用顺序流水，慢推理形成背压而不是丢帧。解码器、转换器、模型会话、编码器和封装器由单 Worker 持有；任务开始时复制输入路径、输出目录、模型和尺寸，不让 Worker 持续读取可变 Config。

OpenGL 只负责 UI/预览，不通过屏幕读回获取导出帧。输出不包含 UI、字幕叠加、播放亮度或音量效果。

## 4. 输入支持范围

### 4.1 视频与色彩

当前接受经验证的 8-bit、逐行、软件 YUV SDR；矩阵、primaries、transfer 和 range 必须组成支持的显式标签组合，不按分辨率猜测。

| 类别 | 当前处理 |
| --- | --- |
| BT.709 | matrix/primaries/transfer均BT.709，range明确 |
| NTSC BT.601 | matrix及primaries为SMPTE170M，transfer为SMPTE170M或BT.709 |
| PAL BT.601 | primaries为BT470BG，matrix为BT470BG或SMPTE170M，transfer为BT.709或GAMMA28 |
| full/limited range | 实际进行输入范围转换，输出limited，保留支持的色彩标签 |
| 动态尺寸/格式/色彩变化 | 逐帧检查，变化则失败，不静默转换为另一契约 |
| HDR/WCG、高位深、交错、RGB/PAL输入、损坏帧、裁剪 | 明确拒绝 |
| 色彩或时间戳缺失 | 明确拒绝，不猜测为普通SDR/固定帧率 |

容器可打开不等于内容可导出。仅处理选定主视频及默认音轨，不承诺多视频、多音轨、软字幕、章节、附件完整复制；无音轨时不创建人工静音轨。

### 4.2 SAR、方向与画布

- 保持源尺寸/模型原生尺寸：保留源 SAR。
- 预设/自定义画布：输出 SAR=1，根据源显示比例等比缩放和补黑边，不拉伸。
- 支持受限的 0°/90°/180°/270° 单位显示矩阵，原样写入输出，不再次旋转像素；编码尺寸按旋转前表示。
- 镜像、透视、平移、复杂或逐帧显示矩阵仍拒绝。
- 宽高、像素数、中间尺寸有安全上限；编码宽高要求偶数。图像缓冲估算上限512 MiB，不等于整个进程/ORT内存峰值保证。

## 5. 模型、运行库与推理

### 5.1 固定模型契约

| 资源 | 输入 | 原生输出 |
| --- | --- | --- |
| `source/models/realesrgan/realesrgan-x2plus.onnx` | FP32 RGB NCHW，1×3×256×256 | 1×3×512×512 |
| `source/models/realesrgan/realesrgan-x4plus.onnx` | FP32 RGB NCHW，1×3×256×256 | 1×3×1024×1024 |

模型通过 `Config::getResourcePath` 查找，校验SHA-256、输入输出数量、dtype及固定shape，不仅检查文件存在。来源、散列和许可见模型目录README及LICENSE；不得通过同名替换规避契约。

固定 tile=256、halo=32、有效核心192，边缘采用 Reflect-101。每块规范化为RGB FP32，去halo后拼接有效区域，检查非有限值并clamp/量化。不缩小halo、不跳边缘块、不用普通插值代替推理。

每帧块数为 `ceil(width/192) × ceil(height/192)`；边缘块仍执行完整256输入。模型中间图为有效源尺寸乘原生倍率，padding不计入输出。

### 5.2 实际执行设备

当前优先支持 Mac arm64、ORT 1.23.2，按受控路径动态加载，不强链接到基础播放器。macOS Auto默认尝试快速CoreML，参数为 `NeuralNetwork / ALL / RequireStaticInputShapes=1 / AllowLowPrecisionAccumulationOnGPU=0`，用于原生2x/4x模型。NeuralNetwork允许设备相关的FP16中间精度，FP32输入输出及关闭低精度累加不代表全程FP32，也不保证与旧输出逐像素一致。ORT intra-op threads为硬件并发数与4的较小值，至少1。

快速CoreML初始化失败时，在写输出前重试标准 `MLProgram`，仍失败才尝试CPU；强制CPU模式不进入CoreML。运行中失败仍终止任务，不中途更换精度或混入原画。诊断环境变量 `FLUX_SR_COREML_MODEL_FORMAT=MLProgram` 可恢复标准FP32路径，允许值仅为 `MLProgram` / `NeuralNetwork`，无效值明确报错；不新增用户设置项或修改INI。Windows现有DirectML分支不受本次切换影响。

CoreML 编译缓存放在应用数据目录的 `sr-coreml/`，按真实 ORT 版本、校验后的模型 SHA-256、ModelFormat、计算单元及固定shape/累加配置隔离，快速与标准路径不能共用缓存。缓存目录不可用时记录警告并无缓存继续；首次使用快速路径需要单独编译。此缓存不缓存视频、图像或推理结果，不自行改变执行精度。状态/日志标明 `NeuralNetwork fast`、`MLProgram FP32` 或CPU，快速路径另记录中间精度警告，不宣称全部运行于GPU/ANE。

CoreML EP成功不代表整图在GPU/ANE；节点分配警告也不能证明整图退回CPU。`ALL`和FP32输入输出不保证内部设备或精度。Windows CUDA、Intel Mac/Linux运行库及安装包未完成验收；不自行下载大依赖。

固定 Mac arm64 ORT dylib 通过精确 `.gitignore` 白名单随仓库分发，散列及许可见 `source/onnxruntime/README.md`；不依赖开发机未提交的忽略文件。CMake install 和 xmake 资源部署包含模型与 ORT；macOS 打包脚本复制到 `Contents/Resources`，检查 ORT 散列及依赖闭包。这不代表 Windows 运行库或干净机器包已验收。

### 5.3 已接入的局部优化

- 每任务复用模型Session和两路SwsContext，不逐帧重建色彩转换器。
- 输入/输出 FP32 tile 缓冲及 OrtValue 跨块、跨帧复用；尺寸不变时缓存 Reflect-101 横纵索引。归一化使用与原除法一致的256项查表。
- 源 RGB、增强 RGB 缓冲复用；额外保存前一 RGB，仅逐字节相同才复用其增强结果。当前 PTS、帧时长及编码均不复用，安全预算包含新增缓冲和 tile 输入/输出。
- 整帧变化时进一步检查各块：比较 Reflect-101 后完整256×256 RGB输入（含32像素halo），全部相同才保留上一帧该块的增强输出，不调用ORT。不能仅比较192×192核心、使用相似度阈值或跳过halo。首帧必须全部推理，任务间不共享结果；源尺寸/格式/色彩变化仍按原协议拒绝。
- 分块复用不额外缓存多帧或多套模型，复用已预算的前帧RGB和原地增强输出。该逻辑为平台无关C++，不使用CoreML/CUDA/OpenGL平台接口，未来Windows EP接入后沿用同一前后处理；仍需在对应设备验证输出与吞吐。
- 保持模型、分块顺序、归一化、clamp和舍入语义不变。
- 未引入多Session/多tile并发、输出零拷贝或新的硬件解码路径。

## 6. 编码、音轨与时间线

### 6.1 当前编码策略

输出 MP4 或 MKV / H.264，使用 **libx264、CRF18、medium、zerolatency**，限制编码线程、关闭B帧并限制重排缓冲。视频必须重新编码，不能以源视频流复制冒充增强。未降低 CRF 质量、模型精度、输入分辨率或 tile halo 来提速。

项目FFmpeg的VideoToolbox路径曾在VFR素材上生成不合法DTS，因此当前不启用VideoToolbox/NVENC作为超分编码器。不能通过改源PTS掩盖问题，也不在写文件后静默切换编码器。更多编码器属于后续独立验证项。

### 6.2 公共原点与视频时序

源媒体时间决定输出时间，不使用墙钟或处理耗时生成PTS。以容器start_time建立原点，再结合已探测首视频帧及相关音频包调整，避免容器起点晚于实际首帧导致MP4裁掉首帧。

视频保留相邻PTS间隔，以后帧确定前帧时长；尾帧要求可信duration。缺失/异常时间戳、未完全解码或编码器没有输出全部已接受帧均失败。VFR不能被强制改成CFR来通过验收。

### 6.3 原音轨保留与显式AAC转换

默认复制所选原音轨的编码参数及音频包，不解码、不做样本级修复、不静默转 AAC。MP4 不支持原编码时改用 MKV；MP4 头预检因具体封装参数返回 EINVAL 时也预检 MKV（例如8kHz MP3）。不能只凭编码 ID 推断参数兼容，更不能把读包错误当成换容器的理由。

延迟开始 AAC 使用 MKV 保留原包，避免旧 MP4 muxer 的 priming/edit-list 限制。若需 MKV 且素材带显示矩阵，当前明确拒绝并提示显式选择 AAC/MP4，因为 MKV 显示矩阵保留未验收；不静默丢弃方向信息。两个容器均不能承载或原时间戳不合法时，在加载模型前失败，不自动有损转码。

只有用户显式选择 AAC 时走解码→swresample→有界 FIFO→AAC。保留支持的采样率/声道，不静默降混；当前不新增采样率改变功能。以下时间线修复规则仅适用于该显式转换分支。

项目旧版FFmpeg对延迟开始AAC的priming裁剪不可靠，转码音轨显式补前导静音，使实际声音起点不变，UI提示可能增加前导静音。这改变空白区的表达方式，不是无损原包复制。

AAC码率上限按采样率和声道约束，避免8kHz每声道固定96kbps触发编码器clamping。首包标记initial padding，末包限制有效时长；正常结束排空解码器、转换器、FIFO和编码器，并核对采样计数。

### 6.4 有界时间戳修复

解码帧的 `best_effort_timestamp` 从源时间基换算到 `1/sample_rate`，减去公共原点的采样位置。与 `first + received` 比较；received仅累计已保留样本及静音，不把每帧舍入误差累加成新的全局偏移。

| 情况 | 当前策略 |
| --- | --- |
| 一个tick以内的偏差 | 允许时间基量化误差；每帧仍对照绝对PTS |
| 正向缺口 | 分块补等长静音；单次最多60秒 |
| 延迟音轨开头 | 补前导静音，上限1小时 |
| 不超过100ms的重叠 | 保留已有区间，裁掉新帧重复前缀；完全重复帧不增加游标 |
| 超过100ms的重叠/回退 | 明确失败，输出原始PTS、预期/实际采样位置、偏差、采样率及容差 |
| 时间基粗于当前2ms限制、时间戳缺失 | 明确拒绝 |

间断处先排空swresample再重置滤波状态，不把前一段延迟样本放到静音之后。裁重叠会丢弃重复时间区间的新样本，是有损的时间线修复策略，不宣称无损保留全部样本；完整UI说明及实际原片听感仍待验收。

用户日志中的 `+440 samples` 为8kHz下55ms缺口，`-136 samples` 为17ms重叠。负偏差仅证明当前帧起点早于累计游标，不能仅凭它断定PTS小于上一帧PTS或一定是舍入误差。此前旧策略在约27秒媒体位置退出；现在小重叠处理已接入，但原始失败素材未提供，不能宣称原片问题已完全验收。

## 7. 安全提交、取消与错误

- 输出目录共用 `Config::recordDir`；支持中文和空格路径，不能输出到模型资源目录或覆盖输入/既有文件。
- 使用唯一文件名、同目录独占临时文件，显式选择 MP4/MKV muxer 及对应扩展名。最终文件只有成功后才对UI发布。
- 成功顺序：解码/转换/编码drain → trailer → flush及错误检查 → fsync/close → 最终取消检查 → 平台不覆盖提交 → done。
- macOS 使用 `renamex_np(RENAME_EXCL)`，Windows 使用不带覆盖标记的 `MoveFileExW`；这两端不要求输出目录支持硬链接。未适配平台仍可使用不覆盖硬链接，但不将普通可覆盖 rename 作为回退。此协议不等于断电恢复保证。
- 处理阶段失败或正常取消时，释放资源后清理本任务不完整文件；完整视频已收尾而最终提交失败时，保留 `.part.mp4` 或 `.part.mkv` 并报告恢复路径，不再删除成果，也不报告成功。清理失败保留具体路径与诊断。
- 取消标记覆盖读包及处理循环，ORT单次Run通常需返回后才能响应，不承诺立即停止。
- 最终提交和取消通过终态锁协调；状态锁不跨推理、磁盘I/O和join。
- 异常退出时AAC的 `frames left in the queue` 可由未正常drain产生，先定位上层触发错误，不能当作首要原因。

模型加载和输出创建前，独立读句柄完整扫描音轨，并使用实际封装器写入可 seek 的丢弃 sink。默认复制只检查包与封装，不额外打开视频解码器；显式 AAC 会完整验证转换与 drain，因此该模式预检仍有一次转码成本。不能把音轨预检通过视为全片视频均可处理承诺。

## 8. 性能诊断与实际证据

### 8.1 日志含义

| 指标 | 范围 |
| --- | --- |
| load ms | 模型哈希、运行库加载、Session创建与形状校验 |
| RGB ms/frame | 输入缓冲及YUV→RGB，含首次转换器初始化 |
| model+tiles ms/frame | 整个enhance，不是纯设备内核时间 |
| output scale ms/frame | 输出帧、补边、最终缩放及RGB→YUV |
| prepare / ORT Run / stitch | enhance内部进一步拆分；首帧单列，每30帧报告排除首帧的后续均值 |
| exact-input reuse / exact-tile reuse | 整帧/分块精确复用累计次数；后者不包含整帧复用已经省掉的块 |

ORT Run包含执行提供者内部调度和数据传输，不能等同GPU/ANE内核耗时。上述图像阶段不含读包/解码、音频、H.264编码、封装和最终提交；百分比必须说明统计分母。短片数据不等于长片稳态或热降频验收。

### 8.2 已有性能结果

- 用户素材第120帧累计平均：RGB约0.54ms、model+tiles约3048.89ms、output scale约12.37ms。主要耗时在enhance整体，约0.327帧/秒；当时未拆出该素材的Run时间。
- 256×194、三帧、多tile VFR诊断素材：缓冲/索引优化前后model+tiles约990→1013ms/帧，未证明整体提速；四tile首帧prepare约0.409→0.283ms，Run约1.1秒。
- 64×48、30帧、2x短片：单tile首帧Run365.56ms；后29帧平均Run232.46ms、prepare0.060ms、stitch0.048ms。
- 结论：已验证的外围优化保持画面，但不足以把几十分钟缩到几分钟。下一步优先对相同素材/模型做CoreML执行路径与profile对照，不盲目改编码器、缩halo或增加并发。

### 8.2.1 分块精确复用与执行分配（2026-10-18）

- 400×32、三帧局部变化、原生2x、CPU：原实现9次tile推理，精确复用后5次；图像推理/分块均值6476.34→3719.36ms/帧，短样本减少约43%。视频解码后的YUV420P逐字节相同。该素材专门包含静态区域，不代表全画面运动视频也能获得同样收益。
- 同一构建以 `FLUX_SR_DISABLE_TILE_REUSE=1` 禁用块复用进行对照；该诊断开关不禁用既有整帧相同复用，不修改模型/精度，也不是用户画质选项。
- 两帧halo边界变化素材：第二块只有halo变化，仍必须重新推理，只有第三块可复用。CPU 2x/4x和CoreML 2x对照均保持输出像素、PTS及duration一致，推理调用6→5；CPU 2x图像阶段均值6632.33→5502.89ms/帧，CPU 4x为27949.50→21948.23ms/帧，CoreML 2x为838.90→675.24ms/帧。均为短样本，非稳态硬件基准。
- CoreML 2x对照profile中，启用复用后CoreML子图累计约1345.65ms，CPU节点累计约2.10ms；CPU节点为Reshape/Transpose。只说明ORT可见节点耗时主要在CoreML子图，不揭示CoreML内部CPU/GPU/ANE占比，也不证明设备饱和。未单独分离硬件内核与数据搬运时间。
- 未改变UI，因此本轮无需改变SVG布局。实际收益取决于含halo的块是否逐字节相同；压缩噪声、镜头运动及动态背景会降低命中率。不通过缩halo、降低输入尺寸、改精度或降低编码质量扩大收益。
- 本轮macOS CMake/xmake构建通过，使用项目FFmpeg7.x头文件对模型适配器和导出器的语法检查通过；不等于Windows编译、CUDA执行或发布包验收。

### 8.3 硬件解码基准不能当作超分性能

`HardwareInfo.cpp` 固定优先选择 `video/video_01.mp4`，其次 `Subtitles/test_Subtitles.mp4`，通过Demuxer/VideoDecoder测解码，不执行RealESRGAN。

日志中的720×1280、30fps、AAC 44.1kHz双声道属于该测速样本。用户实际超分日志为μ-law PCM、8kHz单声道；实际输入来自GUI选择路径或CLI参数，并未在所贴日志里给出。不能将基准分辨率、播放倍率或VideoToolbox启用状态用于推断该导出任务的输入或推理性能。

### 8.4 Windows GPU 执行与 Mac 路径对照（2026-10-21）

本节为新测量，不以旧版 Mac 状态描述当前 Windows 行为。用户新提供的文件实际为 464×848、30fps，不是此前截图中的 1080p；固定 256 输入、32 halo 的每帧分块数为 15。以下基准使用相同尺寸、原生 2x 模型、每帧变化的合成纹理，不是完整用户视频导出。

| 项目 | 测量结果 | 能说明什么 |
| --- | --- | --- |
| 首帧短基准 | prepare 4.02ms、同步 Run 578.97ms、stitch 2.77ms，总计约 585.85ms / 1.71fps | 主要耗时位于同步 Run，不能再把 CPU 拼接当作主要瓶颈；该次启用 profile，仅用于定位 |
| ORT 节点分配 | 15 个可见计算事件均为 DML 融合节点，无可见 CPU 计算节点 | 该样本没有观察到模型算子回退 CPU；不代表 DirectML 内部耗时已细分 |
| GPU 运行中采样 | 利用率 98%、功耗约 146W | 独显确实在工作；这是单次采样，不能当全片均值，也不能证明当前内核已最优 |
| 同步自旋初步对照 | 预热 1 帧、统计后 5 帧：关闭约 575.88/575.65ms，开启约 561.50/559.61ms | 最初看似有 2.6%–2.9% 收益，需要交错对照消除时钟及其他波动 |

保留 `FLUX_SR_DML_CPU_SYNC_SPIN=1` 作为开发诊断选项，默认关闭；它只改变 CPU 忙等策略，不改变模型算术和精度，也不影响 Mac/CPU 推理。所有 6 帧变化输入的 2x RGB24 对照、4x 小尺寸的 6 帧 RGB24 对照均逐字节一致。固定 ORT 版本的选项定义见 [DML 1.23.0 配置](https://github.com/microsoft/onnxruntime/blob/v1.23.0/onnxruntime/core/providers/dml/dml_session_options_config_keys.h)。

另一个图捕获试验没有通过：仅设置 `ep.dml.enable_graph_capture=1` 后，虽然表观速度超过 60fps，但连续 6 个不同输入的输出 hash 全部相同，且与参考输出不符。生产未启用该选项；必须先设计正确的固定设备缓冲、输入更新、输出读回、I/O Binding 与同步，再重新验证，不能单靠开关宣称提速。

当前 Mac 代码默认已变成 `NeuralNetwork fast`，并在日志中警告可能使用 FP16 中间值；原 MLProgram 是保守参考路径。Mac 的 1.6fps 必须结合当时的实际格式与计算单元日志，不能直接当作与 Windows FP32 等精度的比较。本轮没有修改 Mac 的默认路径，且不以降低 Windows 精度换速度。

可迁移的是静态形状、会话/缓冲复用、图优化与编译缓存思路；CoreML 格式、ANE 与统一内存机制不能直接移植到 Windows。Windows 当前已经有固定 shape、Session 复用、tensor 复用和 DML 图融合，重复加这些机制没有新收益。

后续按以下顺序开展，均须保持权重、tile/halo、输入分辨率、逐帧处理及现有色彩/编码策略，并验证输出：

1. **NVIDIA 原生执行效率对照**：若后续获准部署依赖，用相同 FP32 模型比较 CUDA/cuDNN 与 DirectML，CUDA 显式设置 `use_tf32=0`。当前没有安装或实测该后端，不承诺更快；也没有再次执行此前未获批准的大依赖下载。Mac 继续走自身 CoreML 路径。
2. **固定设备缓冲与正确图捕获**：先隔离输入更新、模型执行、输出回读耗时，落实设备 tensor / I/O Binding，验证不同帧、不同 tile、缓存复用、取消后重启和 2x/4x。设备端裁 halo 与拼接可以减少读回量，但收益须与实际 GPU 计算占比一起衡量。
3. **共用有界流水线**：解码/下载、增强、编码分别拥有独立上下文，以有界队列重叠执行。禁止播放器式丢帧；音频不全片缓存，muxer 单线程持有，取消时唤醒队列并安全收尾。该方向减少外围串行时间，不能消除模型的 GPU 计算。

每轮至少报告预热与稳态耗时、重复交错测量、原始输出一致性及峰值资源。现阶段证据支持“GPU 已在承担重负载，主要成本在模型 Run”，不支持“显卡未用上”或“某个同步开关能使速度翻倍”。

### 8.5 已实现：单帧有界编码重叠（2026-10-21）

在现有 FFmpeg/ORT 依赖内，将上一帧的 libx264 编码及视频包复用与下一帧的增强重叠执行，默认开启。没有更换模型、推理精度、分块、缩放算法或编码参数；无需 CUDA、ncnn 或 Vulkan。新增 `SRSerialWorker` 使用标准 C++17，供 Windows/macOS 共用。

```text
原路径：编码 N → 增强 N+1 → 编码 N+1 → 增强 N+2
新路径：编码 N ─────┐   编码 N+1 ─────┐
        增强 N+1 ──┴→ 增强 N+2 ──────┴→ …
```

- 单个持久编码线程，最多一帧在途；提交下一帧前应用背压，AVFrame 只增加引用，不全片缓存。
- 主增强线程读取独立的不可变输出格式快照，不并发访问编码器上下文。音频复制/转码与任何主线程 mux 操作先等待视频写入完成，避免并发访问同一个 muxer。
- 输出帧仍使用下一帧 PTS 确定 duration，末帧保持可靠源 duration；帧数在编码成功后更新。取消或异常时先 join 写线程，再关闭上下文和删除临时文件；编码失败会回传到导出线程。
- `FLUX_SR_SERIAL_ENCODE=1` 可切回串行参考路径；创建线程失败时自动使用串行路径。新增 `encode/mux ms/frame` 日志，该值与推理计时存在重叠，不能简单相加作为总墙钟耗时。

Windows RTX 5060 Ti 上，同一构建与原生 2x 模型对照，记录 processing 阶段到收尾完成的墙钟时间；模型加载/音频预检不在该列中：

| 样本 | 串行 | 编码重叠 | 解释 |
| --- | ---: | ---: | --- |
| 用户素材前 30 帧，464×848 → 1280×720，复制 48 个 AAC 包 | 17.640s | 17.482s | 该短片约快 0.9%，模型推理占主导，不代表整片结果 |
| 同素材 30 帧视频轨，两组交错均值 | 17.903s | 17.460s | 观察到约 2.5% 吞吐差异，含 GPU 时钟等波动，不全部归因于调度改动 |
| 编码负载较重的合成样本，12 帧、512×288 → 原生 1024×576 → 最终 1920×1080，两组交错均值 | 3.627s | 2.867s | 处理时间减少约 21%，吞吐提高约 26%；此样本不是用户素材，输出大于模型原生尺寸，不能作为普遍提速承诺 |

上述各组串行/重叠的完整输出文件 SHA-256 一致。用户音视频短片两条路径均重新解码为 30 帧视频、48 个 AAC 包；另验证 2x/4x、显式 AAC 转码、原音轨复制、软件解码回退和取消清理。Windows xmake 构建通过；macOS 随仓库 FFmpeg 4.4 头文件接口检查通过，尚无这次改造的 Mac 真机性能与完整运行验收。

并发回归曾覆盖顺序、单槽背压、异常传递、在途任务析构等待和空任务拒绝。当前仓库已无对应测试源码，这些属于历史验证记录，不作为仓库可复跑入口；遵守用户要求，不新增测试代码。

本轮未采用的实验：

- 正确固定 GPU tensor、D3D12 显式上传/下载和 I/O Binding 的原型，对 6 个变化输入逐帧验证了完整 RGB 一致；但相同合成尺寸下设备 I/O 约 585ms/帧、设备 I/O 加图捕获约 615ms/帧，没有胜过原路径，因此没有加入生产实现。它与 8.4 节直接给 CPU tensor 打开捕获后产生重复输出的无效实验不同。
- 用户素材前 30 帧共 450 个 tile，现有相邻帧精确复用与额外 32 项全 tile LRU 预测均未发现命中，因此没有为该素材增加大内存缓存。

当前可交付收益主要是隐藏编码等待。该素材上模型 GPU 执行仍占绝大多数；保持现有模型与精度、且不引入其他推理后端时，不应把本轮描述为数倍加速。

### 8.6 约 3 fps 后的继续排查（2026-10-21）

本轮复用已有本地诊断入口，重新链接当前生产 `RealESRGAN.cpp` 与像素转换实现，没有新增或修改测试源码。使用 RTX 5060 Ti、DirectML FP32、2x、600×336 的六个变化 RGB 输入，首帧预热后统计后五帧；这是模型路径测量，不是用户整片导出测量。

| 对照 | 两组交错测量的平均耗时 | 模型路径吞吐 |
| --- | ---: | ---: |
| 当前实现 | 306.269 ms/帧 | 3.265 fps |
| 候选：提前逐行比较完整 halo 输入、未变化块不再准备浮点输入 | 306.371 ms/帧 | 3.264 fps |

两者差异约 0.03%，没有稳定收益，候选改动已撤回。没有以增加代码量代替性能收益，也没有改变模型、精度、halo、帧数或编码设置。

另一次当前路径复测为 305.158 ms/帧。首帧细分为准备 2.096 ms、ORT Run 306.332 ms、拼接 1.048 ms；模型调用内部约 99% 时间位于 ORT Run。同期 GPU 采样在推理阶段达到 95%～97% 利用率、约 144 W，确认 GPU 正在承担计算；利用率本身不能证明具体算子的硬件效率，也不能单独分解卷积和传输成本。

600×336 每帧需要 8 个 tile，原生 2x 得到 1200×672，再缩放到用户选择的画布。此前 464×848 的素材需要 15 个 tile，不能把两个输入的 fps 差异全部归因于代码优化。保持其他条件相同，减少最终输出画布不会减少已有 8 次模型推理。

后续优先方向是降低 GPU 上同一 FP32 模型的实际执行时间，而不是继续堆叠解码线程：

- 先分析同一模型的 GPU 算子执行、融合和调度；ORT 的 CPU 提交时间不等于 GPU 内核时间。仅有当前证据，无法承诺某项内核改动可提高多少。
- 同精度其他后端只有在用户接受相应依赖后再开展对照，并使用同一素材、模型、尺寸和输出质量验收；本轮没有下载 CUDA/cuDNN 或引入新运行库。
- 不默认采用此前未胜出的 batch、设备 I/O、图捕获或 CPU 自旋方案。对大量静态区域，已有逐字节精确复用仍有价值，但不能指望其普遍加速动态视频。

以约 306 ms/帧为参照，达到 5 fps 需把每帧处理降至 200 ms，达到 10 fps 需降至 100 ms。消除几毫秒 CPU 工作无法填补这一差距。Windows 当前结论来自本机测量；macOS 仍需在相同输入和精度设置下独立测量，不能直接套用上述 fps。

## 10. 剩余工作与验收标准

优先顺序：

1. **原素材音频验收**：获取失败素材，核对原包保留、声音时刻及实际播放器兼容性；显式 AAC 分支另验收相邻PTS/nb_samples和裁重叠听感。完整音轨预检已接入，更多异常封装和长片仍需覆盖。
2. **性能实测**：同素材、同模型、同画布记录加载/首次Run/后续Run，确认CoreML分区和拷贝开销；可选优化必须有输出一致性、内存及吞吐对比，不承诺未经测量的提速。
3. **GUI完整验收**：退出旧进程后验证选择/拖放、英文布局、首页悬停、真实进度/时间格式、取消/失败、打开目录/播放结果/重新处理。
4. **长片与画质**：检查细节真实性、过锐/伪纹理、闪烁、tile拼缝、长时间稳定性和内存峰值。完成短片不等于通过该项。
5. **安全与发布**：磁盘满、无权限、并发同名冲突、无硬链接文件系统上的不覆盖提交、提交失败保留完整文件、资源缺失、干净机器包及基础播放器启动回归；核实ORT来源、架构、依赖和许可部署。

Windows CUDA/大依赖与Git LFS不在当前恢复范围。不得为优化恢复实时播放超分，或未经验证切回VideoToolbox VFR编码。
