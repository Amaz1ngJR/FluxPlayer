### 核心类关系图

Player 是**门面（Facade）**，持有职责单一的组件；控制流通过**命令队列**收口到控制线程，
数据流仍是三线程解耦（demux 读包分发 → PacketQueue → video/audio 独立解码 → FrameQueue → 渲染/播放）。

```
   UI 线程                          控制线程（主循环 run()）
  ┌──────────┐  post 命令(非阻塞)  ┌──────────────────────────────┐
  │Controller│ ───────────────────▶│ CommandQueue → pumpCommands()│ ← 每帧 UI 前串行执行命令
  │ .seek()  │   SeekCommand 等     │  (Seek/Pause/Resume/Stop/... │
  └──────────┘                      └───────────────┬──────────────┘
                                                    │ 委托各组件
                         ┌──────────────────────────┼────────────────────────────┐
                    ┌────▼─────┐  ┌──────────────┐  ┌▼─────────────┐  ┌──────────▼──┐
                    │StateMgr  │  │ClockController│  │QueueManager  │  │RecordingSvc │
                    │(状态机)  │  │(AVSync+seek) │  │(4 队列生命周期)│  │(录制,无锁)  │
                    └──────────┘  └──────────────┘  └──────────────┘  └─────────────┘

   数据流（三线程解耦，由 Worker 组件承载）：
┌───────────┐ DemuxWorker 读包分发（seek 协议/DASH 重启/背压/录制写入）
│  Demuxer  │──────────────────────────────────────┐ （字幕在此同步解码）
└───────────┘                                       ▼
        ┌──────────────┐  ┌──────────────┐  ← QueueManager 持有的 PacketQueue（serial+背压）
        │videoPktQueue │  │audioPktQueue │
        └──┬───────────┘  └──┬───────────┘
   DecodeWorker(Video)│   DecodeWorker(Audio)  ← 对称解码线程（PTSNormalizer 共享，mutex 保护）
           ▼                 ▼
        ┌──────────┐      ┌──────────┐  ← QueueManager 持有的 FrameQueue（环形，keep-last）
        │VideoQueue│      │AudioQueue│
        └──┬───────┘      └──┬───────┘
   主线程 run()/RenderPipeline│ 平台音频线程 audioOutputCallback
           ▼                 ▼
        ┌──────────┐      ┌──────────┐
        │GLRenderer│      │AudioOutput
        └──────────┘      └──────────┘
```

要点：
- **命令队列收口控制流**：UI 线程不再直接改播放管线状态，只投递命令；控制线程在每帧
  `pumpCommands()`（UI 渲染前）串行执行，消除「UI 线程伸手进播放管线」的并发脆弱性。
  只读 query（getCurrentTime/isRecording 等）仍走原子量直读，不入队列。
- **GLFW context 亲和**：控制线程 = 主线程 = 渲染线程，命令执行与取帧渲染同线程串行，
  天然不会并发踩 GL 状态。
- **三线程解耦不变**：视频帧队列满只阻塞 video 解码线程，audio 解码线程从独立的
  `audioPktQueue` 持续产帧、音频时钟照常推进——消除「视频队列满 → 音频饿死 → 主时钟冻结」死锁。
- **录制无锁**：RecordingService 的录制器创建/销毁/writePacket 全归 demux 线程串行，
  query 走原子状态块，彻底去除录制锁。

详见 `docs/多线程解耦重构方案.md`、`docs/v0.6.0命令队列与控制线程架构重构方案.md`。

### 第四步：解码线程工作流程（demux + video/audio 三线程解耦）

**代码位置**：`DemuxWorker::run()` / `DecodeWorker::runVideo()` / `DecodeWorker::runAudio()`

历史上读包与音视频解码在**同一线程串行**完成。该模型存在结构性死锁：mov/mp4
视频包密集前置时，容量仅 4 的视频帧队列在读到首个音频包前被灌满，解码线程阻塞在
`videoQueue_->peekWritable()`，再也读不到音频包 → 音频队列饿死 → 音频主时钟冻结 →
渲染线程不取帧 → 视频队列永不腾空，画面卡死。

现采用 **ffplay 式多线程解耦**，彻底消除该死锁：

```
demuxThread        → av_read_frame → 按流分发到 videoPktQueue_ / audioPktQueue_
                     （PacketQueue），字幕同步解码，seek/DASH/直播重连也在此线程
videoDecodeThread  → videoPktQueue_.get() → 解码 → 归一化 → videoQueue_（帧）
audioDecodeThread  → audioPktQueue_.get() → 解码 → 归一化 → audioQueue_（帧）
主线程 run()        → 消费 videoQueue_ 渲染
平台音频线程        → audioOutputCallback 消费 audioQueue_
```

视频帧队列满只阻塞 video 解码线程；audio 解码线程从独立的 `audioPktQueue_` 取包持续
产帧，音频时钟照常推进，渲染照常消费，视频队列腾空，video 解码线程解阻塞。**结构性
死锁消除。**

**PacketQueue（压缩包队列，对标 ffplay PacketQueue）**：
- 链表实现，`put()` 非阻塞追加、`get(block)` 阻塞取包
- **serial 序号**：`flush()`（seek/重连）时自增。解码线程发现 `get()` 返回的 serial
  变化，即知道发生过 seek/flush，自行 flush 自己的解码器与帧队列（与生产者同线程，
  无竞态）——跨线程 seek 无需 demux 线程触碰解码器
- **背压**：字节软上限 15MB（对齐 ffplay）/ 硬上限 64MB / 单路 48MB / 各流时长门槛，
  防止坏文件或差交织导致单路无限缓冲 OOM

**线程访问模型（线程安全约束）**：

| 资源 | 写入/控制线程 |
|------|--------------|
| `demuxer_` / `dashMerger_` | demux 线程（seek/reopen/DASH 重启只在此线程） |
| `videoDecoder_` + `videoQueue_` | video 解码线程独占 send/receive/flush |
| `audioDecoder_` + `audioQueue_` | audio 解码线程独占 send/receive/flush |
| `videoPktQueue_` / `audioPktQueue_` | demux 生产、对应解码线程消费，内部加锁 + serial |
| 实时流 PTS 归一化 | `PTSNormalizer` 内部 mutex 保护组合状态，两解码线程共用 |

**FrameQueue 环形队列设计（对标 ffplay，不变）**：
- 预分配固定大小 Frame 数组，消除每帧 `make_shared` + `av_frame_alloc` 开销
- 生产者：`tryPeekWritable()`（非阻塞）/ `waitWritableSlot()`（可中断轮询，serial
  变化即放弃，避免 seek 时硬阻塞死锁）+ `push()`
- 消费者：`peek()` + `next()`
- keep-last 机制：视频队列保留最后渲染帧，暂停/截图时可复用
- `abort()` + `flush()`：stop/seek 时干净唤醒阻塞线程

**EOF 处理**：demux 读完后向各启用的 packet 队列投递 null 包，解码线程 drain 解码器
残帧后置 `*DecodeFinished_` 退出；`run()` 按已启用的流组合（`hasVideoStream_` /
`hasAudioStream_`）判定整体结束。**本地文件 EOF 后 demux 线程不退出而是停泊**（投递
一次 null 包让 decode drain 后，每 10ms 轮询 `processSeekRequest()`）——否则小文件几毫秒
读到 EOF 退出后，再无线程消费 seek 请求，seek 会失效。仅 `shouldQuit_` 能终结停泊。

**seek 正确性（serial + 三层丢旧帧）**：网络流（尤其 DASH 重启上游需数秒）seek 时，
旧位置的在途帧若混入会污染 AV 时钟、把进度条拉回旧位置。三层互补保证只有目标位置的
新帧生效：
- **`seek()` 即时 flush**（UI 线程）：置位精确跳转（`decodingToTarget_`）的同时同步
  `flush`（serial++），不等 demux 线程，第一时间关闭「在途已解码帧」窗口
- **demux 挂起期丢包**：demux `readPacket` 成功后、入队前，若 `seekRequest_.pending`
  为真则丢弃该包 —— 旧 pipe 残包不进队列、拿不到新 serial（根因修复）
- **enqueue serial guard**：`enqueueVideoFrame/AudioFrame` 开头丢弃
  `serial != pktQueue->serial()` 的在途残帧
  这三层不依赖任何 PTS 阈值（PTS 无法区分「旧的靠后帧」与「新的合法靠后帧」，serial 才能）。

**数据变化过程（对应代码中的具体函数调用）**：

```
第3步 readPacket:
  Demuxer::readPacket(packet)          → 得到 AVPacket（压缩码流）
  ↓                                       代码: av_read_frame(m_formatCtx, packet)
  ↓
第3步 sendPacket:
  VideoDecoder::sendPacket(packet)     → 将 AVPacket 送入FFmpeg解码器内部缓冲区
  ↓                                       代码: avcodec_send_packet(m_codecCtx, packet)
  ↓
第1步 receiveFrame:
  VideoDecoder::receiveFrame(rawFrame) → 从解码器取出 AVFrame（原始像素数据）
  ↓                                       代码: avcodec_receive_frame(m_codecCtx, frame.getAVFrame())
  ↓                                       此时 rawFrame 内部的 AVFrame 包含解码后的YUV数据
  ↓                                       同时计算 PTS: pts = avFrame->pts * av_q2d(m_timeBase)
  ↓
第1步 prepareFrame:
  VideoDecoder::prepareFrame(...)      → 将 AVFrame 准备为可渲染格式的 Frame
                                          硬件解码: av_hwframe_transfer_data() → NV12 → av_frame_ref()
                                          软件解码: av_frame_ref()（YUV420P零拷贝）或 sws_scale()
                                          最终得到的 Frame 通过 videoQueue_->push() 入队
```

> **注意 sendPacket 和 receiveFrame 的异步关系**：
> FFmpeg的解码是异步的——`sendPacket()` 只是把数据送进去，不会立即产出帧。
> 解码器内部可能需要积累多个packet才能输出一帧（比如B帧需要参考前后帧），
> 也可能一个packet解出多个帧。所以代码中是**先尝试receiveFrame，再去readPacket**，
> 确保解码器缓冲区里的帧都被取出来。

### 第五步：视频渲染循环 (Player::run)

**代码位置**：`Player::run()` / `Player::renderVideoFrame()`

主线程负责渲染视频帧，由 **VSync 驱动 + 主时钟调度**（非 sleep 定时），下面是简化伪代码：

```cpp
void Player::run() {
    while (!shouldQuit_ && !window_->shouldClose()) {
        glfwPollEvents();
        // 2. 取帧由主时钟决定：peek 队首帧，PTS <= 主时钟+0.005 才显示
        Frame* peeked = videoQueue_->peek();
        if (peeked && peeked->getPTS() <= avSync_->getMasterClock() + 0.005) {
            videoQueue_->next();                  // 推进读索引（keep-last 机制）
            avSync_->updateVideoClock(peeked->getPTS());
            renderer_->renderFrame(...);          // YUV/NV12 上传 + 着色器转 RGB
            lastRenderedPTS_.store(peeked->getPTS());
        }
        // else: 还没到显示时间则按剩余时间短暂 sleep（上限 20ms）避免空转；
        //       seek 精确跳转期（decodingToTarget_）暂停取帧，复用 GPU 纹理保持上一帧

        // 3. EOF 判定：按已启用的流组合（hasVideoStream_/hasAudioStream_）
        if (demuxFinished_ && videoDone && audioDone) { shouldQuit_ = true; }

        if (renderCallback_) renderCallback_();   // 渲染 UI（进度条/控制面板）
        window_->swapBuffers();                   // VSync 节流
        window_->pollEvents();
    }
}
```

**关键点**：
- 渲染节奏由 **VSync（swapBuffers）+ 主时钟比较**驱动，不再用 `sleep(computeFrameDelay)` 的旧帧率控制
- 主时钟优先音频时钟（有音频时），视频帧 PTS 与主时钟比较决定显示/等待
- seek 期间 `decodingToTarget_` 冻结取帧、复用缓存纹理；进度条读 `lastRenderedPTS_`（seek 时即时置为目标值）

---

### 第六步：音频播放回调 (audioOutputCallback)

**代码位置**：`Player::audioOutputCallback()`

音频输出是**回调驱动**的，由平台音频线程在需要数据时调用，消费 `audioQueue_`（下为简化伪代码）：

```cpp
size_t Player::audioOutputCallback(uint8_t* buffer, size_t bufferSize) {
    size_t bytesWritten = 0;
    
    while (bytesWritten < bufferSize) {
        // 1. 从音频队列取出一帧（FrameQueue peek/next）
        auto frame = audioQueue_->peek();
        if (!frame) {
            // 队列空，填充静音
            memset(buffer + bytesWritten, 0, bufferSize - bytesWritten);
            break;
        }
        
        // 2. 获取音频数据
        uint8_t* audioData = frame->getData()[0];
        int dataSize = frame->getNbSamples() * audioChannels_ * 2;  // S16格式
        
        // 3. 应用音量
        int16_t* samples = (int16_t*)audioData;
        float vol = muted_ ? 0.0f : volume_.load();
        for (int i = 0; i < frame->getNbSamples() * audioChannels_; i++) {
            samples[i] = (int16_t)(samples[i] * vol);
        }
        
        // 4. 拷贝到输出缓冲区
        size_t bytesToCopy = std::min(dataSize, bufferSize - bytesWritten);
        memcpy(buffer + bytesWritten, audioData, bytesToCopy);
        bytesWritten += bytesToCopy;
        
        // 5. 更新音频时钟
        avSync_->updateAudioClock(frame->getPTS());
    }
    
    return bytesWritten;
}
```

**这个回调做什么？**
1. 从音频队列取出PCM数据
2. 应用音量控制
3. 填充到系统音频缓冲区
4. 更新音频时钟（用于音视频同步）

### 1. Demuxer（解封装器）

### 2. VideoDecoder（视频解码器）

**代码位置**：`include/FluxPlayer/decoder/VideoDecoder.h`

**作用**：将压缩的H.264/H.265视频解码为可渲染帧，支持硬件加速

```cpp
class VideoDecoder {
    AVCodecContext* m_codecCtx;     // 解码器上下文
    SwsContext* m_swsCtx;           // 格式转换器（回退路径用）
    AVBufferRef* m_hwDeviceCtx;     // 硬件设备上下文（null=软件解码）
    AVFrame* m_hwTransferFrame;     // 可复用的GPU→CPU传输帧
    
    bool init(AVCodecParameters* codecParams, AVRational timeBase);
    bool sendPacket(AVPacket* packet);      // 送入压缩包
    bool receiveFrame(Frame& frame);        // 接收解码帧
    bool prepareFrame(AVFrame* src, Frame& dst);  // 帧准备（替代原convertToYUV420P）
    bool isHWAccelActive() const;           // 是否正在使用硬件加速
    AVHWDeviceType getHWDeviceType() const; // 供 Player 检测后端类型（CUDA/D3D11VA等）
};
```

**工作流程**：
1. `init()`：查找解码器，尝试硬件加速初始化（按平台优先级）
2. `sendPacket()`：将压缩数据包送入解码器
3. `receiveFrame()`：从解码器取出解码后的帧
4. `prepareFrame()`：硬件帧→GPU→CPU传输(NV12)→零拷贝入队；软件帧→YUV420P零拷贝

**硬件加速初始化**（`initHWAccel()`）：
- macOS：尝试 VideoToolbox
- Windows：按优先级尝试 CUDA(NVDEC) → D3D11VA → DXVA2
- 第一个成功的即用，全部失败则自动回退软件解码
- 新增 `getHWFormat` 回调，确保 FFmpeg 正确协商硬件像素格式

**硬件解码自动降级**（`reinitAsSoftware()`）：

VideoToolbox/CUDA 等硬件解码器遇到参考帧丢失（如视频文件本身有丢帧）时，整个解码线程池进入不可恢复状态，`avcodec_flush_buffers()` 无法恢复。

降级机制：
- `sendPacket()` 内部维护连续失败计数 `m_hwFailCount`
- 连续失败 ≥ 3 次时调用 `reinitAsSoftware()`，完全重建解码器上下文（禁用硬件加速，单线程）
- 重建后立即重发当前 packet，软件解码器对损坏帧会尽力输出花屏而非拒绝
- `init()` 时将 `codecParams` 深拷贝到 `m_savedCodecParams`，供降级重建使用

**CUDA 绿屏修复**（Windows CUDA 后端）：

CUDA + NVIDIA 驱动下 `GL_RG8` 纹理存在兼容性问题，UV 数据采样异常导致绿色画面。解决方案：
- `GLRenderer` 新增 UV 解交错模式：将交错 UV 平面拆分为独立 U/V 平面，复用 YUV420P shader 路径
- `Player` 通过 `getHWDeviceType() == AV_HWDEVICE_TYPE_CUDA` 检测后端，自动启用解交错模式

**FFmpeg API调用**：
- `av_hwdevice_ctx_create()` - 创建硬件设备
- `avcodec_send_packet()` - 送入数据
- `avcodec_receive_frame()` - 接收帧
- `av_hwframe_transfer_data()` - GPU→CPU帧传输
- `sws_scale()` - 格式转换（回退路径）

**实现位置**：`src/decoder/VideoDecoder.cpp`

### 4. AVSync（音视频同步）

**代码位置**：`include/FluxPlayer/core/AVSync.h`

**作用**：确保音频和视频同步播放，这是播放器最核心的算法

```cpp
class AVSync {
    ClockType clockType_;           // 同步模式
    std::atomic<double> audioClock_;  // 音频时钟
    std::atomic<double> videoClock_;  // 视频时钟
    
    // 核心方法
    double computeFrameDelay(double framePTS, double lastFramePTS);
    bool shouldDropFrame(double framePTS, double threshold);
};
```

**同步策略**：

FluxPlayer使用**外部时钟（系统时钟）**作为基准：

```cpp
// 计算帧延迟的核心算法
double AVSync::computeFrameDelay(double framePTS, double lastFramePTS) {
    // 1. 计算帧间隔（理论延迟）
    double delay = framePTS - lastFramePTS;
    
    // 2. 获取主时钟（系统时钟）
    double masterClock = getMasterClock();
    
    // 3. 计算视频与主时钟的差值
    double diff = framePTS - masterClock;
    
    // 4. 根据差值调整延迟
    if (diff <= -syncThreshold) {
        // 视频落后，减少延迟（加快）
        delay = std::max(0.0, delay + diff * 0.5);
    } else if (diff >= syncThreshold) {
        // 视频超前，增加延迟（减慢）
        delay = delay + diff * 0.5;
    }
    
    return delay;
}
```

**三种时钟模式**：
- `AUDIO_CLOCK`：以音频为基准，视频跟随音频
- `VIDEO_CLOCK`：以视频为基准，音频跟随视频
- `EXTERNAL_CLOCK`：以系统时钟为基准（FluxPlayer使用这种）

**实现位置**：`src/core/AVSync.cpp:74-129`

### 4.1 播放速度控制

**代码位置**：`include/FluxPlayer/core/Player.h`，`src/core/AVSync.cpp`

**作用**：支持 0.5x / 0.75x / 1.0x / 1.25x / 1.5x / 2.0x 六档变速播放，视频和音频同步加速/减速。

#### 时钟驱动机制

变速的核心是让外部时钟以 `rate` 倍实时速率推进。视频渲染循环的帧显示条件为 `nextPTS <= masterClock + 0.005`，主时钟加速后视频帧被更快消耗：

```cpp
// AVSync::getExternalClock()
double elapsed = duration_cast<double>(now - externalClockBase_).count();
return externalClockOffset_ + elapsed * playbackRate_;  // 乘以速率
```

**速率切换防时钟跳变**：切换速率前先锁定当前时钟值，重置基准，避免 `elapsed × newRate` 导致时钟大幅跳变（如 2x→0.5x 时时钟跳退导致视频冻结）：

```cpp
// AVSync::setPlaybackRate(rate)
double current = getExternalClock();
externalClockBase_ = steady_clock::now();
externalClockOffset_.store(current);
playbackRate_.store(rate);
```

#### 快放丢帧（>1.0x）

外部时钟加速后视频帧被快速消耗，对已取出的帧做智能丢帧减少解码压力：
- I 帧永不丢弃（解码基准）
- B 帧按概率丢弃：`(rate-1)/rate`（2.0x 时 50%）
- P 帧仅 2.0x 时以 25% 概率丢弃

**代码位置**：`src/core/Player.cpp` `shouldDropFrameForSpeed()`

#### 音频变速重采样

每次音频回调消耗 `bufferSize × rate` 字节内容，最近邻重采样到 `bufferSize` 字节输出：

```
快放(2x)：消耗 2× 内容 → 压缩到 1× 输出 → 音调升高
慢放(0.5x)：消耗 0.5× 内容 → 拉伸到 1× 输出 → 音调降低
```

音频时钟同步更新：`currentAudioPTS = prevClock + deviceDuration × rate`

**代码位置**：`src/core/Player.cpp` `audioOutputCallback()`

### 5. GLRenderer（OpenGL渲染器）

**代码位置**：`include/FluxPlayer/renderer/GLRenderer.h`

**作用**：使用OpenGL将视频帧渲染到屏幕，支持YUV420P和NV12两种格式

```cpp
class GLRenderer {
    GLuint m_textureY;   // Y平面纹理（亮度，两种格式共用）
    GLuint m_textureU;   // U平面纹理（色度Cb，YUV420P用）
    GLuint m_textureV;   // V平面纹理（色度Cr，YUV420P用）
    GLuint m_textureUV;  // UV交错纹理（GL_RG8，NV12硬件解码零拷贝用）
    
    void renderFrame(uint8_t* yData, uint8_t* uData, uint8_t* vData,
                     int yPitch, int uPitch, int vPitch,
                     bool isNV12 = false,
                     int colorSpace = 0, int fullRange = 0);
};
```

**渲染流程**：

1. **上传YUV/NV12数据到GPU纹理**：

YUV420P 路径（软件解码）：
```cpp
// Y平面（全分辨率，GL_RED 单通道）
glTexSubImage2D(..., GL_RED, GL_UNSIGNED_BYTE, yData);
// U平面（1/2分辨率，GL_RED 单通道）
glTexSubImage2D(..., GL_RED, GL_UNSIGNED_BYTE, uData);
// V平面（1/2分辨率，GL_RED 单通道）
glTexSubImage2D(..., GL_RED, GL_UNSIGNED_BYTE, vData);
```

NV12 路径（硬件解码零拷贝）：
```cpp
// Y平面（全分辨率，GL_RED 单通道，与YUV420P相同）
glTexSubImage2D(..., GL_RED, GL_UNSIGNED_BYTE, yData);
// UV交错平面（1/2分辨率，GL_RG 双通道，U和V交错存储）
glTexSubImage2D(..., GL_RG, GL_UNSIGNED_BYTE, uvData);
```

2. **在片段着色器中转换YUV/NV12到RGB**：

**着色器代码位置**：`assets/shaders/video.frag`

```glsl
uniform int isNV12;      // 0 = YUV420P, 1 = NV12
uniform int colorSpace;  // 0 = BT.601(SD), 1 = BT.709(HD), 2 = BT.2020(UHD)
uniform int fullRange;   // 0 = TV/limited range, 1 = PC/full range

float y = texture(texY, TexCoord).r;
float u, v;

if (isNV12 == 1) {
    // NV12：从 GL_RG8 纹理的两个通道分别读取 U 和 V
    vec2 uv = texture(texU, TexCoord).rg;
    u = uv.r - 0.5;
    v = uv.g - 0.5;
} else {
    // YUV420P：U 和 V 各自独立的单通道纹理
    u = texture(texU, TexCoord).r - 0.5;
    v = texture(texV, TexCoord).r - 0.5;
}

// TV range 量化范围缩放（ITU-R 标准 studio swing）
if (fullRange == 0) {
    y = (y - 16.0/255.0) * (255.0/219.0);
    u = u * (255.0/224.0);
    v = v * (255.0/224.0);
}

// YUV→RGB 转换（根据 colorSpace 选择 BT.601/709/2020 系数）
// 以 BT.709 为例：Kr=0.2126, Kb=0.0722
float r = y + 1.5748 * v;
float g = y - 0.1873 * u - 0.4681 * v;
float b = y + 1.8556 * u;
FragColor = vec4(clamp(r,0,1), clamp(g,0,1), clamp(b,0,1), 1.0);
```

Player 在渲染前从 `AVFrame` 提取色彩元数据传递给着色器：
- `AVFrame::colorspace` → 映射为 colorSpace（0/1/2）
- `AVFrame::color_range` → 映射为 fullRange（0/1）
- 元数据为 `AVCOL_SPC_UNSPECIFIED` 时按分辨率启发式选择（≥720p → BT.709）

**为什么用YUV而不是RGB？**
- 视频编码器输出的就是YUV格式
- YUV可以色度抽样（4:2:0），节省带宽
- GPU可以高效处理YUV到RGB的转换

**实现位置**：`src/renderer/GLRenderer.cpp`

### 8. PacketQueue（压缩包队列）

**职责：** 解耦 demux 线程（生产者）与 video/audio 解码线程（消费者）的压缩包队列，对标 ffplay `PacketQueue`。是多线程解耦模型的核心同步原语。

**数据结构：** 单向链表（`Node{AVPacket* pkt; int serial; Node* next;}` + `first_`/`last_` 指针），内部 `std::mutex` + `std::condition_variable` + `std::atomic<bool> abort_`。全程 `av_packet_move_ref` 转移所有权，零数据拷贝。

**接口：**
- 生产者：`put(AVPacket*)` 非阻塞追加；`putNullPacket(streamIndex)` 投递 EOF 标记包（data=NULL）驱动解码器 drain
- 消费者：`get(pkt, block, &serial)` 返回 1=取到 / 0=abort（应退线程）/ -1=非阻塞且空，出参返回该包入队时的 serial
- 控制（任意线程，内部加锁）：`flush()` 清空并 `++serial_`；`abort()` / `start()`（`start` 也 `++serial_`）
- 查询：`size()` / `byteSize()` / `duration()`（需 `setTimeBase`）/ `serial()` / `isAbort()`

**serial 序号（seek 正确性核心）：** 每次 `flush()`/`start()` 自增。消费者发现 `get()` 返回的 serial 变化，即知发生过 seek/flush，**自行** flush 自己的解码器与帧队列（与生产者同线程，无竞态）——跨线程 seek 无需 demux 线程触碰解码器。seek 时旧帧的丢弃也据此判定（见「seek 正确性」三层丢旧帧）。

**背压：** 同时维护字节数与时长（注释指出「字节数对高码率视频/低码率音频区分度差，时长更稳定」）；阈值在 Player 侧判断：软上限 15MB（对齐 ffplay）/ 硬上限 64MB / 单路 48MB / 各流时长门槛，防坏文件或差交织导致单路无限缓冲 OOM。

### 9. PTSNormalizer（实时流 PTS 归一化）

**职责：** 实时流 PTS 归一化的线程安全组合状态。video/audio 解码线程拆分后，「首帧记录 + 统一基准校准 + 回绕重校准 + reset」横跨两线程，单个 atomic 无法保证「判断未校准 → 写基准」这类组合操作原子性，故用**一个 mutex 保护整组状态**。

**接口：**
- `normalizeVideo(rawPTS, frameInterval)` / `normalizeAudio(...)` → `Result{bool drop; bool estimated; double pts;}`
- `reset()`：play/seek 重新校准时清空全部状态
- `Result.estimated` 语义关键：估算值不应驱动主时钟（Player 据此决定是否更新 AV 时钟）

**归一化规则（由原 `Player::normalizeVideoPTS/AudioPTS` 迁入）：**
- 无效 PTS（非有限 / 超 ±1e15，排除 `AV_NOPTS_VALUE`）：已校准则 `lastValid + frameInterval` 估算并置 estimated；未校准则 drop
- 首帧记录原始 PTS；**音视频均到达后取两者较小值为统一基准 `basePTS_`**
- 已校准：`normalized = rawPTS - basePTS_`
- **回绕处理不对称**（32bit RTP 时间戳溢出）：视频检测到 `normalized < -10` **只丢帧不重置基准、等音频统一处理**；音频回绕则**立即以当前音频 PTS 为新基准重校准**——音频是回绕重校准的主导方
- 异常跳变仅视频侧做：倒退 > 0.5s 或前跳 > 30s 视为脏数据，用估算值代替并置 estimated

### 10. FrameInterpolator（慢放补帧，预留未接入）

**职责（设计意图）：** 慢放时在相邻两帧间生成中间帧。**集成状态：当前仅在 `Player` 构造时实例化，`interpolate()` 从未在渲染循环中被调用，配套字段 `prevVideoFrame_` 也未被引用——属已实现但尚未接入 `run()` 的预留能力。** 阅读本节请以此为前提，它目前不影响实际播放行为。

**接口：** `Frame* interpolate(const Frame* f1, const Frame* f2, double alpha)`，alpha∈[0,1]（0=f1，1=f2，0.5=中点），返回新建 Frame（调用方负责 delete），仅支持同分辨率 YUV420P，失败返回 nullptr。

**自适应策略：** 先 `detectMotion` 算归一化 SAD（每 4 像素降采样取 Y 平面）：
- SAD < 0.02（低运动）→ `blendFrames` 定点线性混合（Y 全分辨率 + U/V 半分辨率）
- 否则 → `motionCompensatedInterpolate` **三步搜索法（TSS）** 块匹配运动补偿（块 16×16、搜索范围 16），Y 平面按块沿运动向量×alpha 取中间位置 + 前后向混合减伪影，U/V 仅线性混合；返回 null 时降级回 `blendFrames`

全程定点整数运算避免浮点开销；头文件用前向声明 `class Frame;` 不暴露 FFmpeg 类型。

FluxPlayer 采用 **ffplay 式解耦的五线程模型**（demux 与音视频解码分离）：

```
┌──────────────────────────────────────────┐
│           主线程 (Main Thread)            │
│  - 窗口事件处理 (glfwPollEvents)          │
│  - 视频帧渲染 (GLRenderer::renderFrame)   │
│  - UI绘制 (ImGui) / 帧率控制              │
│  - 消费 videoQueue_                       │
└──────────────────────────────────────────┘

┌──────────────────────────────────────────┐
│           demux 线程 (Demux Thread)       │
│  - 读包 (demuxer->readPacket)             │
│  - 按流分发到 videoPktQueue_/audioPktQueue_│
│  - 字幕同步解码                            │
│  - seek / DASH 重启 / 直播重连            │
│  - 录制 writePacket                       │
└──────────────────────────────────────────┘

┌────────────────────┐  ┌────────────────────┐
│ video 解码线程      │  │ audio 解码线程      │
│ - videoPktQueue_.get│  │ - audioPktQueue_.get│
│ - 解码 + 归一化     │  │ - 解码 + 归一化     │
│ - 入 videoQueue_    │  │ - 入 audioQueue_    │
│ - serial 变化自 flush│  │ - serial 变化自 flush│
└────────────────────┘  └────────────────────┘

┌──────────────────────────────────────────┐
│      平台音频线程 (Audio Thread)          │
│  - 系统音频回调驱动                       │
│  - 从 audioQueue_ 取数据 / 应用音量       │
│  - 更新音频时钟                           │
└──────────────────────────────────────────┘
```

> 纯音频模式不创建 video 解码线程；无音频流时不创建 audio 解码线程与平台音频线程。

**为什么解耦**：旧的「读包+音视频解码」单线程模型存在结构性死锁——视频帧队列满时
解码线程阻塞，读不到音频包导致音频饿死、主时钟冻结、画面卡死（mov/mp4 视频包前置
交织必中）。拆分后视频帧队列满只阻塞 video 解码线程，audio 链路独立推进，死锁消除。
详见「第四步」。

**线程同步**：
- 帧队列 `FrameQueue` / 包队列 `PacketQueue` 内部各自加锁
- `PacketQueue` 用 **serial 序号**标记 seek/flush 边界，解码线程据此自行 flush 解码器与帧队列
- 实时流 PTS 归一化组合状态由 `PTSNormalizer` 内部 mutex 保护，两解码线程共用
- 使用 `std::atomic` 保存状态标志（`shouldQuit_` / `*DecodeFinished_` 等）
- Seek 请求用 `seekMutex_` 保护的 `SeekRequest` 结构体，消除 TOCTOU 竞态
- 录制器 start/stop 与 demux 线程 writePacket 之间用 `recorderMutex_` 保护
- 音视频同步通过时钟（`AVSync`）协调

### 网络流缓冲策略

**实时流识别**（`src/decoder/Demuxer.cpp`）：

原先只靠格式名判断，RTMP 被 FFmpeg 解析为 `flv` 格式名导致漏判。现在采用多重判断：
1. URL 协议头（`rtsp://`、`rtmp://`、`http://`、`https://`）
2. HLS 格式名（`hls`、`.m3u8`）
3. `duration == 0`（无时长信息）

**按协议设置专用选项**：
- HTTP/HLS：`reconnect_on_network_error=1` 断流自动重连，`probesize=512KB` / `analyzeduration=2s` 加速起播
- RTSP：TCP 传输 + `buffer_size=1MB` 抗丢包；`probesize=256KB` / `analyzeduration=500ms` 把默认 5 秒探测期压到 0.5 秒
- RTMP：`live=1` 直播模式
- DASH pipe（`pipe:N`）：`probesize=256KB` / `analyzeduration=500ms`；且 header 自描述时直接跳过 `find_stream_info`（见 DashMerger 节），消除探测段网络等待

**网络流媒体信息（codec/分辨率等）提取**：网络流（RTSP/RTMP/HLS/网页流）不重复连接探测，而是**复用 Player/Demuxer 已打开的 `AVFormatContext`**——`Player::getFormatContext()` 暴露内部 demuxer 的 format context，`MediaInfo::extractFromContext()` 据此填充 UI 字段，零额外连接开销。否则这些字段会显示 "Unknown"。

**起播追赶**（`src/core/Player.cpp::demuxThread`）：
- 实时流首个 IDR 之前的视频包全部丢弃，避免参考帧缺失导致的 "Could not find ref with POC" 灰屏
- prebuffer 期间若再次收到 IDR，flush 队列与解码器从最新关键帧重新起播，端到端延迟最多 = 网络握手 + 1 个 GOP

**队列深度策略**（`src/core/Player.cpp::open`）：
- 本地文件：视频队列 4 帧，音频队列 10 帧
- 实时流：视频队列 3 帧（≈120ms@25fps）、音频队列 8 帧、预缓冲 2 帧后起播 —— 浅队列降低端到端延迟
- 音频队列动态扩容：欠载（underrun）频繁时自动扩大，上限 100 帧

**PTS 稳定性**（`src/core/Player.cpp::normalizeVideoPTS / enqueueVideoFrame`）：
- VideoDecoder 优先取 `best_effort_timestamp`（FFmpeg 内部按 pts → dts → 推断的优先级），减少 NOPTS 概率
- 归一化后倒退 > 0.5s 或前跳 > 30s 视为脏数据，用 `lastPTS + frameInterval` 估算值代替并标记为 estimated
- 入队前强制 PTS 单调递增（夹紧到 `lastEnqueued + 1ms`），防止队列内非单调 PTS 导致进度条抖动
- prepareFrame 内部用 AVFrame::pts 重置 PTS 会覆盖归一化结果，入队时显式回写归一化 PTS 与 estimated 标记
- prebuffer 完成后调 `AVSync::resetExternalClock`，否则 master clock 已超前队列首帧，渲染线程会一次性消化所有缓冲帧导致 FPS 异常飙高
- 实时流 `getCurrentTime` 改用 audio clock 驱动进度条，与视频帧 PTS 抖动解耦

## 字幕模块解析

### 整体数据流

```
Demuxer (AVPacket, stream_index=字幕流)
    ↓
DemuxWorker::run() 路由（字幕在 demux 线程内同步解码）
    ↓
SubtitleDecoder::decode(packet) → vector<Item>{text, startPTS, endPTS}
    ↓
SubtitleManager::addEntry()  ← demux 线程写入（加锁）
    ↓
Controller::renderSubtitles() 每帧查询 getCurrentText(masterClock)
    ↓
ImGui 半透明浮层渲染（底部居中）
```

### SubtitleDecoder（`include/FluxPlayer/subtitle/SubtitleDecoder.h`）

- 封装 FFmpeg `avcodec_decode_subtitle2` API
- 支持文本类字幕：SRT / ASS / SSA / WebVTT / mov_text
- 图形字幕（PGS / DVB-SUB）阶段一跳过，记录 DEBUG 日志
- 用 RAII scope guard 确保 `avsubtitle_free` 在所有路径被调用
- PTS 换算优先级：`end_display_time` > `packet->duration` > 5 秒兜底
- `stripASSOverrides()` 清理 `{\\xxx}` 控制标签，兼容 FFmpeg 4.x 的 `Dialogue:` 前缀格式

### SubtitleManager（`include/FluxPlayer/subtitle/SubtitleManager.h`）

- **零 FFmpeg 依赖**，可被 UI 层安全 include
- 线程安全：单 `std::mutex` 保护 `std::deque<Entry>`
- `addEntry()`：常见路径 O(1) 尾插；乱序时 `upper_bound` 插入；超 500 条从头裁剪
- `getCurrentText()`：正序扫描，同时惰性清除 `endPTS < currentPTS - 5s` 的过期条目

### Controller 字幕渲染（`src/ui/Controller.cpp`）

- `renderSubtitles()` 在 `render()` 最前调用，**独立于 UI 可见性**（UI 自动隐藏时字幕仍显示）
- `loadSubtitleFont()` 在 ImGui 初始化时调用，按平台探测 CJK 字体，用 MergeMode 叠加多字符范围
- `Controller.h` 中 `ImFont*` 用 `void*` 存储，保持头文件零 ImGui 依赖

### Seek 与循环播放

- Seek 时：`SubtitleDecoder::flush()` + `SubtitleManager::clear()`，避免残留旧字幕
- 循环播放重启时：`decodingFinished_` 必须重置为 false，否则渲染循环立即退出

### 配置项（`[Subtitle]` 节）

| 配置项 | 说明 | 默认值 |
|--------|------|--------|
| `subtitleEnabled` | 字幕总开关（重开媒体生效） | `true` |
| `subtitleFontScale` | 字幕字体缩放（0.5 ~ 4.0） | `1.4` |
| `subtitleFontPath` | 自定义字体路径（空则自动探测） | 空 |

## 网页视频播放模块

### 整体数据流

```
用户输入网页 URL
    │
    ▼ StreamExtractor::needsExtraction()
    │
    ├─ false → 原有流程（直链/RTSP/RTMP）
    │
    └─ true  → StreamExtractor::extract()
                    │ 调用 yt-dlp -j
                    ▼
               ExtractedStream { videoUrl, audioUrl, headers, isDash, duration }
                    │
                    ├─ isDash=false → Demuxer::open(videoUrl, headers)
                    │
                    └─ isDash=true  → DashMerger::start(videoUrl, audioUrl, headers)
                                           │ FFmpeg API 合并，写入 pipe
                                           ▼
                                      Demuxer::open("pipe:N", "", duration)
```

### StreamExtractor（`src/utils/StreamExtractor.cpp`）

**职责：** 调用 yt-dlp 提取网页视频流信息，解析 JSON 输出。

**关键方法：**
- `needsExtraction(url)`：检测 URL 是否需要提取。直链（含媒体扩展名）、RTSP/RTMP 返回 false；已知平台域名或无扩展名的 HTTP URL 返回 true。
- `extract(pageUrl, formatId, out, error)`：同步调用 yt-dlp，解析 JSON，填充 `ExtractedStream`。应在后台线程调用（阻塞约 2-5 秒）。
- `prepareCookieArgForUrl(pageUrl)`：根据目标 URL 主机查 `CookieStore`，命中则返回 `--cookies "<专用 cookie 文件路径>"`，未命中返回空。不再访问系统浏览器的 cookie 数据库。供 StreamExtractor 和 Downloader 共用。

**yt-dlp 路径：** 编译时通过 `YTDLP_BUNDLED_PATH` 宏注入（CMakeLists.txt / xmake.lua），优先使用 `third_party/yt-dlp/` 打包版本，找不到则回退到系统 PATH。

**格式选择：** 默认优先 H.264（`bestvideo[vcodec^=avc1]+bestaudio`），避免 AV1/HEVC 在 MKV pipe 中的兼容性问题。

**DASH 判断：** JSON 中存在 `requested_formats` 数组即为 DASH 分离流，第一个对象为视频，第二个为音频。

### DashMerger（`src/utils/DashMerger.cpp`）

**职责：** 在后台线程用 FFmpeg API 将视频流和音频流合并为 MKV，通过管道输出给 Demuxer。

**关键设计：**
- macOS/Linux：用 `pipe(2)` 创建匿名管道，写端由合并线程写入，读端以 `"pipe:N"` 形式传给 `Demuxer::open()`
- Windows：使用 Win32 命名管道（`\\.\pipe\FluxPlayer_DashMerger_PID_SEQ`），`FILE_FLAG_OVERLAPPED` 模式创建，支持异步等待连接和写入
- 合并时清除 `codec_tag = 0`，避免 mp4a 与 MKV 容器不兼容
- 按 DTS 顺序交错写出（`av_compare_ts`），确保音视频时间戳连续，避免 `Starting new cluster` 警告
- `start()` 支持 `startSeconds` 参数：在两个 input 打开后调用 `av_seek_frame(ctx, -1, ts, AVSEEK_FLAG_BACKWARD)` 跳转。FFmpeg 内部利用源 m4s URL 的 HTTP Range 拉取目标位置数据，**输出的 PTS 保留原始绝对时间**（不重置为 0），Player 的 AClock/VClock 无需偏移修正
- **视频/音频远程流并行打开**：两路 `avformat_open_input` + `find_stream_info` 各需经代理拉取数秒，原先串行（视频开完才开音频）是 seek/起播延迟主因。改为两条线程并行打开，各用独立 `InterruptCtx`（共享会数据竞争），墙钟约减半
- **MKV header 写入帧率**：建输出流时拷贝源流 `avg_frame_rate`/`r_frame_rate`，使 header 完全自描述。否则下游 pipe demuxer 的 `find_stream_info` 无法从 header 得到 fps，只能从管道读大量包估算（受 merger 下载速度限制，达数秒）
- **`write_header` 后立即 `avio_flush`**：header 仅几 KB，默认滞留在 32KB AVIO 缓冲里要等帧数据攒满才推进管道；而 seek 后首个关键帧经冷连接下载可能数秒，期间下游 `avformat_open_input` 一直读不到 header 而阻塞。主动 flush 把"打开"与"等首帧下载"解耦

**Windows 命名管道时序（避免死锁）：**
1. 合并线程先打开远程视频/音频流（网络请求）
2. 准备输出上下文、添加流映射
3. `ready_.store(true)` 通知主线程
4. `ConnectNamedPipe`（OVERLAPPED）等待客户端连接
5. 主线程 `waitReady()` 返回 → `Demuxer::open(pipeName)` → FFmpeg `CreateFile` 连接管道
6. `ConnectNamedPipe` 返回 → 立即 `avformat_write_header` 写 MKV header
7. Demuxer 读到 header 完成格式探测，播放开始

**Windows 停止机制：** `stop()` 通过 `SetEvent(stopEvent_)` + `CancelIoEx` 中断 `ConnectNamedPipe` 的 OVERLAPPED 等待，避免线程无法 join。

**FFmpeg 版本兼容：** `avio_alloc_context` 的 write callback 参数类型在 FFmpeg 7.x（`LIBAVFORMAT_VERSION_MAJOR >= 61`）中改为 `const uint8_t*`，旧版为 `uint8_t*`。通过 `AVIO_WRITE_BUF_TYPE` 宏统一处理。

**DASH 流 seek 实现：** pipe 输入对 FFmpeg 不可 seek，matroska 流式生成时无 cues 索引，无法走 `demuxer_->seek` 路径。`DemuxWorker::restartDashMerger(seekTime)` 停止旧 merger、用 `seekTime` 参数重启从目标位置下载，再重建 demuxer。`processSeekRequest` 检测到 `dashMerger_ != nullptr` 时分流到此路径。重启 + 重开 demuxer 包成**重试循环（最多 3 次）**，bilibili 分片经代理拉取偶发瞬时失败（TLS pull error 等）单次失败不再让整个 seek 永久 ERROR。

**DASH seek 提速（pipe demuxer 跳过 find_stream_info）：** DashMerger 写 MKV header 时已带完整 codecpar（含 extradata）+ 帧率，header 完全自描述。`Demuxer` 用 `streamInfoReadyForPipe()` 判定：`pipe:` 前缀且所有音视频流 codecpar 关键字段（codec_id/宽高/采样率）就绪时，**跳过 `find_stream_info`**——它只会从管道再读包/试解码一帧来"确认"，而读包受限于 merger 从远程下载，正是 seek 探测段数秒延迟的根源。任何字段缺失则回退正常探测保证健壮。配合 pipe 专用 `probesize=256KB`/`analyzeduration=500ms`，seek 实测从 ~6s 降到 ~2s（首次远跳因冷连接下载首个 4K 关键帧仍可能 ~8s，属固有网络成本）。

**注意：** 不能用 `av_dict_set(opts, "ss", ...)` 在 input 之前注入 ss——这等价于 ffmpeg CLI 的"input 前 -ss"，会重置输出 PTS 从 0 开始，导致 AClock 与帧 PTS 不一致。必须用 input 打开后的 `av_seek_frame` 实现保留原 PTS 的 seek。

**线程安全：** `start()`/`stop()` 应在同一线程调用；`running_` 为 `atomic<bool>`，合并线程通过它感知停止信号；`ready_` 为 `atomic<bool>`，主线程通过 `waitReady()` 自旋等待合并线程就绪。

### Downloader（`src/utils/Downloader.cpp`）

**职责：** 后台线程用 FFmpeg API 直接读取网络流写入文件，支持 DASH 分离流合并。不依赖 ffmpeg.exe CLI 工具。

**流程：**
1. `StreamExtractor::extract()` 获取流 URL（按画质高度筛选最佳格式）
2. `avformat_open_input()` 打开视频/音频流（注入 headers、代理、interrupt_callback）
3. 创建输出 `<title>.mp4.part` / `<title>.mkv.part` 临时文件（`avformat_alloc_output_context2()` + `avio_open()`）
4. 逐 packet 读取并写入（DASH 双流按 DTS 交织，单流直写）；每写一帧记录原始输入时间基下的最大 DTS（单位 1us）作为续传锚点
5. 通过码率估算总大小，定期回调进度
6. 写入循环结束（自然 EOF）后 `av_write_trailer` → `std::rename(.part → 最终文件)`

**临时文件 `.part`：** 下载中文件统一带 `.part` 后缀，明示"未完成"。`PartFileGuard` RAII 守卫绑定在 `downloadLoop` 栈上，析构时若未提交则 `std::remove(.part)`，覆盖所有异常路径（`openStream` 失败、`createOutputContext` 失败、`avformat_write_header` 失败、写循环失败、用户取消）。`downloadLoop` 入口处主动 `std::remove(partPath)` 清理上次进程崩溃留下的同名残留。仅 `std::rename` 成功后置 `keep=true` 跳过删除。

**自动重连 + seek 续传：** 写入循环是状态机，状态包括"正常读写 / 用户暂停 / 退避等待 / 连接未打开"：
- `av_read_frame` 返回非 EOF 错误（含 interrupt_callback 超时）→ 关闭输入 ctx，进入退避态
- 退避秒数 `computeBackoffSecs(retryCount) = min(2^(n-1), 30)`，1/2/4/8/16/30s 上限
- 退避到期后用 `reopenAndSeek()` 重开输入流：`avformat_open_input` + `avformat_seek_file(-1, lastDtsUs, AVSEEK_FLAG_BACKWARD)`，从最近关键帧续传
- 重开后设置 `skipUntilUs = lastDtsUs`，过滤掉关键帧到 lastDts 之间的重复包，避免重复写入
- DASH 任一路失败时两路一起重连（简化状态机），代价是少量重复读

**暂停/恢复：** 原子标志 `paused_`。检测到暂停时主动关闭 `videoCtx/audioCtx` 释放网络连接（不再像原先那样空转 sleep + 刷 deadline），避免长时间暂停被对端 RST 或缓冲溢出；恢复时走与"网络失败"相同的 `reopenAll()` 路径，从 lastDts 续传。

**取消：** 原子标志 `cancelled_`，interrupt_callback 返回 1 中断 `av_read_frame` 与 `avformat_open_input`；写循环退出后 `PartFileGuard` 析构自动删除 `.part`。

**回调：**
- `onProgress(float progress, string speed, string eta, string fileSize)`：每 0.5 秒触发；暂停/重连过渡态传 `progress = -1.0f` + `speed = "已暂停"/"重连中…"`，Controller 端 `p < 0` 时保留上次进度不更新
- `onFinish(bool ok, string path, string error)`：下载完成（path 为最终文件，已去掉 `.part`）或失败时触发

### VideoMerger（`src/utils/VideoMerger.cpp`）

**职责：** 后台线程用 libav* API 把多个本地视频片段按顺序裁剪合并为一个文件，输出到 `Config::recordDir`。不依赖 ffmpeg CLI。详见 `docs/视频合并技术方案.md`。

**片段模型：** 输入为 `vector<MergeClip>`（`path` + `startSec`/`endSec`，同一 path 可多次出现）。旧 `start(vector<string>)` 入口把每个路径转为「整段」片段后委托，保证基础合并不回退。`probeClip` 探测源时长并校验范围（`start>=0`、`end<=源时长`、`end-start>=0.1s`）。

**智能策略：** 探测所有片段后决策——
- 全部整段（`isFullClip`）且视频参数一致、音频全无或全一致 → **流拷贝 concat**（`runStreamCopy`）：以首片段参数建输出 Matroska 流，逐片段读包、按累计裁剪时长平移各流时间戳（保证 A/V 同步），零重编码、极速无损，输出 `.mkv`
- 否则（任一片段有截取，或参数不一致）→ **精确转码**（`runTranscode`/`transcodeClip`）：`avformat_seek_file`+`AVSEEK_FLAG_BACKWARD` 跳到入点前关键帧 → 丢弃入点前帧、出点截断 → `sws_scale` 缩放到首片段分辨率 → H.264 编码；音频按帧裁剪后 `swr_convert` 重采样 → `AVAudioFifo` 整帧送 AAC；视频 PTS = 片段内相对时间(`srcSec-startSec`)+时间轴偏移，换算到 1/90000，跨片段连续，输出 `.mp4`。任一片段无音频则丢弃音轨输出纯视频
- `totalDuration_` = 各片段「裁剪后」时长之和；进度按裁剪后时长推进

**FFmpeg 版本适配：** Windows 7.x（新 `ch_layout`）/ macOS 4.x（旧 `channels`），声道相关代码用 `LIBAVUTIL_VERSION_MAJOR>=57` / `LIBAVCODEC_VERSION_MAJOR>=59` 宏分支，与 `AudioDecoder.cpp` 一致。

**线程安全：** `state_`/`running_`/`cancelRequested_`/进度均为原子量，UI 线程每帧轮询；`error_`/`outputPath_` 用 `mutex_` 保护。`cancel()` 置标志，写出循环每轮检查后中止并删除半成品；析构 `join` 线程。

### VideoFramePreviewer（`src/utils/VideoFramePreviewer.cpp`）

**职责：** 异步单帧预览解码器，供 MergeScreen 拖动 IN/OUT 滑块时实时展示画面。不持有 GL 纹理、不调用 GL（纹理由 UI 线程上传）。

**线程模型：** worker 线程消费「最新一个」请求（拖动时旧请求被覆盖）：`avformat_seek_file` 跳到目标时间前关键帧 → 解码到目标附近首帧 → `sws_scale` 转 RGBA（等比缩到 ≤480×270）入完成队列。每次 `request` 带递增 `generation`，`poll` 只返回最新 generation 的帧、丢弃过期结果。

**防抖/缓存：** MergeScreen 端 100ms 防抖（窗口内暂存待发）；内部 48 帧 LRU 缓存，key=`path + round(ts*10)`（0.1s 粒度），来回拖动命中缓存免重复解码。`probeDuration` 静态方法供 UI 添加片段时取源时长（仅 open+find_stream_info，无解码）。

### MergeScreen（`src/ui/MergeScreen.cpp`）

**职责：** 多视频合并与片段截取界面，复用共享 UiContext 与皮肤 token 渲染。从 HomeScreen 的「MERGE VIDEOS」按钮进入（`HomeScreenResult::openMerge`），由 `main.cpp` 在 GUI 循环中独立运行，结束回 HomeScreen。

**状态机：** `Editing`（双栏：左栏片段列表 `renderClipList`——tinyfd 多选 / GLFW 拖放追加为新片段 / 行内拖拽调序 / 删除；右栏片段编辑 `renderClipEditor`——预览面板 + IN/OUT 滑块 + RESET RANGE / DUPLICATE）→ `Merging`（轮询 `VideoMerger::progress()` 进度条 + CANCEL）→ `Done`（成功提示 + 输出路径 + 转码/丢音轨提示）/ `Failed`（错误信息）。完成后停留界面，可「MERGE AGAIN」或「BACK」。UI 文案全英文。

**预览面板（`renderPreviewPanel`）：** 拖动滑块 → `requestPreview` 带防抖发请求；`pollPreview`（UI 线程每帧）取 RGBA 并上传/更新 OpenGL 纹理（`previewTex_` 存 GLuint）。IN 用青色（accentPrimary）描边、OUT 用紫色（accentSecondary）描边，左上角标 IN/OUT。每次添加片段用 `VideoFramePreviewer::probeDuration` 取源时长以启用滑块；时长未知时滑块禁用但仍可整段合并。

### Demuxer 扩展（`src/decoder/Demuxer.cpp`）

新增重载 `open(url, httpHeaders, knownDuration)`：
- `httpHeaders`：注入 `Referer`、`User-Agent` 等防盗链 headers（`av_dict_set(&opts, "headers", ...)`）
- `knownDuration`：pipe 流无法从容器头读取 duration，手动注入 `m_formatCtx->duration = knownDuration * AV_TIME_BASE`，避免被误判为直播流（否则 seek 和倍速会被禁用）

### Player 扩展（`src/core/Player.cpp`）

**`open()` 新增流程：**
1. `StreamExtractor::needsExtraction()` 检测
2. 若需要：`setState(EXTRACTING)` → `StreamExtractor::extract()` → 根据 `isDash` 决定走 DashMerger 还是直接 URL
3. 保存 `lastPageUrl_`（供画质切换和下载使用）

**`switchQuality(formatId, seekTime)`：**
1. `pause()` 暂停音频输出和 AVSync
2. 重新调用 `StreamExtractor::extract(lastPageUrl_, formatId + "+bestaudio/...")` 提取指定画质流
3. `shouldQuit_=true` + flush 队列解除解码线程阻塞 → `join()` 等待线程退出
4. 重置旧 DashMerger / Demuxer
5. DASH 流：以 `seekTime` 为 `startSeconds` 启动新 DashMerger（`-ss` 参数，避免在 pipe 上 seek）；非 DASH 流：直接用新 URL 打开 Demuxer 后 `demuxer_->seek()`
6. `initDecoders()` 用新流 codec 参数重新初始化解码器
7. `renderer_->setVideoSize()` 更新 OpenGL 纹理尺寸（分辨率可能变化）
8. `avSync_->seekTo(seekTime)` + `audioOutput_->resume()` + `avSync_->resume()` 恢复播放

**画质列表同步：** `render()` 每帧检测 `player_.getLastPageUrl()` 变化，URL 变化时从 `player_.getLastExtractedInfo()` 拉取 `qualities` 列表（`open()` 时 `controller_` 尚未注册，不能在 `open()` 内推送）。

### Controller 扩展（`src/ui/Controller.cpp`）

**画质按钮（`renderQualityButton`）：** 仅当 `currentQualityLabel_` 非空时显示（即当前播放内容来自网页 URL）。点击弹出画质列表，选择后调用 `player_.switchQuality()`。

**下载按钮（`renderDownloadButton`）：** 仅当 `currentPageUrl_` 非空时显示。点击弹出系统文件夹选择对话框，确认后启动 `Downloader`，底部显示蓝→紫渐变进度条。

**`currentPageUrl_` 同步：** 每帧 `render()` 开始时从 `player_.getLastPageUrl()` 读取，自动跟随播放内容变化。

### Cookie 与登录窗口

详见 `docs/网页视频播放技术方案.md` 中「登录 Cookie 支持」一节。
关键模块：

- `CookieStore`：维护 `<getAppDataDir()>/cookies/web_cookies.txt`，Netscape 格式，按 `(domain, path, name)` 合并去重，过期自动清理。
