# FluxPlayer 多视频合并与片段截取技术方案

## 一、需求概述

- 在主页面提供入口，用户可选择多个本地视频文件，按指定顺序合并为一个视频。
- 在合并前支持对每个素材片段设置截取范围：`startSec` / `endSec`。
- 支持从同一个文件或不同文件中选取任意片段参与合并，例如从 A 视频中间截取 10s~35s，再与 B 视频的 8s~72s 合并。
- 支持同一个源文件被添加多次，每次作为独立片段拥有不同的入点/出点。
- 调整截取点时实时展示所选画面，帮助用户准确定位入点/出点。
- 合并结果输出到录制目录（`Config::recordDir`，与录像/录音共用）。
- 支持文件多选、拖放添加、列表内拖拽调序、单项删除、范围重置、取消合并、合并进度展示。
- 不引入新的第三方依赖，沿用项目已链接的 FFmpeg libav* 库。

## 三、目标交互

### 1. 基础合并

用户只添加文件、不调整截取范围时，行为保持当前体验：

```
HomeScreen → MERGE VIDEOS → 添加文件 → 调序 → START MERGE → 输出文件
```

### 2. 任意片段截取合并

每次添加文件都会生成一个独立 `Clip`。`Clip` 是合并时间线上的基本单位，而不是“文件”本身：

```
A.mp4  [00:10.000 → 00:35.000]
B.mp4  [00:08.000 → 01:12.000]
C.mp4  [整段]
```

最终输出时间线为：

```
A 的 10s~35s  +  B 的 8s~72s  +  C 整段
```

如果用户希望从同一个文件中截取多个不连续片段，也可以把同一个文件添加多次：

```
A.mp4  [00:10.000 → 00:20.000]
A.mp4  [01:05.000 → 01:18.000]
B.mp4  [00:08.000 → 00:45.000]
```

最终输出：

```
A 的 10s~20s  +  A 的 65s~78s  +  B 的 8s~45s
```

### 3. AB 任意片段精确拼接

用户选择 A 文件对应的片段，分别拖动入点/出点滑块，从 A 中间截取任意一段；再选择 B 文件对应的片段，同样设置任意入点/出点。点击合并后输出：

```
A[startA, endA] + B[startB, endB]
```

例如：

```
A[00:20.000, 00:40.000] + B[01:10.000, 01:25.000]
```

这表示不是简单从 A 的某个位置一直取到结尾，也不是从 B 开头一直取到某个位置，而是 A、B 都可以各自只取中间任意一段。

如果用户只关心快捷场景“A 从中间开始，B 到中间结束”，也可以通过以下范围表达：

- A：`startSec = 用户选择位置`，`endSec = A.duration`
- B：`startSec = 0`，`endSec = 用户选择位置`

## 四、数据模型改造

### 1. 新增片段模型

`VideoMerger` 的输入应从 `vector<string>` 升级为 `vector<MergeClip>`。`MergeClip` 表示时间线上的一个片段，同一个 `path` 可以出现多次：

```cpp
struct MergeClip {
    std::string path;
    double startSec = 0.0;
    double endSec = -1.0;      // -1 表示到文件末尾
    double durationSec = 0.0;  // 探测后填充，供 UI 与校验使用
};
```

建议放在 `include/FluxPlayer/utils/VideoMerger.h`，因为 UI 和合并引擎都需要使用。为兼容现有调用，可保留旧接口：

```cpp
bool start(const std::vector<std::string>& inputs, const std::string& outputPath);
bool start(const std::vector<MergeClip>& clips, const std::string& outputPath);
```

旧接口内部转换为全段 `MergeClip`，保证当前基础合并功能不破。

### 2. 探测信息扩展

当前 `InputInfo` 记录路径、音视频参数和文件时长。需要扩展为：

```cpp
struct ClipInfo {
    MergeClip clip;
    bool ok = false;
    int vIdx = -1;
    int aIdx = -1;
    AVCodecID vCodec = AV_CODEC_ID_NONE;
    AVCodecID aCodec = AV_CODEC_ID_NONE;
    int width = 0;
    int height = 0;
    int pixFmt = -1;
    AVRational frameRate{25, 1};
    int sampleRate = 0;
    int channels = 0;
    int aSampleFmt = -1;
    double sourceDuration = 0.0;
    double startSec = 0.0;
    double endSec = 0.0;
    double clipDuration = 0.0;
};
```

校验规则：

- `startSec >= 0`
- `endSec <= sourceDuration`，`endSec < 0` 时视为 `sourceDuration`
- `endSec > startSec`
- `clipDuration = endSec - startSec`
- 同一个 `path` 的多个 `MergeClip` 独立校验、独立预览、独立参与合并。
- 总进度使用所有 `clipDuration` 之和，而不是源文件总时长。

## 五、合并策略变化

加入截取后，策略需要从“参数是否一致”升级为“参数是否一致 + 是否需要精确裁剪”。

```
所有片段都是整段
  且 所有视频/音频参数一致
            │
      ┌─────┴─────┐
     是           否
      │           │
   流拷贝      统一转码
  (.mkv)       (.mp4)

存在任意片段设置自定义 start/end
            │
      默认统一转码
      (.mp4，帧级准确)
```

原因：

- 流拷贝只能在包/关键帧边界附近截取，无法保证用户拖到哪一帧就从哪一帧开始。
- 用户要求“实时展示我选取的画面”，这隐含了输出边界应尽量和预览帧一致。
- 因此默认选择“精确模式”：只要有任意片段不是整段，就走解码/编码路径。

后续可以再提供“快速模式”：

- 允许关键帧误差。
- 对齐到最近关键帧后走流拷贝。
- UI 必须明确提示：“Fast trim may start/end near the selected frame, not exactly on it.”

## 六、转码裁剪实现

### 1. seek 到片段起点

`transcodeFile()` 改为处理 `ClipInfo`：

```cpp
bool transcodeClip(const ClipInfo& info,
                   TranscodeCtx& tc,
                   int targetW,
                   int targetH,
                   std::atomic<bool>& cancelFlag,
                   std::atomic<double>& processed,
                   double timelineBaseSec,
                   double& outConsumedSec,
                   std::string& err);
```

打开输入后执行 seek：

```cpp
int64_t seekTarget = (int64_t)(info.startSec * AV_TIME_BASE);
avformat_seek_file(in, -1, INT64_MIN, seekTarget, seekTarget, AVSEEK_FLAG_BACKWARD);
avcodec_flush_buffers(vDec);
if (aDec) avcodec_flush_buffers(aDec);
```

使用 `AVSEEK_FLAG_BACKWARD` 先跳到起点前的关键帧，然后继续解码，丢弃 `startSec` 之前的帧。

### 2. 视频裁剪

视频帧处理规则：

- 计算当前帧源时间 `srcSec`。
- `srcSec < startSec`：丢弃。
- `srcSec >= endSec`：停止读取本片段。
- 输出 PTS 使用片段内相对时间：

```cpp
double relSec = srcSec - info.startSec;
int64_t pts = (timelineBaseSec + relSec) * 90000;
```

这样 A/B/C 多段拼接时，输出时间轴连续，且每段都从 0 相对时间开始。

### 3. 音频裁剪

音频处理规则：

- 同样根据音频帧 `best_effort_timestamp` / `pts` 计算 `srcSec`。
- `srcSec + frameDuration <= startSec`：整帧丢弃。
- `srcSec >= endSec`：停止音频处理。
- 起点或终点落在一帧中间时，优先做简单整帧裁剪；后续可进一步做 sample-level trim。

建议分两期：

1. 第一阶段：音频按帧裁剪，误差通常在几十毫秒内。
2. 第二阶段：在 `swr_convert` 后按 sample 精确裁剪，保证音频边界与视频帧更贴合。

### 4. 进度计算

当前 `processedDuration_` 以文件实际处理时间推进。裁剪后改为：

```cpp
totalDuration = sum(clip.clipDuration);
processed = timelineBaseSec + min(currentSrcSec - startSec, clipDuration);
```

合并完成时强制 `processedDuration_ = totalDuration_`。

## 七、硬件加速架构

### 1. 设计目标

- **零拷贝流水线**：GPU 解码 → GPU 缩放 → GPU 编码，避免 GPU ↔ CPU 数据传输
- **跨平台抽象**：统一接口支持 Windows D3D11 和 macOS VideoToolbox
- **优雅降级**：硬件失败时自动回退到软件编解码，不中断任务
- **性能提升**：GPU 缩放比 libswscale 快 3-5 倍

### 2. 核心组件

#### HWAccelDevice（硬件设备管理）

**职责**：创建和管理硬件加速设备上下文，供编解码器共享

```cpp
class HWAccelDevice {
public:
    enum class Type { Auto, D3D11VA, VideoToolbox };
    static std::unique_ptr<HWAccelDevice> create(Type type = Type::Auto);
    
    bool isValid() const;
    AVBufferRef* avDeviceContext() const;  // 传给 AVCodecContext::hw_device_ctx
    void* nativeDevice() const;            // D3D11: ID3D11Device*
};
```

**实现要点**：
- Windows: 使用 `av_hwdevice_ctx_create(AV_HWDEVICE_TYPE_D3D11VA)`
- macOS: 使用 `av_hwdevice_ctx_create(AV_HWDEVICE_TYPE_VIDEOTOOLBOX)`
- 设备上下文生命周期与 HWAccelDevice 对象绑定（RAII）

#### 硬件编码器选择

**优先级**（`VideoMerger::selectHWEncoder()`）：
1. NVENC (`h264_nvenc`) - NVIDIA GPU
2. QSV (`h264_qsv`) - Intel 核显/独显
3. AMF (`h264_amf`) - AMD GPU
4. VideoToolbox (`h264_videotoolbox`) - macOS
5. 回退到软件 (`libx264`)

**探测逻辑**：
```cpp
const AVCodec* codec = avcodec_find_encoder_by_name("h264_nvenc");
if (codec && avcodec_open2(testCtx, codec, nullptr) == 0) {
    // 硬件可用
}
```

#### GPU 缩放

**Windows D3D11 VideoProcessor**：
```cpp
ID3D11VideoProcessor* processor;
ID3D11VideoProcessorInputView* inputView;
ID3D11VideoProcessorOutputView* outputView;

// 执行缩放
videoContext->VideoProcessorBlt(processor, outputView, 0, &stream);
```

**性能对比**：
- libswscale（CPU）：~15ms / 1080p 帧
- D3D11 VideoProcessor（GPU）：~3ms / 1080p 帧

**macOS**：使用 `VTPixelTransferSession`（已预留接口）

### 3. 分辨率策略

#### Unified 模式（统一分辨率）

- 所有片段缩放到相同分辨率
- 可选：使用首个 clip 分辨率或自定义分辨率
- 实现：创建一次编码器 + 硬件帧池，复用到最后

#### KeepOriginal 模式（保持原始）

- 每个片段保持原始分辨率
- 多阶段编码：检测到分辨率变化时重建编码器
- **GLOBAL_HEADER 处理**：
  - 阶段一：设置 `AV_CODEC_FLAG_GLOBAL_HEADER`，容器写入 extradata
  - 阶段二+：移除该标志，使用 in-band SPS/PPS（避免 extradata 冲突）

**重建触发条件**：
```cpp
if (frame->width != currentWidth || frame->height != currentHeight) {
    rebuildEncoder(frame->width, frame->height);
}
```

### 4. 硬件帧管理

**AVHWFramesContext**：
- 管理硬件帧池（texture 缓冲区）
- 绑定到编码器的 `hw_frames_ctx`
- 分辨率变化时必须重建

**帧传输流程**：
```cpp
// 解码得到硬件帧
AVFrame* hwFrame = ...;  // pix_fmt = AV_PIX_FMT_D3D11

// GPU 缩放
scaleOnGPU(hwFrame, scaledHwFrame, targetW, targetH);

// 直接送入硬件编码器
avcodec_send_frame(hwEncoder, scaledHwFrame);
```

### 5. 错误处理与回退

**三层容错**：
1. **设备创建失败** → 回退软件编解码
2. **编码器初始化失败** → 尝试下一个硬件编码器
3. **编码过程失败** → 任务标记为 Failed，显示错误信息

**日志示例**：
```
[INFO] Using NVENC hardware encoder
[WARN] NVENC initialization failed, trying QSV...
[INFO] Using QSV hardware encoder
```

## 八、流拷贝裁剪策略

第一阶段建议只在“全部整段合并”时保留流拷贝：

- 没有任何 clip 设置自定义 `startSec/endSec`
- 音视频参数一致
- 沿用当前 `runStreamCopy()`

第二阶段如果要支持快速裁剪流拷贝，可新增：

```cpp
bool runStreamCopyTrimmed(const std::vector<ClipInfo>& clips, ...);
```

但需要接受以下限制：

- 入点通常只能落在起点前最近关键帧。
- B 帧会导致 DTS/PTS 更复杂，需要重新归一化时间戳。
- 音频与视频边界可能不是同一时间点，需要额外处理 A/V offset。

因此默认不把它作为首版目标。首版以“准确”为先，速度慢一些但行为符合用户预期。

## 九、实时预览设计

### 1. 新增预览解码器

新增模块：

```
include/FluxPlayer/utils/VideoFramePreviewer.h
src/utils/VideoFramePreviewer.cpp
```

职责：

- 根据 `path + timestampSec` 解码单帧。
- 使用 `avformat_seek_file` seek 到目标时间前的关键帧。
- 解码到目标时间附近的第一帧。
- 用 `sws_scale` 转为 RGBA。
- 不持有 OpenGL 纹理，不直接调用 GL。

接口建议：

```cpp
struct PreviewFrame {
    std::string path;
    double timestampSec = 0.0;
    int width = 0;
    int height = 0;
    std::vector<uint8_t> rgba;
};

class VideoFramePreviewer {
public:
    bool request(const std::string& path, double timestampSec);
    bool poll(PreviewFrame& outFrame);
    void cancel();
};
```

### 2. 线程模型

预览解码不能阻塞 UI 线程：

- UI 滑块拖动时发起异步 request。
- worker 线程执行 FFmpeg seek + decode。
- 每次 request 带递增 `generation`。
- worker 完成后，如果 generation 已过期则丢弃结果。
- UI 线程 `poll()` 到 RGBA 后，再创建/更新 OpenGL texture。

注意：OpenGL texture 必须在 UI 线程创建或更新，因为 GL context 属于渲染线程。

### 3. 防抖与缓存

实时拖动时不能每个像素都解码一帧：

- 拖动中：80~120ms 防抖。
- 鼠标释放：立即请求一次最终帧。
- 缓存 key：`path + round(timestampSec * 10)`，即 0.1 秒粒度。
- 使用小型 LRU 缓存，例如 32~64 帧，避免来回拖动反复解码。

### 4. 预览质量

首版目标：

- 预览帧准确到目标时间附近。
- 入点/出点切换时明显标记：
  - `IN` 使用青色描边。
  - `OUT` 使用紫色描边。
- 预览区域展示：
  - 文件名
  - 当前时间码
  - 总时长
  - 是否仍在解码中

- `TRIM HEAD TO HERE`：等价于设置 start。
- `TRIM TAIL TO HERE`：等价于设置 end。
- `DUPLICATE CLIP`：复制当前片段后重新设置范围，用于从同一个源文件抽第二段。
- `SPLIT AT HERE`：把当前片段按预览时间拆成前后两个片段，作为第二阶段增强。

首版可以只做 `IN/OUT` 滑块，快捷按钮作为第二阶段增强。

## 十二、边界与错误处理

- 输入文件无法探测：该片段显示错误，禁止开始合并。
- 同一个文件被添加多次：允许，每个片段独立记录范围和顺序。
- 源时长未知：允许合并整段，但禁用精确 OUT 滑块；预览可按用户输入时间尝试 seek。
- 入点大于出点：UI 阻止，并显示错误。
- 片段短于最小长度：建议最小 `0.1s`。
- 预览解码失败：显示占位框和错误文案，不影响其他片段编辑。
- 合并中取消：沿用当前 `cancelRequested_`，删除半成品。
- 裁剪后无音频：沿用当前策略，任一输入无音频时转码输出纯视频；后续可补静音填充。
- 不同分辨率/帧率：沿用当前统一转码策略，输出分辨率以首个有效片段为目标。

## 十四、验收标准

### 基础功能
- 未设置裁剪范围时，当前多视频合并功能保持可用。
- 设置 A/B 片段后，输出只包含用户指定范围。
- 拖动入点/出点时 UI 不阻塞，预览画面能跟随更新。
- 合并进度按裁剪后的总时长计算，而不是源文件总时长。
- 自定义裁剪默认输出 `.mp4`，并走转码路径，保证边界尽量准确。
- 合并中取消会停止后台任务并删除半成品。
- 错误输入、无效范围、预览失败都有明确 UI 提示。

### 硬件加速
- Windows 系统优先使用 NVENC/QSV/AMF 硬件编码器。
- macOS 系统使用 VideoToolbox 硬件编码器。
- 硬件编码器不可用时自动回退到软件编码，不中断任务。
- 日志清晰显示使用的编码器类型（NVENC/QSV/libx264 等）。
- GPU 缩放（D3D11 VideoProcessor）在 Unified 模式下正常工作。
- KeepOriginal 模式下分辨率变化时正确重建编码器。

### UI 与交互
- 片段列表显示文件名、裁剪范围、分辨率、编码格式、文件大小。
- 删除按钮大小和样式符合 mockup 设计。
- 所有自定义控件（Radio、Checkbox、虚线按钮）正确渲染。
- 分辨率配置布局完全匹配 mockup（对齐、间距、边框）。
