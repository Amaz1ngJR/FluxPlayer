# FluxPlayer 多视频合并与片段截取

## 1. 使用入口

Home 的 MERGE VIDEOS 进入 MergeScreen。用户可多选或拖放本地文件，调整顺序、删除、复制片段，并设置每个片段的 IN/OUT。相同文件可重复加入，每个条目独立保存截取范围。界面由 Lua merge Surface 绘制，C++ 负责校验、预览和合并任务。

输出目录使用 `Config::recordDir`。VideoMerger 在后台执行，UI 查询状态和进度，取消通过原子标志传递。

## 2. 片段与选项

`MergeClip` 定义于 `include/FluxPlayer/utils/VideoMerger.h`：

- `path`：输入路径。
- `startSec`：入点，默认 0。
- `endSec`：出点，-1 表示到末尾。
- `durationSec`：探测所得源时长。

VideoMerger 同时提供路径列表和片段列表的 start 重载，路径列表转换为整段 MergeClip。运行中或参数非法时拒绝启动。

`MergeOptions` 提供：

- **Unified**：统一分辨率和 GOP，可使用首个片段参数或自定义宽高/GOP。
- **KeepOriginal**：保留各片段分辨率，中途按参数变化重建编码器。UI 提示该输出与部分第三方播放器存在兼容性限制。
- 视频编码：KeepSource、H.264、HEVC。
- 音频编码：KeepSource、AAC、PCM。
- 硬件加速开关，默认开启，初始化失败有软件回退路径。
- `maxParallelClips`：默认 2，上限 2；设为 1 可强制串行。仅 Unified 转码使用，是引擎选项，未新增 UI/INI 设置。

## 3. 合并管线

探测所有输入后决定流拷贝或转码：

- 全部整段且编码参数符合流拷贝条件时，逐包重写累计时间戳并合并，不重编码。
- 自定义截取、输入参数不一致或输出选项要求转换时，执行解码、处理和编码。

默认流拷贝输出 Matroska，转码使用所选编码和对应容器路径。默认混合输入转码为 H.264/AAC；PCM 音频使用 MOV 复用器。最终扩展名由实际策略校正，不仅由用户输入文件名决定。

转码裁剪先定位到入点附近，再按源时间戳丢弃范围外帧，输出时间轴从片段起点重新计时并叠加之前片段实际视频时长。音频保持相对视频的源偏移，执行前导采样丢弃、正偏移补静音和出点采样裁剪；各段共享输出音频 FIFO 与编码器。

转码模式下，只有所有输入都含音频才输出音轨；任一输入无音频时输出纯视频，并通过 `audioDropped()` 向 UI 提供提示，不填充静音音轨。

### 3.1 Unified 有限并行

仅多个片段、需要转码、且 `resolutionMode == Unified` 时默认启用。流拷贝与 KeepOriginal 保持原先的顺序处理策略。

```text
输入片段 -> 最多两个独立视频解码/缩放/编码任务 -> 编号临时 MP4（仅视频）
                                                        |
原素材音频 -> 顺序解码/重采样 -> 一个连续音频编码器        |
                                      |                 |
                                      +-> 单线程按顺序复用视频包 -> 最终输出
```

- 每个视频任务独占 FFmpeg 编解码上下文、硬件设备、帧池和缩放器。Windows 的 D3D11/VideoProcessor、NVENC/QSV/AMF 会话和 macOS 的 VideoToolbox 会话均不跨任务共用；只有 UI 硬件状态快照经过原有 mutex 发布。
- 目标宽高、视频编码格式、GOP 和编码器帧率提示统一从整次任务的设置/首片段确定，不能随单个 worker 的源文件改变。视频仍使用源 PTS，不补帧、不抽帧；码率、CRF 和质量预设不因并行而降低。每段独立起始关键帧，码流不承诺与串行输出逐字节一致。
- 软件编解码器设置每路 `thread_count` 请求上限，按逻辑 CPU 数的一半分配，范围 1–8；底层库自身线程池仍取决于具体编码器，不能把 C++ worker 数等同于设备总线程数。
- 临时视频只编码一次；最终视频包按累计实际视频时长平移 PTS/DTS，直接复用，不再次解码或编码。复用前检查编码参数、尺寸、色彩、SAR 和完整 extradata，写出时检查首包关键帧及跨段 DTS 单调性。不能安全拼接时不强行修改时间戳。
- 音频重新读取**原素材**，不经过分段 AAC 临时文件。最终仅一个音频编码器、一个 FIFO 和连续采样计数，避免分段有损编码与各段 encoder priming/padding 累积；原有 AAC/PCM/KeepSource 选择规则不变。PCM 交错采样偏移与 AAC 平面采样分别处理。
- 输出旁创建独占的 `.flux-merge-*` 临时目录，不使用硬链接。转码阶段最多两份在途编解码资源，但会保留全部已完成片段，临时磁盘占用约为完整输出视频大小；最终复用时临时文件与成品同时存在。正常完成、取消、可捕获的任务失败均在 worker join、文件关闭后清理；进程被强杀或断电不保证自动清理。
- Windows 文件系统边界使用 `u8path`，传给 FFmpeg 的路径使用 UTF-8 `u8string`；输出目录与临时文件包含中文、空格也应保持一致，不经本地 ANSI 代码页往返。
- 任一任务失败时停止继续领取片段，等待已启动 worker 退出并清理，再回退原串行转码。独立硬件会话受驱动限制、参数集不兼容、跨段 DTS 重叠等都不应直接产出损坏文件。用户取消不触发串行重试。
- 进度前 90% 按各 worker 已处理的媒体时长汇总，后 9% 为顺序音频与复用，完成收尾后才到 100%。回退串行会重置进度并记录原因，允许进度回退，不伪装为继续原任务。

并行不是固定倍率提速：硬件编码单元已经饱和、软件编码器自身已吃满 CPU、短片启动和额外磁盘读写，都可能使双路与单路持平或更慢。应以同素材完整任务计时判断，不能只比较解码 FPS。

## 4. 视频参数与硬件

Unified 按共同目标处理视频，KeepOriginal 按各段参数重建编码器。视频使用源帧真实 PTS 保持节奏，没有独立统一 FPS 输入。GOP 从源关键帧间隔探测，不可用时使用 250 帧回退值。

硬件编解码及 GPU 处理由 VideoMerger 与 HWAccelDevice 管理，软件回退属于该合并管线的行为。`HWAccelInfo` 分别发布硬件解码、硬件编码、零拷贝、设备与编码器名称；硬件开关本身不等同于零拷贝。

## 5. 单帧预览

VideoFramePreviewer 根据 path 和 timestampSec 在后台定位、解码并通过 swscale 转成 RGBA，结果交 UI 上传纹理；预览 Worker 不调用 OpenGL。

每次 request 带递增 generation，只保留最新挂起请求，过期完成结果被丢弃。小型 LRU 按路径与 0.1 秒粒度时间缓存，容量 48 帧；poll 非阻塞取出完成结果。cancel 丢弃挂起请求，不销毁工作线程。

## 6. 状态与资源

任务状态包括 Idle、Probing、Merging、Done、Failed、Cancelled。进度按已处理媒体时长与总时长估算，状态和进度使用原子量，错误字符串、输出路径和硬件快照由 mutex 保护。

输入探测、范围或编码失败通过 Failed 和错误字符串报告。取消停止后台处理并清理半成品；资源仅在使用线程退出后回收。

## 8. 并行回归验证

`tests/video_merger_parallel.cpp` 是独立驱动，使用真实 VideoMerger，不启动播放器 UI。`scripts/test_video_merger_parallel.py` 生成小型本地素材并检查：混合尺寸/帧率、非关键帧截取、H.264/HEVC、AAC/PCM、缺音轨、中文空格输出路径、视频包 DTS、完整解码、取消后无残留临时目录，以及流拷贝/KeepOriginal 不启用并行。AAC 解码后的 PCM 散列应与串行参考完全相同。

macOS 构建/运行（先完成 CMake Release 构建；依赖命令行 ffmpeg/ffprobe）：

```sh
rtk proxy clang++ -std=c++17 -O2 -Iinclude -Ithird_party/ffmpeg-macos/include \
  tests/video_merger_parallel.cpp \
  build/cmake/CMakeFiles/FluxPlayer.dir/src/utils/VideoMerger.cpp.o \
  build/cmake/CMakeFiles/FluxPlayer.dir/src/utils/HWAccelDevice.cpp.o \
  build/cmake/CMakeFiles/FluxPlayer.dir/src/utils/Logger.cpp.o \
  build/cmake/CMakeFiles/FluxPlayer.dir/src/utils/Config.cpp.o \
  -Lthird_party/ffmpeg-macos/lib -lavformat -lavcodec -lavutil -lswscale -lswresample \
  -framework VideoToolbox -framework CoreVideo -framework CoreMedia -framework CoreFoundation \
  -o /tmp/flux-merge-test
rtk proxy env DYLD_LIBRARY_PATH="$PWD/third_party/ffmpeg-macos/lib" \
  python3 scripts/test_video_merger_parallel.py /tmp/flux-merge-test --hardware --benchmark
```

`--hardware` 要求本机真实 GPU/硬件编解码访问；不传则只测软件路径。`--benchmark` 对四段 720p/30fps、每段截取 4.5 秒的任务交错执行单路/双路/双路/单路，检查总计 540 帧；输出端到端耗时，不将启动、探测、音频和复用排除在外。Windows 可用同一驱动和 Python 检查逻辑，但须使用 Windows 工具链及本项目 FFmpeg DLL 构建驱动，不可把 macOS 命令当作 Windows 构建说明。

2026-10-20 验证范围：macOS M3 的统一参数软件/VideoToolbox 路径通过上述功能回归；另用临时动态库注入首个视频编码器初始化失败，确认清理后串行重试成功。FFmpeg 7.x 头文件语法检查通过，但执行的是 macOS 条件编译分支，**不是 Windows SDK 构建或 Windows GPU 实测**。Windows 双会话资源限制、驱动回退和中文路径仍须在真实 Windows 环境验证。

本机 720p 四片段交错短测（同一轮共四次，不是长片统计）：

| 路径 | 单路两次耗时 | 双路两次耗时 |
| --- | --- | --- |
| 软件 H.264 | 2.428 / 3.929 秒 | 3.053 / 2.836 秒 |
| VideoToolbox H.264 | 2.158 / 2.750 秒 | 2.153 / 2.111 秒 |

四片段各 135 帧，成品均完整解码 540 帧，没有触发串行回退。硬件双路此次未变慢，但单路波动明显；软件数据重叠，**不能据此宣称稳定提速或两倍吞吐**。小分辨率/短片的软件案例还观察过双路稍慢，必要时使用 `maxParallelClips=1` 做同素材对照。

范围外的旧路径问题：混合尺寸 KeepOriginal 的编码器重建存在后写流风险；KeepOriginal 的 VideoToolbox 连续片段还复现过 `pts < dts`。本轮未重设计该路径，增加写出错误传播后会明确报错而非忽略错误宣布成功。回归只对同参数软件 KeepOriginal 检查未进入并行。FFmpeg 4.x 的串行 MP4 edit list 在混合帧率测试中还可能标记末帧为 discard，因此测试同时区分编码包数与实际解码帧数，不以串行末帧缺失作为新路径的正确性基线。
