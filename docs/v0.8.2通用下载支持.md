# v0.8.2 通用下载支持

## 1. 目标

v0.8.2 的目标是：**在协议、权限、加密方式和封装兼容性允许的前提下，播放器能够将支持的网络媒体保存到本地**。

“通用下载”表示统一覆盖播放器支持的常见网络媒体来源，不表示绕过 DRM、登录授权、付费限制或服务端防下载机制。以下来源明确不在本版本承诺范围内：

- Widevine / FairPlay / PlayReady 等 DRM 加密内容。
- 缺少合法 Cookie、Token、Referer 或账号权限的受限内容。
- FFmpeg / yt-dlp 当前版本无法读取的私有协议或站点。
- 必须转码且当前平台没有可用的硬件解码、硬件编码或兼容零拷贝链路的编码组合（用户关闭硬件加速时允许使用软件转码）。

这里的“网络媒体”不是只指 B 站 / YouTube 这类网页视频，而是覆盖通过 URL 打开的、且满足上述支持边界的媒体来源：

| 来源 | 示例 | v0.8.2 行为 |
|------|------|-------------|
| 网页视频 | Bilibili / YouTube / 抖音页面 URL | 通过 `yt-dlp` 提取真实流后下载 |
| HTTP/HTTPS 直链 VOD | `.mp4` / `.mkv` / `.flv` / `.ts` | 直接 remux 保存 |
| HLS / DASH 点播 | `.m3u8` / `.mpd`，可探测到有限 duration | 直接保存，显示百分比和 ETA |
| HLS / DASH 直播 | `.m3u8` / `.mpd`，duration 未知或无限 | 只能追随服务端新增分片，显示已保存时长 |
| 实时流协议 | `rtsp://` / `rtmp://` / `rtp://` | 先探测是否可 seek/可快拉；不可快拉才按实时保存 |

本地文件不显示 `Download` 入口。因为本地文件已经在磁盘上，下载按钮没有意义；后续若需要“另存为/转封装”，应作为单独的导出功能。

## 2. 设计原则

- **统一入口**：播放器控制栏只保留一个 `Download` 按钮。可完成内容是下载，真实直播是实时保存，但用户入口一致。
- **统一实现**：`Downloader` 负责所有网络来源，内部根据 source 类型走提取、直连、VOD、Live 分支。
- **不转码优先**：源编码与目标容器兼容时只 remux packet，避免 CPU 开销和画质损失；只有无法 remux 且产品允许时才进入转码。
- **硬件链路强约束**：开启硬件加速后，转码必须使用硬件解码、GPU 处理、硬件编码和经过验证的零拷贝硬件帧链路；任一环节不可用即明确失败，不允许无提示回退软件或 CPU 拷贝。
- **不中断播放**：下载/保存任务在后台线程执行，不影响当前播放管线。
- **状态清晰**：可快拉内容显示百分比、速度、大小、ETA；真实实时内容显示保存中、速度、大小、已保存时长。
- **取消语义分流**：可完成的下载取消后删除 `.part`；真实实时保存停止后保留已保存文件。
- **快拉优先**：只要服务端允许按客户端读取速度吐数据，就尽量快速下载；只有真正没有未来数据可取的直播才退化为实时保存。

## 4. Source 分类

新增统一分类，不建议只用 `duration < 0` 做全部判断。分类应先看 URL，再看提取/探测结果。

这里有三个正交概念，不能混在一起：

| 概念 | 问题 | 示例 |
|------|------|------|
| SourceKind | URL 是什么来源 | 网页、HTTP 直链、RTSP |
| ContentMode | 内容有没有自然完成点 | 点播可完成，真实直播不可完成 |
| TransferMode | 能不能按客户端速度快拉 | HTTP VOD/HLS VOD 可快拉；真实直播只能实时等 |

```cpp
enum class DownloadSourceKind {
    LocalFile,          // 本地文件，不显示 Download
    WebPage,            // 已确认需要 yt-dlp 提取的网页 URL
    HttpMedia,          // HTTP/HTTPS 媒体或 manifest
    RealtimeProtocol,   // RTSP/RTMP/RTP
    UnknownHttp         // 尚未确认是网页还是媒体的 HTTP/HTTPS URL
};

enum class DownloadMode {
    Unknown,            // 探测中，尚未确定取消语义
    VodDownload,        // 有完成点，显示百分比/ETA，取消删除 .part
    LiveSave            // 无完成点，显示已保存时长，停止后保留文件
};

enum class TransferMode {
    Unknown,            // 尚未确认服务端传输特征
    FastPull,           // 尽可能快地读取，服务端给多快就拉多快
    RealtimePull        // 服务端只实时产生数据，只能边播边保存
};
```

`SourceKind` 只描述来源形态，不携带 VOD/Live 结论；例如 `HttpMedia` 可以同时覆盖 HLS VOD 和 HLS Live，避免出现 `DirectVod + LiveSave` 这类自相矛盾的组合。

分类规则：

1. 非网络路径：`LocalFile`。
2. `rtsp://` / `rtmp://` / `rtp://`：标为 `RealtimeProtocol`，再结合 duration、demuxer 信息和有限的 seek 能力探测判断内容模式；协议名称本身不决定是否为 Live。
3. HTTP/HTTPS URL 先按以下顺序分类，不能把“无媒体扩展名”等同于网页：
   - Host 命中已知网页平台，或 URL 明确为普通 HTML 页面：`WebPage`，走 `yt-dlp`。
   - Path 命中已知媒体扩展名，或响应 `Content-Type` 为媒体/manifest：直接交给 FFmpeg。
   - 无法静态判断：先用 FFmpeg 低成本探测；打开成功且存在音视频流则视为直链，失败且符合网页特征时再回退 `yt-dlp`。
4. 网页经 `yt-dlp` 提取后，根据 `is_live`、`live_status`、manifest 类型和 duration 综合判断 `VodDownload` 或 `LiveSave`。
5. HTTP/HTTPS 直链经 FFmpeg 探测后统一标记为 `HttpMedia`，再独立确定模式：
   - manifest 明确为静态点播，或普通 HTTP 文件具备有限内容长度/可读至 EOF：`VodDownload`。
   - manifest 明确为动态直播：`LiveSave`。
   - 仅 duration 未知时保持 `Unknown` 探测态，不能立即按 Live 处理。

注意：`.m3u8` 和 `.mpd` 不能天然等同 Live，`duration > 0` 也不能单独证明可以快拉；duration 可能只是直播窗口长度，seek 成功也可能只代表能在滑动窗口内跳转。

## 5. 快拉与实时保存

“实时流协议”不等于“只能实时保存”。下载策略应优先判断服务端能否快拉：

| 类型 | 是否能快拉 | 说明 |
|------|------------|------|
| HTTP 文件 / progressive MP4 | 通常可以 | `av_read_frame` 会按网络和服务端速度尽快读取，不需要按播放速度等待 |
| HLS/DASH VOD | 通常可以 | playlist/manifest 中已有完整分片列表，可并行或连续快速拉取 |
| HLS/DASH Live | 不可以超过直播生产速度 | playlist 只有滑动窗口，新分片没生成前没有东西可下载 |
| RTSP Live 摄像头 | 通常不可以 | 服务端按实时 RTP 推包，客户端快读也读不到未来帧 |
| RTSP/RTMP VOD | 可能可以 | 如果服务端支持 seek/range/trickplay，可以作为 VOD 快拉；否则按实时保存 |

### 5.1 探测策略

`Downloader` 打开输入后应生成一个 `DownloadPlan`：

```cpp
struct DownloadPlan {
    DownloadSourceKind sourceKind;
    DownloadMode mode;
    TransferMode transferMode;
    bool seekable = false;
    double duration = 0.0;
    int64_t estimatedSize = 0;
};
```

判断规则按证据强度排序：

1. `is_live == true`、HLS 无 `#EXT-X-ENDLIST` 且持续刷新、或 DASH `type="dynamic"`：`LiveSave + RealtimePull`。
2. HLS 有 `#EXT-X-ENDLIST`、DASH `type="static"`、普通 HTTP 文件，或输入可稳定读到 EOF：`VodDownload + FastPull`。
3. `duration > 0` 只作为 VOD 的辅助证据，不直接决定 `FastPull`；直播滑动窗口也可能报告有限 duration。
4. RTSP/RTMP 的 seek 探测必须使用不会破坏正式下载上下文的独立连接，并验证 seek 后时间戳确实跳转；一次 API 返回成功不足以证明可快拉。
5. 对仍不确定的来源进入短暂 `Probing` 状态：采样 wall-clock 与媒体时间推进比率。媒体时间能持续显著快于墙钟推进才标记 `FastPull`；否则按 `LiveSave + RealtimePull`。探测期间收到的数据必须缓存或重新开流，不能静默丢失开头内容。
6. 分类结果允许在写入早期从 `Unknown` 收敛，但创建输出文件和 UI 展示前必须确定取消语义；无法可靠确定时采用更保守的 `LiveSave`，并明确提示“停止后保留文件”。

### 5.2 快拉实现要求

快拉模式不要人为按播放时钟 sleep。当前 `Downloader` 用 FFmpeg 读包写包，只要不加节流，HTTP VOD/HLS VOD 本身就会尽量快地读。

后续可以优化：

- HLS/DASH VOD 分片并发下载，再按顺序 remux。
- HTTP Range 并发下载，适用于普通 MP4 文件，但需要处理 moov/索引和容器拼接，第一版不做。
- 对服务端限速的源，UI 只展示实际速度，不承诺一定超过 1x。

### 5.3 实时保存的边界

真实 Live 没有“下载完”这个概念，因为未来数据还没产生。此时 `Download` 的实际语义是“保存当前开始之后收到的数据”，用户停止时封口成文件。

UI 文案可以保留按钮名 `Download`，但状态应显示 `LIVE SAVE` / `REC` / `已保存`，不要显示 ETA。

## 6. StreamExtractor 改造

### 6.1 直链快速路径

`StreamExtractor::extract()` 应在调用 `isAvailable()` 之前处理**已经确认的直链**，否则用户下载 `.mp4` / `.m3u8` / RTSP 时会被错误要求安装 `yt-dlp`。对于无扩展名且类型未知的 HTTP URL，不应仅凭 `needsExtraction()` 直接调用 `yt-dlp`，应由上层分类流程先做 FFmpeg/Content-Type 探测。

建议将接口职责拆清：

- `classifyUrlSyntax()`：仅做 scheme、host、path 扩展名等无网络分类，结果允许为 `UnknownHttp`。
- `probeDirectMedia()`：在下载线程中用 FFmpeg 探测是否存在音视频流。
- `extractWebPage()`：只处理已确认的网页来源并检查 `yt-dlp`。

若为已经确认的直链，可使用以下快速路径：

```cpp
if (!needsExtraction(pageUrl)) {
    out.videoUrl = pageUrl;
    out.audioUrl.clear();
    out.headers.clear();
    out.isDash = false;
    out.title = titleFromUrl(pageUrl);
    out.platform = "Direct";
    out.duration = 0.0;  // 未探测，后续由 Downloader 用 FFmpeg 补齐
    out.filesize = 0;
    return true;
}
```

`titleFromUrl()` 需要：

- 去掉 query / fragment。
- 从最后一个 path segment 提取文件名。
- URL decode 可后置，第一版至少保证文件名合法。
- 空路径回退到 `stream_YYYYMMDD_HHMMSS`。

### 6.2 网页视频补充字段

后续最好在 `ExtractedStream` 中增加：

```cpp
bool isLive = false;
std::string originalUrl;
```

`yt-dlp` JSON 中常见字段：

- `is_live`
- `live_status`
- `duration`
- `requested_formats`
- `protocol`

判断优先级：

1. `is_live == true` 或 `live_status == "is_live"`：`LiveSave + RealtimePull`。
2. `live_status` 明确为已结束直播，或 manifest 明确静态且有结束标记：按 VOD。
3. `duration > 0` 仅作为 VOD 辅助证据，还需排除动态 manifest 和直播状态。
4. `duration == 0` 且 protocol 为 HLS/DASH 也不能单独判 Live，应继续检查 manifest 或进入 `Unknown/Probing`。
5. 不确定时保持探测态；若仍无法确认则保守采用 `LiveSave`，保证用户停止时不会误删已保存数据。

## 7. Downloader 改造

### 7.1 任务模型

`Downloader::start()` 的参数名应从 `pageUrl` 改成 `sourceUrl`，表达它不再只服务网页 URL。

建议新增任务上下文：

```cpp
struct DownloadJob {
    std::string sourceUrl;
    std::string outputDir;
    std::string formatId;
    DownloadSourceKind sourceKind = DownloadSourceKind::UnknownHttp;
};
```

`DownloadJob` 只保存用户输入和语法级分类，`mode` / `transferMode` 必须由探测生成的 `DownloadPlan` 给出，避免在未探测时默认成 VOD/FastPull。`DownloadPlan` 在首次 UI 状态回调前确定，并传给 `runWriteLoop()`。

### 7.2 输入探测

流程应调整为：

```text
sourceUrl
  → classifyUrlSyntax()
  → if WebPage: extractWebPage()
  → if HttpMedia/RealtimeProtocol: probeDirectMedia()
  → if UnknownHttp: probeDirectMedia(), then conditionally fall back to extractWebPage()
  → open selected stream(s)
  → probe manifest / duration / seekability / transfer behavior
  → build immutable DownloadPlan
  → choose compatible output container
  → runWriteLoop(plan)
```

对直链 VOD，`Downloader` 不能只依赖 `ExtractedStream::duration`，而要在 `openStream()` 后读取：

- `AVFormatContext::duration`
- `bit_rate`
- stream metadata
- HLS/DASH manifest 的静态/动态属性和结束标记（必须在 P0 落地；若仅依赖 FFmpeg 暴露信息无法可靠判断，可对 manifest 做一次受限读取，但必须复用鉴权 headers、代理和超时配置）

### 7.3 输出文件、封装兼容与转码策略

处理策略按以下顺序固定：

1. `PacketRemux`：编码与容器兼容时直接复制 packet，不发生解码/编码，此时“硬解/硬编/零拷贝”均显示为 `BYPASS`。
2. `HardwareTranscode`：无法 remux 且硬件加速开启时，必须使用硬件解码 → GPU 格式/尺寸处理 → 硬件编码，并保持经过验证的零拷贝链路；否则在创建输出前失败。
3. `SoftwareTranscode`：仅当用户明确关闭硬件加速时允许使用；硬件加速已开启但硬件链路不可用时，默认失败并提示原因，不静默回退 CPU。

Remux 前必须先基于所有输入流的 `codecpar` 选择输出容器，不能只按 URL 后缀决定。若需要转码，应在创建输出文件前完成整条链路协商，避免运行中途才发现编码器或零拷贝不可用。

输出扩展名：

| 输入 | 推荐扩展名 | 说明 |
|------|------------|------|
| 单流 MP4/MOV/MKV/FLV/TS | 优先沿用源扩展名，否则 `.mp4` | 第一版可统一 `.mp4`，但 TS/FLV remux 到 MP4 可能遇到 codec tag 兼容问题 |
| DASH 分离音视频 | `.mkv` | 容器兼容性更宽 |
| RTSP/RTMP/HLS Live | `.mkv` 优先，`.mp4` 可选 | 实时保存中断时 MKV 更抗损坏；MP4 需要 trailer 才最完整 |

建议第一版策略：

```text
mode == LiveSave                         → 优先 .mkv
DASH 分离音视频或 MP4 不兼容的编码组合      → .mkv
源容器和编码均兼容 MP4 且为 VOD             → .mp4
无法可靠选择容器                            → 尝试 .mkv；仍失败则明确报错
```

最低兼容性验收至少覆盖 H.264/H.265 + AAC、VP9/AV1 + Opus、TS 中 AAC/MP3，以及含字幕/数据流的输入。默认只处理音视频流；附件、数据流和不兼容字幕是否保留必须记录日志，不能因一个非核心流导致整个任务无提示失败。

### 7.3.1 硬件转码与零拷贝约束

硬件加速开关复用项目现有配置语义，并尽量复用 `HWAccelDevice`、`VideoMerger::HWAccelInfo` 一类已有能力，但下载任务应拥有独立的转码上下文，不能复用播放中的 decoder/context。

平台目标链路：

| 平台 | 硬件解码 | GPU 帧/处理 | 硬件编码 | 零拷贝判定 |
|------|----------|-------------|----------|------------|
| Windows | D3D11VA / 对应硬件 decoder | D3D11 `AVHWFramesContext` | Media Foundation / QSV / NVENC（按已集成能力选择） | 解码输出到编码输入始终保持兼容的 D3D11 硬件帧，未经过 `av_hwframe_transfer_data()` 下载到 CPU |
| macOS | VideoToolbox | VideoToolbox/CVPixelBuffer 硬件帧 | VideoToolbox encoder | 同一兼容 CVPixelBuffer/硬件帧链路，无 CPU readback |
| Linux（后续支持时） | VAAPI / CUDA | 对应 `AVHWFramesContext` | VAAPI / NVENC / QSV | 同一设备或可验证的设备间映射，无 CPU readback |

实现约束：

- 硬件开启时，视频必须同时满足硬解、GPU 处理、硬编和零拷贝；任一端初始化失败或需要 CPU readback 时，任务在创建输出前进入 `Failed`，UI 显示具体失败阶段。若未来允许非零拷贝或软件回退，必须由独立配置和确认提示控制。
- “硬件解码”和“硬件编码”分别根据实际成功打开的 codec/context 上报，不能根据配置开关或编码器候选名称推断。
- 只有视频帧从 decoder 到 encoder 全程保留在硬件 `AVHWFramesContext`，且缩放/像素格式转换也在 GPU 完成时，`zeroCopy=true`；仅硬解后下载到 CPU、或 CPU 处理后再上传硬编，都必须显示 `Zero-copy: No`。
- decoder 与 encoder 的硬件像素格式、设备上下文、frame pool、分辨率和色彩参数必须在启动前协商；不兼容时明确报错。
- 音频没有通用的硬件加速要求，按流复制优先；必须转码时使用软件音频编码，并在 UI 中独立标明，不能影响“视频硬件/零拷贝”的判定。
- 转码会改变画质和码率，默认参数需在实现前单独列出 codec、profile、level、bitrate/quality、GOP 和 HDR/色彩元数据保留策略。

建议新增：

```cpp
enum class DownloadPipeline {
    PacketRemux,
    HardwareTranscode,
    SoftwareTranscode
};

struct DownloadAccelerationInfo {
    DownloadPipeline pipeline = DownloadPipeline::PacketRemux;
    bool hardwareRequested = false;
    bool hardwareDecoding = false;
    bool hardwareEncoding = false;
    bool zeroCopy = false;
    std::string deviceType;
    std::string decoderName;
    std::string encoderName;
    std::string zeroCopyReason;
};
```

`DownloadAccelerationInfo` 在管线协商后发布，若运行中因设备丢失导致链路变化，必须再次通知 UI；硬件开启策略下不得把状态悄悄改成软件。

### 7.4 `.part` 与取消语义

继续使用 `.part`，避免未完成文件被误认为完整。

| 模式 | 用户动作 | 行为 |
|------|----------|------|
| VOD 下载 | Cancel | 删除 `.part`，回调失败 `已取消` |
| VOD 下载 | EOF 完成 | 写 trailer，rename 为最终文件 |
| Live 保存 | Stop / Cancel | 写 trailer，rename 为最终文件，回调成功 `保存已停止，文件已保存` |
| Live 保存 | 写入失败 | 尽量写 trailer；能 rename 就保留，错误 toast 告知“已保留部分内容” |

UI 上建议 Live 模式按钮文案仍可用 `Cancel` 图标，但 tooltip/状态文案要表达“停止并保存”，不要让用户以为会删除。

### 7.5 进度回调语义

当前 `ProgressCallback(progress, speed, eta, fileSize)` 无法可靠表达探测、Live、重连和终态，同一字段在不同模式下复用也容易造成 UI 分支错误，因此 v0.8.2 将其替换为结构化回调，不使用 `-1/-2` sentinel。

建议接口：

```cpp
struct DownloadProgress {
    DownloadMode mode;
    TransferMode transferMode;
    DownloadState state;
    double progress = -1.0;
    int64_t bytesWritten = 0;
    int64_t totalBytes = 0;
    double speedBytesPerSec = 0.0;
    double etaSeconds = 0.0;
    double savedSeconds = 0.0;
    DownloadAccelerationInfo acceleration;
    std::string message;
};
```

v0.8.2 直接采用结构化回调，不再新增 sentinel 技术债。`DownloadState` 至少包含 `Probing / Downloading / LiveSaving / Paused / Reconnecting / Finalizing / Completed / Failed / Cancelled`；回调线程仍是下载线程，Controller 必须投递到 UI 线程或写入受同步保护的状态，禁止在回调中直接调用 ImGui。

### 7.6 暂停/恢复

现有暂停策略是关闭网络连接，恢复时重新打开输入；VOD 可尝试按时间戳恢复，但这不是严格意义上的字节级断点续传。

需要明确以下约束：

- VOD：重连后以关键帧为边界 seek 到 `lastMuxedDts - overlap`，丢弃已写入区间内的重复包，并保证每个输出流 DTS 单调递增；仅用单个全局 `lastDtsUs` 不足以处理音视频交错和不同 time base，应按输出流保存最后 DTS/PTS。
- 对 HLS/DASH，重新打开后分片边界和时间戳可能变化；如果无法证明连续，应中止并保留错误信息，不能生成表面成功但存在缺口的文件。
- HTTP progressive 下载本版本仍通过 demux/remux 恢复，不承诺 Range 字节级续传。
- Live：暂停意味着停止拉流；恢复只能从直播当前点继续，文件中会出现时间缺口，UI 应显示“已暂停，恢复后继续保存当前直播”。
- Live 模式下不得强行 seek 到旧时间戳，除非独立探测已确认这是可 seek 的 VOD。

验收时需用 ffprobe 检查完成文件的 DTS 单调性、总时长和音画同步，并加入下载中断后恢复的专项用例。

### 7.7 任务生命周期与线程安全

`Downloader` 当前由后台线程执行回调，v0.8.2 必须固定以下生命周期约束：

- 同一实例同时只允许一个任务；重复 `start()` 返回明确错误，不能静默忽略。
- `cancel()` 只负责请求取消和唤醒阻塞 I/O；线程退出、写 trailer 和 rename 在下载线程串行完成。
- 每个任务只能产生一次终态回调，终态为 `Completed / Failed / Cancelled` 之一；Live 用户停止属于 `Completed`，并附带“停止并保存”原因。
- 所有回调捕获的 Controller/Player 生命周期必须安全；关闭窗口时先取消并 join 下载线程，或通过共享任务状态投递事件。
- `running_` 必须在任何异常和提前返回路径上恢复，可使用 RAII；回调抛异常不得逃出下载线程。
- `cancel()` 与析构不能在下载线程自身调用 `join()`，否则会死锁；需要检测线程 ID 或统一由拥有者回收。

### 7.8 鉴权、代理与重定向

下载必须复用播放/提取阶段所需的请求上下文：

- 网页提取继续复用 CookieStore；yt-dlp 返回的 `http_headers` 传给 FFmpeg 的视频和音频输入。
- 直链需要支持用户已有的 Referer、User-Agent、Cookie、Authorization；若播放器当前未保存这些信息，本版本不承诺重新构造受限请求。
- 视频/音频双输入必须使用一致的代理和必要 headers，重连时也必须重新注入。
- HTTP 重定向后的最终 URL 仅在内存中使用，日志必须脱敏；不得覆盖用于重新提取的原始 URL。
- 超时需区分打开超时、读取空闲超时和用户取消，禁止把超时一律视为永久失败。

## 8. UI 改造

### 8.1 Download 按钮显示条件

当前注释是“仅网页视频时显示”，需要改成：

```text
当前播放源是网络 URL → 显示 Download
当前播放源是本地文件 → 不显示 Download
```

来源应该保存为：

```cpp
currentSourceUrl_      // 当前原始输入 URL，本地文件为空或不用于下载
currentSourceKind_     // LocalFile/WebPage/HttpMedia/RealtimeProtocol/UnknownHttp
```

不要把 `currentPageUrl_` 当作唯一来源。直链、RTSP、RTMP 不是 page URL，但也需要能下载/保存。

### 8.2 VOD 下载 UI

保持现有样式：

- `Download` 按钮。
- 百分比进度条。
- 暂停/继续。
- 取消。
- 速度 + 文件大小。
- `ETA`。

文案继续使用 `Download`，不要缩写成 `DL`。

### 8.3 Live 保存 UI

Live 模式不显示百分比，显示保存态：

```text
[Download]  LIVE SAVE  00:01:23  [Pause] [Stop]  3MiB/s  120MiB
```

如果为了复用现有布局，第一版可把进度条区域改成：

- 左侧红色/洋红色闪烁点。
- 中间文字 `LIVE SAVE 00:01:23` 或 `REC 00:01:23`。
- 不填充百分比。

取消按钮 tooltip 改为 `Stop and save` / `停止并保存`。

### 8.4 处理管线与硬件状态

下载状态区必须展示实际生效的处理管线，而不是只展示用户配置：

```text
REMUX             Decode: BYPASS            Encode: BYPASS             Zero-copy: N/A
TRANSCODE / HW    Decode: HW (h264_mf)      Encode: HW (h264_mf)       Zero-copy: YES
TRANSCODE / SW    Decode: SW (...)          Encode: SW (...)           Zero-copy: NO
```

UI 要求：

- `Probing` 阶段显示 `Pipeline: Detecting...`，不得提前显示 HW/Zero-copy。
- Remux 明确显示 `BYPASS` 和 `Zero-copy: N/A`，因为它不产生像素帧，不能误标为零拷贝转码。
- 转码分别显示 `Decode: HW/SW`、`Encode: HW/SW`、设备/codec 名称及 `Zero-copy: YES/NO/UNAVAILABLE`。
- 软件转码显示 `Zero-copy: NO`；硬件模式只能在验证完整链路后显示 `YES`，不可用时显示 `UNAVAILABLE`、简短原因并终止任务，例如 `pixel format conversion requires CPU`、`device mismatch`。
- 硬件已开启但无法建立硬解 + GPU 处理 + 硬编 + 零拷贝完整链路时，状态切到 `Failed` 并提供“关闭硬件加速后重试”的操作建议；不在后台静默改成软件或非零拷贝链路。
- 窄窗口可折叠为 `HW DEC / HW ENC / ZERO-COPY` 三个 badge，点击或悬停显示完整详情；移动端/小窗口不能截断关键状态。

### 8.5 完成提示

FinishCallback 后应显示 toast 或状态文本：

| 模式 | 成功文案 | 失败文案 |
|------|----------|----------|
| VOD | `Download complete: <filename>` | `Download failed: <reason>` |
| Live | `Live save complete: <filename>` | `Live save stopped, partial file kept: <filename>` |

`Finalizing`（写 trailer、关闭文件、rename）期间按钮应禁用并显示“正在完成保存”，避免用户重复 Stop。只有最终 rename 成功后才能提示完成；若 trailer 成功但 rename 失败，应保留 `.part` 路径并提示用户，不得报告成功。

## 9. 播放流程接入

主流程要记录原始来源，而不是只记录 yt-dlp 提取后的临时流地址。

正确数据流：

```text
HomeScreen URL input
  → main/playMediaShared(mediaPath)
  → Player::open(mediaPath)
  → StreamExtractor/Demuxer 内部解析
  → Controller 获取 original source URL
  → Downloader 使用 original source URL
```

原因：

- yt-dlp 提取出的 URL 往往带 token，会过期。
- DASH merger pipe 不是可下载的原始来源。
- 直链/RTSP 需要保留用户输入的原始 URL。

建议 `Player` 暴露：

```cpp
std::string getCurrentSourceUrl() const;
bool isCurrentSourceNetwork() const;
```

并逐步替代 `getLastPageUrl()` 在下载场景里的使用。

## 10. 错误处理

| 场景 | 行为 |
|------|------|
| `yt-dlp` 不存在 | 只影响网页视频下载；直链/RTSP 不应失败 |
| `yt-dlp` 提取失败 | 显示错误，不创建 `.part` |
| 直链打开失败 | 显示 `无法打开网络流` |
| 写入失败 | 关闭上下文；VOD 删除 `.part`，Live 尽量保留部分文件 |
| 网络中断 | 进入重连态，显示 `重连中...`，指数退避 |
| 用户取消 VOD | 删除 `.part` |
| 用户停止 Live | 写 trailer 并保存 |
| 文件名冲突 | 追加序号，禁止默认覆盖已有文件；最终 rename 也必须使用不覆盖语义 |
| DRM/加密不受支持 | 在创建输出前失败，提示“不支持受 DRM 保护的内容” |
| 容器/编码不兼容 | 优先尝试兼容容器；仍需转码时按硬件配置建立转码链路，失败则明确提示 |
| 硬件解码初始化失败 | 硬件开启时终止任务，显示 decoder、设备和 FFmpeg 错误；建议关闭硬件后重试 |
| 硬件编码初始化失败 | 硬件开启时终止任务，显示 encoder、设备和 FFmpeg 错误；不得静默软件编码 |
| 零拷贝不可用 | 硬件开启时在创建输出前失败，UI 显示 `Zero-copy: UNAVAILABLE` 和原因，并建议关闭硬件后改用软件转码；不得继续运行并误报硬件全链路 |
| GPU 设备丢失 | 终止并尽量保留可播放部分，禁止运行中无提示切换 CPU |
| HTTP 鉴权信息 | 播放器已有 headers/Cookie 时复用；日志和 UI 中必须脱敏 |

### 11.1 入口覆盖

| 用例 | 预期 |
|------|------|
| 本地 MP4 | 不显示 `Download` |
| B 站页面 URL | 显示 `Download`，点击后走 yt-dlp |

### 11.2 行为验证

- VOD 下载中取消：`.part` 被删除。
- VOD 下载完成：最终文件存在且可播放。
- HTTP VOD：下载速度可以高于播放码率，不按播放速度节流。
- HLS/DASH VOD：尽可能快拉已有分片，完成后保存。
- Live 保存 30 秒后停止：最终文件存在且可播放。
- Live 保存中暂停 10 秒再恢复：文件继续增长，但不承诺补回暂停期间内容。
- 网络断开：UI 显示重连中；恢复网络后继续。
- 代理开启：网页提取和 FFmpeg 打开直链都使用配置代理。
- Cookie 命中：网页视频下载复用 CookieStore。

### 11.3 日志验收

下载开始时至少记录（URL 必须先脱敏）：

```text
sourceKind=WebPage/HttpMedia/RealtimeProtocol/UnknownHttp
mode=Unknown/VodDownload/LiveSave
transferMode=Unknown/FastPull/RealtimePull
url=<redacted source url: remove userinfo and sensitive query values>
output=<path>
duration=<seconds or unknown>
filesize=<bytes or unknown>
```

首次进度回调记录：

```text
state=<Probing/Downloading/LiveSaving/Paused/Reconnecting/Finalizing/...>
progress=<0..1 for known VOD, otherwise unavailable>
bytesWritten=<n>
totalSize=<n or unknown>
speed=<bytes/s>
saved=<seconds for live>
pipeline=<PacketRemux/HardwareTranscode/SoftwareTranscode>
hardwareRequested=<true/false>

```

日志脱敏规则：

- 删除 URL 中的 `userinfo`，并将 `token`、`auth`、`key`、`signature`、`sig`、`expires`、`cookie` 等 query 值替换为 `<redacted>`。
- 禁止记录完整 `Cookie`、`Authorization`、代理账号密码和 yt-dlp 返回的临时签名 URL。
- 错误日志若包含 FFmpeg 原始 URL，也必须经过同一脱敏函数。

### 11.4 兼容性与安全验收

- 无扩展名媒体直链：FFmpeg 探测成功，不调用 yt-dlp。
- 普通 HTML 页面：直链探测失败后回退 yt-dlp，不创建无效 `.part`。
- DRM/加密源：明确拒绝，不尝试绕过保护。
- 带 Token/Cookie 的源：能够下载，日志中不出现凭据明文。
- 文件名已存在：生成 `(1)` 等新文件名，不覆盖原文件。
- MP4 不兼容编码：选择 MKV；若仍需转码，则按硬件开关建立明确的转码管线，不生成不可播放文件。
- 硬件开启且需要转码：实际使用硬件 decoder 和硬件 encoder，UI 与日志名称和 FFmpeg 实际 context 一致。
- 硬件 decoder 成功、encoder 失败（反向亦然）：任务明确失败且不静默回退软件。
- 真零拷贝链路：无 `av_hwframe_transfer_data()` CPU readback，UI 显示 `Zero-copy: YES`。
- 硬解/硬编但中间需 CPU filter：硬件模式在启动前失败，UI 显示 `Zero-copy: UNAVAILABLE` 及原因；关闭硬件后可改用软件转码。
- 用户关闭硬件后转码：允许软件 decoder/encoder，UI 显示 `TRANSCODE / SW`。
- Remux：UI 显示 Decode/Encode `BYPASS` 与 `Zero-copy: N/A`，不初始化编码器。
- VOD 中断恢复：ffprobe 无 non-monotonous DTS，音画同步和时长符合预期。
- Live 停止和异常断网：可保留的文件均能被 ffprobe 打开。
- 下载线程销毁、取消和重连并发执行时无死锁、重复回调或 use-after-free。

## 13. 非目标

v0.8.2 不做：

- 本地文件“另存为”。
- 转码下载作为独立用户功能（本版本只在源流无法兼容 remux 输出时自动进入转码；不提供分辨率、码率、codec 等手动转码选项）。
- 下载队列 / 多任务并发（单任务生命周期和重复启动错误处理仍属于本版本）。
- 硬件开启时使用 CPU/GPU 混合链路或非零拷贝转码；只有经过实际验证的全硬件帧零拷贝链路才允许运行并显示 `Zero-copy: YES`。
- 严格字节级断点续传；本版本仅提供尽力而为的按时间戳重连恢复。
- 绕过 DRM、付费限制或未授权访问。
- 为容器兼容之外的目的自动转码。
