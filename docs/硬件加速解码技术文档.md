## 为什么需要硬件解码

### 软件解码的瓶颈

视频解码是计算密集型任务。以 4K H.265 视频为例：

```
4K 分辨率 = 3840 × 2160 = 829 万像素/帧
30fps = 每秒 30 帧
每秒需要处理 ≈ 2.5 亿像素的解码运算
```

纯 CPU 软件解码时，这些运算全部由 CPU 通用计算单元完成，会导致：
- CPU 占用率飙升（4K H.265 可达 80%+）
- 笔记本发热严重、风扇狂转
- 其他应用响应变慢
- 移动设备电池快速消耗

### 硬件解码的优势

现代 GPU 内置了专用的视频解码引擎（固定功能硬件），专门为视频解码设计：

```
CPU 软件解码：通用计算单元 → 灵活但效率低
GPU 硬件解码：专用解码引擎 → 功能固定但效率极高
```

硬件解码的好处：
- **CPU 占用率大幅降低**（从 80% 降到 5% 以下）
- **功耗更低**（专用硬件比通用计算省电得多）
- **解码速度更快**（专用电路的吞吐量远超 CPU）

## CPU 解码 vs GPU 解码

### 数据流对比

```
【CPU 软件解码】
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ 压缩数据  │ →  │ CPU 解码  │ →  │ CPU 转换  │ →  │ GPU 渲染  │
│ (H.264)  │    │ (libavcodec)│   │(sws_scale)│    │ (OpenGL) │
└──────────┘    └──────────┘    └──────────┘    └──────────┘
                  ↑ CPU 密集      ↑ CPU 密集      ↑ GPU
                  占用高           额外拷贝         轻松

【GPU 硬件解码】
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ 压缩数据  │ →  │ GPU 解码  │ →  │ GPU 互操作 │ →  │ GPU 渲染  │
│ (H.264)  │    │(D3D11/VT) │   │ 无 CPU 帧  │    │ (OpenGL) │
└──────────┘    └──────────┘    └──────────┘    └──────────┘
                  ↑ GPU 专用       ↑ 原生 surface    ↑ GPU
                  CPU 几乎空闲     不下载像素         直接采样
```

### 关键区别

| 维度 | CPU 软件解码 | GPU 硬件解码 |
|------|-------------|-------------|
| 解码执行者 | CPU 通用计算单元 | GPU 专用解码引擎 |
| CPU 占用 | 高（50-100%） | 极低（<5%） |
| 输出格式 | 通常 YUV420P | 通常 NV12 |
| 兼容性 | 支持所有编解码器 | 仅支持常见编解码器 |
| 像素传输 | CPU→GPU 纹理上传 | 原生 GPU surface 互操作，不经过 CPU |

## 各平台硬件解码方案

### macOS: VideoToolbox

```
Apple 的官方多媒体框架，macOS / iOS 通用
├── 支持编解码器：H.264, HEVC(H.265), VP9, ProRes
├── FFmpeg 设备类型：AV_HWDEVICE_TYPE_VIDEOTOOLBOX
├── 输出像素格式：AV_PIX_FMT_VIDEOTOOLBOX（IOSurface-backed CVPixelBuffer）
├── 底层实现：Apple Silicon 的专用媒体引擎 / Intel Mac 的 Quick Sync
└── 特点：macOS 上唯一的硬件解码方案，无替代品
```

### Windows: D3D11VA

```
D3D11VA（当前唯一启用的 Windows 硬件后端）
├── 适用于支持 DirectX 11 视频解码的 Intel/AMD/NVIDIA GPU
├── FFmpeg 设备类型：AV_HWDEVICE_TYPE_D3D11VA
├── 输出像素格式：AV_PIX_FMT_D3D11
├── 互操作：D3D11 Video Processor + WGL_NV_DX_interop2
└── 特点：解码、色彩转换和 OpenGL 导入全部留在 GPU
```

CUDA/NVDEC 与 DXVA2 虽然可以完成硬件解码，但当前 OpenGL 渲染器没有对应的原生
互操作实现。若启用它们就必须调用 `av_hwframe_transfer_data()` 下载像素，因此严格
零 CPU 拷贝模式不把它们列入候选；D3D11VA 不可用时直接回退软件解码。

### 当前选择策略

```
macOS:   VideoToolbox（唯一选择）
Windows: D3D11VA；互操作不可用时回退软件解码
Linux:   暂不支持（可扩展 VAAPI）
```

FluxPlayer 的实现方式是定义一个候选列表，循环尝试 `av_hwdevice_ctx_create()`，
第一个成功的就用。这种设计的好处是：
- 新增平台只需往列表里加一项
- 自动适配用户的 GPU 硬件
- 失败自动降级，无需用户干预

## FFmpeg 硬件加速 API 详解

### 核心 API 调用流程

```
┌─────────────────────────────────────────────────────────────┐
│                    FFmpeg 硬件加速流程                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. av_hwdevice_ctx_create()     创建硬件设备上下文           │
│         ↓                                                   │
│  2. codecCtx->hw_device_ctx =    绑定到解码器上下文           │
│         av_buffer_ref(hwDeviceCtx)                          │
│         ↓                                                   │
│  3. avcodec_open2()              打开解码器（FFmpeg 自动       │
│         ↓                        协商硬件格式）               │
│  4. avcodec_send_packet()        发送压缩数据（与软件解码相同） │
│         ↓                                                   │
│  5. avcodec_receive_frame()      接收解码帧                   │
│         ↓                        ⚠ 帧在 GPU 内存中！         │
│  6. av_frame_ref()               保留原生 GPU surface 引用    │
│         ↓                                                   │
│  7. 平台互操作层导入 OpenGL，不读取 CPU 像素                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 1. av_hwdevice_ctx_create() — 创建硬件设备

```c
int av_hwdevice_ctx_create(
    AVBufferRef **device_ctx,    // [输出] 硬件设备上下文
    enum AVHWDeviceType type,    // 设备类型（如 AV_HWDEVICE_TYPE_VIDEOTOOLBOX）
    const char *device,          // 设备标识（通常传 NULL，使用默认设备）
    AVDictionary *opts,          // 额外选项（通常传 NULL）
    int flags                    // 标志位（通常传 0）
);
// 返回值：0 = 成功，负数 = 失败
```

这个函数做了什么：
- 检测系统是否有对应的硬件解码能力
- 初始化硬件设备（打开 GPU 驱动、分配设备资源）
- 返回一个 `AVBufferRef*`，内部包含设备句柄

如果系统没有对应的 GPU 或驱动不支持，这个函数会返回错误码，
此时我们可以尝试下一个候选方案或回退到软件解码。

### 2. hw_device_ctx 绑定 — 告诉解码器使用硬件

```c
// 将硬件设备上下文绑定到解码器
codecCtx->hw_device_ctx = av_buffer_ref(hwDeviceCtx);
```

`av_buffer_ref()` 增加引用计数（不是拷贝），这样解码器和我们各持有一个引用。
绑定后，`avcodec_open2()` 会自动检测该设备支持哪些编解码器，
并在可能的情况下使用硬件解码路径。

### 3. av_hwframe_transfer_data() — 本项目硬件路径禁止使用

```c
int av_hwframe_transfer_data(
    AVFrame *dst,    // [输出] CPU 端帧（格式由 FFmpeg 自动选择，通常 NV12）
    AVFrame *src,    // [输入] GPU 端帧（格式为 AV_PIX_FMT_VIDEOTOOLBOX 等）
    int flags        // 标志位（通常传 0）
);
```

该 API 会把解码结果从 GPU 下载到 CPU，随后 OpenGL 还要再次上传纹理。它适合离线
CPU 滤镜、软件编码等必须读取像素的场景，但不是硬件播放的必经步骤。

FluxPlayer 的硬件播放路径明确禁止调用它。硬件 `AVFrame` 通过 `av_frame_ref()` 保留，
由 `HardwareFrameInterop` 在渲染线程直接导入；平台互操作不可用时，解码器在 worker
启动前重建为软件模式，而不是隐藏地执行 GPU→CPU→GPU 往返。

### 引用计数与内存管理

```
AVBufferRef 引用计数机制：

av_hwdevice_ctx_create(&ctx)  →  ctx 引用计数 = 1
av_buffer_ref(ctx)            →  ctx 引用计数 = 2（解码器持有一份）
av_buffer_unref(&ctx)         →  ctx 引用计数 = 1（我们释放，解码器还在用）
avcodec_free_context()        →  ctx 引用计数 = 0（解码器释放，设备真正销毁）
```

## NV12 像素格式深度解析

### 为什么硬件解码器输出 NV12 而不是 YUV420P？

两者都是 YUV 4:2:0 采样（色度分辨率为亮度的 1/4），区别在于**内存布局**：

```
【YUV420P — 平面存储（Planar）】
三个独立的内存平面，U 和 V 分开存储：

Y 平面（全分辨率）：
┌────────────────────┐
│ Y00 Y01 Y02 Y03 ...│  width × height 字节
│ Y10 Y11 Y12 Y13 ...│
│ ...                 │
└────────────────────┘

U 平面（1/4 分辨率）：
┌──────────┐
│ U00 U01 ..│  width/2 × height/2 字节
│ U10 U11 ..│
└──────────┘

V 平面（1/4 分辨率）：
┌──────────┐
│ V00 V01 ..│  width/2 × height/2 字节
│ V10 V11 ..│
└──────────┘

总内存：width × height × 1.5 字节
data[0] = Y, data[1] = U, data[2] = V


【NV12 — 半平面存储（Semi-Planar）】
两个内存平面，U 和 V 交错存储：

Y 平面（全分辨率）：
┌────────────────────┐
│ Y00 Y01 Y02 Y03 ...│  width × height 字节
│ Y10 Y11 Y12 Y13 ...│
│ ...                 │
└────────────────────┘

UV 交错平面（1/2 分辨率）：
┌──────────────────────┐
│ U00 V00 U01 V01 ...  │  width × height/2 字节
│ U10 V10 U11 V11 ...  │  （每个像素 2 字节：U + V）
└──────────────────────┘

总内存：width × height × 1.5 字节（与 YUV420P 相同）
data[0] = Y, data[1] = UV 交错
```

### NV12 对硬件更友好的原因

1. **缓存局部性**：U 和 V 交错存储，访问一个像素的色度信息只需一次内存读取
2. **DMA 效率**：两个平面比三个平面需要更少的 DMA 传输操作
3. **GPU 纹理映射**：NV12 的 UV 平面可以直接映射为 GL_RG8 纹理（双通道）

这就是为什么所有主流硬件解码器（VideoToolbox、NVDEC、D3D11VA）都输出 NV12。

## 零拷贝渲染技术

### “零拷贝”的准确边界

```
【旧路径：存在 CPU 往返】
GPU 解码 → av_hwframe_transfer_data → CPU(NV12) → sws_scale → CPU(YUV420P) → glTexSubImage2D → GPU

【当前路径：零 CPU 像素拷贝】
GPU 解码 surface → 平台 GPU 互操作 → OpenGL texture → 显示
```

这里只把“视频像素不经过 CPU”称为零 CPU 拷贝。`av_frame_ref()` 的引用计数操作、
GPU 内部的 `CopyResource`、framebuffer blit 和纹理采样都不会把像素映射到主存，
因此不破坏这个定义。软件帧调用 `glTexSubImage2D()` 属于 CPU→GPU 上传，不能称为
端到端零拷贝。

### Windows：D3D11VA → WGL/OpenGL

```text
FFmpeg AV_PIX_FMT_D3D11 texture array slice
    -> ID3D11VideoProcessorInputView
    -> VideoProcessorBlt（GPU 内 YUV/P010 -> BGRA）
    -> 专用 D3D11 输出纹理
    -> CopyResource 到隔离的 WGL 互操作纹理
    -> WGL_NV_DX_interop2 注册为 OpenGL renderbuffer
    -> framebuffer blit 到普通 OpenGL texture
    -> RGBA shader
```

使用独立互操作纹理是稳定性要求。部分驱动若直接把 Video Processor 输出注册给 WGL，
会出现黑屏，并可能在注销共享资源时崩溃。`CopyResource` 完全在 GPU 内执行；WGL
lock/unlock 负责 D3D11 与 OpenGL 之间的访问同步。

### macOS：VideoToolbox → IOSurface/CGL

```text
FFmpeg AV_PIX_FMT_VIDEOTOOLBOX
    -> IOSurface-backed CVPixelBuffer
    -> CGLTexImageIOSurface2D 映射 Y plane
    -> CGLTexImageIOSurface2D 映射 UV plane
    -> sampler2DRect shader 完成 NV12/P010 -> RGB
```

渲染器使用两个纹理槽轮换，并用 OpenGL fence 延迟释放 `AVFrame` 引用，保证
VideoToolbox 不会在 GPU 采样完成前复用对应 IOSurface。整个过程不调用
`CVPixelBufferLockBaseAddress()`，也不读取 plane 的 CPU 地址。

### 软件解码路径

软件解码输出 YUV420P/NV12 CPU frame 时仍使用普通 OpenGL 纹理上传。YUV420P 可直接
引用进入队列，其他 CPU 像素格式才通过 `sws_scale` 转换。该路径保证兼容性，但不会在
状态面板中标记为硬件或零拷贝。

截图属于显式 CPU 消费场景。当前版本尚未实现从最终 GPU 输出纹理按需 readback，
因此 PNG/JPEG/YUV/NV12 截图会拒绝硬件 `AVFrame` 并记录 WARN，避免把 D3D11 texture
或 CVPixelBuffer 句柄误当作 CPU plane。后续 readback 只在用户触发截图时执行，不影响
正常逐帧播放的零 CPU 拷贝定义。

### 内存优化汇总

| 优化项 | 技术 | 效果 |
|--------|------|------|
| 保留硬件 surface | `av_frame_ref` | 队列只增加引用，不复制 GPU 像素 |
| 禁止硬件帧下载 | 不调用 `av_hwframe_transfer_data` | 消除 GPU→CPU→GPU 往返 |
| Windows 隔离互操作对象 | GPU `CopyResource` | 避免视频引擎输出直接共享造成驱动崩溃 |
| macOS 双槽与 fence | 延迟释放 IOSurface 引用 | 避免每帧 `glFinish` 和 surface 过早复用 |
| 格式变化检测 | `m_lastSwsFormat` 守卫 | 避免 SwsContext 格式不匹配导致崩溃 |

## FluxPlayer 实现细节

### 完整数据流

```
【硬件路径】
AVPacket
    -> avcodec_receive_frame()
    -> D3D11 texture / VideoToolbox CVPixelBuffer
    -> av_frame_ref() 保留 GPU surface 入队
    -> HardwareFrameInterop::beginFrame()
    -> WGL 共享资源 / IOSurface CGL texture
    -> OpenGL 渲染
    -> endFrame() 同步并保留可重绘画面

【软件回退】
AVPacket
    -> avcodec_receive_frame()
    -> CPU YUV420P/NV12
    -> av_frame_ref() 入队
    -> glTexSubImage2D()
    -> OpenGL shader
```

### 关键代码位置

| 功能 | 文件 | 方法 |
|------|------|------|
| 硬件设备初始化 | `src/decoder/VideoDecoder.cpp` | `initHWAccel()` |
| 硬件像素格式协商 | `src/decoder/VideoDecoder.cpp` | `getHWFormat()` |
| 硬件 surface 引用入队 | `src/decoder/VideoDecoder.cpp` | `prepareFrame()` |
| 平台互操作接口 | `include/FluxPlayer/renderer/HardwareFrameInterop.h` | `HardwareFrameInterop` |
| D3D11/WGL 与 IOSurface/CGL 实现 | `src/renderer/HardwareFrameInterop.cpp` | `beginFrame()` / `endFrame()` |
| 硬件/软件帧分发 | `src/renderer/GLRenderer.cpp` | `renderFrame(const AVFrame*)` |
| 硬件链路统计 | `src/core/Player.cpp` | `getStats()` |
| `S` 状态面板 | `src/ui/Controller.cpp` | `renderStats()` |
| 配置开关 | `src/utils/Config.cpp` | `hwaccel` 字段 |

### 状态面板诊断

按 `S` 可直接确认实际生效路径：

```text
Decoder   : HARDWARE
Backend   : D3D11VA
Device    : NVIDIA GeForce ...
Zero-copy : ACTIVE
Path      : D3D11 Video Processor -> GPU Copy -> WGL/GL
```

`Decoder` 和 `Zero-copy` 依据当前缓存画面的真实来源生成，不只检查 `hwaccel=true`。
Windows 的 `Device` 从当前 D3D11 device 对应的 DXGI adapter 读取；macOS 从当前
CGL 上下文读取 `GL_RENDERER`，可区分 Apple Silicon、Intel 核显和 AMD 独显。
软件降级后显示 `Software / CPU / INACTIVE`。

## 降级策略设计

### 多层降级保障

```
层级 1：配置文件控制
  hwaccel=false → 完全跳过硬件初始化，纯软件解码

层级 2：硬件设备初始化失败
  av_hwdevice_ctx_create() 返回错误
  → 当前平台硬件后端不可用
  → 自动回退软件解码
  → 日志输出警告，用户无感知

层级 3：原生互操作初始化失败
  WGL_NV_DX_interop2 / IOSurface/CGL 不可用
  → 在 demux/decode worker 启动前重建软件解码器
  → 不保留硬解码后执行逐帧下载

层级 4：运行时 surface 导入失败
  beginFrame() 返回 false
  → 当前帧不推进 lastRenderedPTS
  → 日志明确记录互操作错误
  → 绝不隐藏调用 av_hwframe_transfer_data()

层级 5：编解码器不支持硬件
  例如播放 VP8 格式（硬件不支持）
  → FFmpeg 自动使用软件解码路径
  → 输出 YUV420P 格式
  → prepareFrame() 引用 CPU 帧并上传 OpenGL
  → 完全透明，无需特殊处理
```

### 设计原则

1. **失败不崩溃**：所有硬件相关操作的失败都有明确的回退路径
2. **状态可观察**：自动降级不打断播放，并可通过日志与 `S` 面板确认实际路径
3. **最小影响范围**：硬件初始化失败只影响 VideoDecoder，不影响其他模块
4. **可配置**：用户可以通过 `hwaccel=false` 强制使用软件解码（调试用）

## FFmpeg 封装兼容补丁

macOS 项目依赖为 `third_party/ffmpeg-macos/`。本次基于官方 FFmpeg 4.4.6 重编 `libavformat.58.76.100.dylib`，保留原有 `libavcodec.58.134.100.dylib` 和其他同 ABI 核心库，不减少软解码、VideoToolbox 或输入协议能力。容器不识别某种编码时，单纯增加解码器或切换硬件加速无法解决，需要在封装解析层处理。

补丁文件为 `scripts/ffmpeg/patches/ffmpeg-4.4.6-flv-compat.patch`，支持范围如下：

| 封装 | 编码 | 范围 |
| --- | --- | --- |
| 标准 FLV | H.264 / AAC 等 | 保持原有读写行为 |
| 私有扩展 FLV | H.265 codec-id 12 | 读取与写入 hvcC、NAL 数据、CTS 和结束标签 |
| 私有扩展 FLV | 原始 Opus codec-id 13 | 读取与写入 48 kHz 单/双声道，不携带 OpusHead / pre-skip / 多声道映射 |
| Enhanced FLV v1 | `hvc1` H.265 | 读取 SequenceStart、CodedFrames、CodedFramesX |
| Enhanced FLV v1 | `av01` AV1 / `vp09` VP9 | 读取配置与编码帧；AV1 适配旧版解码器的配置 OBU 输入 |

HTTP-FLV 和 RTMP 使用同一 FLV 解复用器，因此可复用这套读取兼容性。Enhanced FLV 写入、多轨扩展、增强音频头与其他私有标签不在此次承诺范围内。私有 Opus codec-id 13 与 Enhanced RTMP 的 Opus 头是两种不同封装。

补丁修正了 HEVC 的包长度、Annex-B 转换、PTS 校验和 EOS 编码标记；扩展头按 FourCC 识别，关键帧判断去除扩展位，读取前检查标签长度，未知包与结束包不会送入视频解码器。重复序列头通过 `AV_PKT_DATA_NEW_EXTRADATA` 传播。AV1 配置剥离 av1C 固定头，并在关键帧前补充配置 OBU，以便 FFmpeg 4 的 libdav1d 使用只在配置标签内发送的序列头。

### Windows 旧式 HEVC FLV 补丁

Windows 项目头文件与 `avutil-59.dll` 的版本标识均为 `n7.1.3-43-g5a1f107b4c-20260331`。上游 FFmpeg 7.1 原生支持 Enhanced FLV FourCC `hvc1`，但不将旧式 codec-id 12 映射为 HEVC。这是封装格式与版本的差异，不能由操作系统或 HEVC 解码器存在与否推断兼容性。

补丁 `scripts/ffmpeg/patches/ffmpeg-7.1-legacy-hevc.patch` 针对官方提交 `5a1f107b4c78318f318897900acad1b6c6aa3f9d`，只修改 `flv.h` / `flvdec.c`：识别 codec-id 12，消费旧式 packet-type 与三字节有符号 CTS，复用 hvcC / 重复配置处理，跳过结束与未知包，并校验标签内的头长度。保留上游 Enhanced FLV 行为，不扩展旧式 HEVC 写入或私有 Opus codec-id 13。

在原 Windows FFmpeg 发行构建环境（完整依赖与工具链）中执行：

```bash
# 源码必须处于匹配提交且无未提交修改；建议使用独立工作树。
# 此命令会修改指定源码的两个 FLV 文件，复用已有构建配置。
bash scripts/ffmpeg/build_ffmpeg_windows.sh \
  --source-dir /path/to/ffmpeg --build-dir /path/to/configured-build --jobs 8
# 已应用补丁后的重复编译：
make -C /path/to/configured-build -j 8 libavformat/avformat-61.dll
```

构建脚本只生成候选 DLL，不自动替换项目库，也不负责安装或重建原发行版的完整依赖环境。不能用仅启用 HEVC/FLV 的裁剪构建替换项目库，否则会损失其他容器、协议能力。保持同版本 ABI、原解码库与硬件后端；若新增外部 DLL 依赖，必须一并审计与携带。

**Windows 验证入口统一为 Python，C 文件是内部解码探针，不需要手工编译。** 在 x64 VS Developer Command Prompt 中，从项目根目录运行（Python 仅使用标准库）：

```bat
python scripts\ffmpeg\verify_ffmpeg_windows.py --avformat-dll C:\ffbuild\libavformat\avformat-61.dll

rem 可显式指定同一码流的 legacy / Enhanced 测试素材：
python scripts\ffmpeg\verify_ffmpeg_windows.py --avformat-dll C:\ffbuild\libavformat\avformat-61.dll --legacy C:\fixtures\legacy-hevc-no-b.flv --enhanced C:\fixtures\enhanced-hevc-x.flv
```

默认素材为 `build/ffmpeg-flv-tests/legacy-hevc.flv` 与 `enhanced-hevc.flv`，可复制 macOS 验证脚本生成的素材；Windows 入口不调用系统 FFmpeg 生成素材。`--ffmpeg-dir` 可指定包含 `include/lib/bin` 的项目依赖目录。

Python 使用项目头文件和导入库编译 `verify_ffmpeg_windows.c`，在独占临时目录放入项目 DLL 副本与候选 `avformat-61.dll`，限制子进程 PATH，再执行探针。探针核对 avformat/avcodec/avutil 确实从 EXE 同目录加载、DLL 版本与头文件一致，实际解码后比较帧时间戳及像素摘要；零帧、解码失败或不一致均失败。验证完成后清理临时目录，不修改项目 DLL。该回归不替代原有协议/容器能力对照、D3D11VA 或真实 HTTP-FLV/RTMP 播放验证。

当前仅在 macOS 将匹配源码打补丁后完成原生回归：legacy/Enhanced HEVC（含 B 帧与 CodedFramesX）各解码 12 帧，时间戳及像素摘要一致；Windows DLL 尚未实际构建、替换或运行。上游依据：[匹配提交的 flvdec.c](https://github.com/FFmpeg/FFmpeg/blob/5a1f107b4c78318f318897900acad1b6c6aa3f9d/libavformat/flvdec.c)。

### macOS 重建与验证

相关文件统一放在 `scripts/ffmpeg/`：`build_ffmpeg_macos.sh` 负责构建补丁库，`bundle_ffmpeg_macos.py` 负责收集与发布依赖，`verify_ffmpeg_macos.py` 负责解码回归验证，`patches/` 存放补丁。以下命令均在项目根目录执行。

```bash
# 默认下载并校验官方 4.4.6 源码，应用项目补丁后更新项目依赖
bash scripts/ffmpeg/build_ffmpeg_macos.sh

# 也可离线导出已有 Git 仓库的官方 n4.4.6 标签，不修改原仓库
bash scripts/ffmpeg/build_ffmpeg_macos.sh --source-dir /path/to/ffmpeg --jobs 8

# 更新运行目录，避免继续加载上次构建复制的动态库
xmake -r
# 或 cmake --build build/cmake --clean-first --parallel

# 生成短测试码流，并明确加载项目动态库做实际解码验证
python3 scripts/ffmpeg/verify_ffmpeg_macos.py
```

官方源码 SHA-256 固定为 `2290461f467c08ab801731ed412d8e724a5511d6c33173654bd9c1d2e25d0617`。传输依赖保留 GnuTLS、SRT、RIST、ZeroMQ、libbluray，XML 封装沿用 macOS SDK 的系统 libxml2。

收集脚本解析完整依赖、改写 `@loader_path`、签名并检查闭包，全部成功后才替换项目依赖目录，并生成 `third_party/ffmpeg-macos/build-info.json`，记录源码版本、补丁路径及发布库 SHA-256。当该文件包含补丁记录时，直接收集原始 Homebrew 库会被拒绝，防止无意覆盖；删除该记录文件会失去此项保护。构建中间产物位于 `build/ffmpeg-macos-patched/`，验证素材位于 `build/ffmpeg-flv-tests/`，不会写入脚本目录。macOS 打包脚本直接复制项目依赖，因此发布产物会包含补丁。

已验证 H.264/AAC、H.265 MP4、legacy/Enhanced H.265 画面与时间戳一致、CodedFramesX、AV1、VP9、单/双声道 Opus、AV1 配置独立起播、重复配置、未知 FourCC 和截断头；输入容器与协议集合未减少。另外通过播放器自身 `Demuxer` / `VideoDecoder` 验证两种 H.265 FLV 均输出 12 帧 VideoToolbox 硬件帧。该结果不替代真实 HTTP-FLV/RTMP 服务端联调，Windows 的不同版本 FFmpeg 二进制此次未更新。
