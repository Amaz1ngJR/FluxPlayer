# v0.8.0 高倍数播放技术方案

## 1. 目标

v0.8.0 支持最高 `16x` 高倍数播放。核心目标不是“尽量渲染更多帧”，而是让媒体时间按用户选择的倍速稳定前进，同时让画面以可承受的采样密度跟随主时钟。

必须保证：

- 有音频输出时，始终使用音频时钟作为主时钟。
- 视频不主动改主时钟，只按主时钟判断 early / late。
- 高倍速下允许丢弃已经解码但过期的视频帧，只显示追到主时钟附近的帧。
- UI 进度条读取主时钟，不能在视频渲染 PTS 和音频媒体时间之间跳变。
- UI 倍速选项根据硬件性能和当前视频分辨率自动裁剪；硬件只建议到 4x 时，不显示 8x/16x。
- 无音频视频才退回外部时钟。

## 2. 主时钟策略

主流播放器的常规模型是 audio master：音频设备是持续输出的时间源，视频根据音频时间决定显示、等待或丢帧。FluxPlayer 也采用这个模型。

```text
有音频输出：
    master = AClock
    AClock 由成功提交的有效 PCM 覆盖区间和排队延迟估计更新
    视频帧：PTS <= master 时可显示；明显落后 master 时丢弃

无音频输出：
    master = ExternalClock
    ExternalClock 按 playbackRate 推进
```

高倍速不能因为 `rate >= 2.0` 切到 `EXTERNAL_CLOCK`。否则会出现两个时间源同时影响播放：外部钟驱动视频调度，音频钟又通过回调和进度条推进媒体时间，最终表现为画面接近 1x、进度条在两个时间之间来回跳。

## 3. 硬件能力、启动实测与 UI 裁剪

可选倍速分两级控制：

- `HardwareInfo::startBenchmarkAsync()` 在主界面启动时后台执行一次真实解码测速。
- `HardwareInfo::estimatePerformance()` 测速完成后优先返回实测能力，测速中/失败时返回静态估算。
- `HardwareInfo::maxSupportedPlaybackSpeed(width, height)` 根据当前视频分辨率返回 UI 应展示、核心应允许的最高倍速。

启动测速使用内置样片 `source/video/video_01.mp4`，发布版安装到 `resources/video/video_01.mp4`。测速路径走真实播放管线中的 `Demuxer + VideoDecoder + prepareFrame`，统计在限定墙钟时间内完成的解码帧数，并按样片像素量折算为 1080p 等效吞吐：

```text
sampleSpeed = decodedFrames / fps / elapsedSeconds
measured1080pSpeed = sampleSpeed * (sampleWidth * sampleHeight) / (1920 * 1080)
sustainableSpeed = measured1080pSpeed * 0.70
```

映射到 `1x / 2x / 4x / 8x / 16x` 档位。这里保留 30% 安全余量，避免首页把极限吞吐误报成稳定可播放倍速。

测速未完成时，主界面硬件能力区显示“实测中”，不直接展示 16x 等可能误导的上限。测速完成后，主界面和倍速裁剪都使用实测结果。

静态兜底规则：

| 硬件档位 | 1080p 上限 | 4K 上限 |
|----------|------------|---------|
| 旗舰，例如 Apple M3/M4、D3D11VA/CUDA 高性能设备 | 16x | 8x |
| 高性能，例如 Apple M1/M2、VAAPI/QSV | 8x | 4x |
| 中等，例如 Intel Mac | 4x | 2x |
| 基础/软件解码 | 2x | 1x |

播放页速度菜单按当前视频宽高裁剪；设置页默认倍速没有具体视频上下文，按 1080p 档裁剪。`Player::setPlaybackSpeedInternal()` 也会做核心层 clamp，防止配置文件绕过 UI 上限。

## 4. 视频抽帧策略

高倍速的关键限制是显示器刷新率和渲染循环频率。例如 30fps 视频在 16x 下，媒体时间每秒会跨过约 480 个视频帧；即使显示器是 144Hz，也无法逐帧显示。

因此视频线程必须做两类丢帧：

- **主时钟追赶丢帧**：如果帧 PTS 已明显落后 `masterClock`，直接消费并丢弃显示。
- **固定间隔抽帧**：本地文件 + 硬件加速 + `rate >= 2.0` 时，按 `floor(rate)` 做采样，例如 16x 大约每 16 帧保留 1 帧。

渲染循环不能每次只消费一帧。一次 VSync tick 内最多批量消费一批已到时的帧，并始终保留最后一个作为本轮渲染候选。这样既能追上音频主时钟，也避免浅队列被丢空后只复用缓存画面。

视频读取通过 `peekRef(frame, token)` 获取独立引用与元素身份；根据主时钟选取到时帧，再调用 `consume(token)` 校验并推进。过期凭证不修改队列，渲染使用已持有的独立引用。

注意：I 帧对解码有依赖意义，但帧已经解码进入 frame queue 后，丢弃显示不会破坏后续帧解码。因此“明显落后主时钟”的 I 帧也可以不显示。

## 5. 音频处理

高倍速保留音频输出。`FrameQueue::renderAudio()` 按速率推进采样相位，并跨回调保存相位；回调只复制有效 S16，欠载尾部补静音。

设备提交成功后登记有效媒体覆盖与排队延迟估计，AVSync 仅在有效区间内插值。设备内仍有有效覆盖时继续推进，覆盖耗尽后冻结；所有倍率下都不按静音输出时长合成 AClock。视频保持音频主时钟，不因欠载切换为外部钟。

修改速率不清空队列、不触发内部 Seek；已提交 PCM 保留生成时的媒体跨度，新速率只作用于新生成的输出。普通暂停保留覆盖并平移恢复锚点，Seek 清缓存后重建。

## 6. UI 进度

普通本地视频过去使用 `lastRenderedPTS_` 作为进度来源。高倍速下这会导致进度条被视频渲染采样率限制，出现 1x 和高倍速主时钟之间跳动。

新策略：

- 有音频输出：进度条读取 `AClock`。
- 无音频实时流：读取 `ExternalClock`。
- 无音频高倍速视频：读取当前 master clock。
- 其它普通无音频视频：可继续使用 `lastRenderedPTS_`。
- 有限时长媒体的显示时间必须 clamp 到 `[0, duration]`；进度条比例也必须 clamp 到 `[0, 1]`。

## 7. 代码位置

- `src/core/Player.cpp`
  - `open()`：有音频时设置 `AUDIO_CLOCK`，不再按高倍速强切外部钟。
  - `renderVideoFrame()`：按音频主时钟批量抽掉过期视频帧。
  - `audioOutputCallback()`：生成有效 PCM 与覆盖数组，欠载尾部补静音，不合成时钟进度。
  - `getCurrentTime()`：有音频输出时返回 AClock。
  - `getCurrentTime()` / 时钟更新路径：有限时长媒体按 duration 封顶。
  - `setPlaybackSpeedInternal()`：保留音频队列和已提交覆盖，切速不触发内部 Seek。
  - `setPlaybackSpeedInternal()`：根据 `HardwareInfo::maxSupportedPlaybackSpeed()` clamp 最高倍速。
  - `shouldDropFrameForSpeed()`：本地硬件解码高倍速下做固定间隔抽帧。
- `src/core/DecodeWorker.cpp`
  - 视频帧入队前统一夹紧为单调 PTS，避免 VClock 在高倍速下被异常回退帧拉回。
- `include/FluxPlayer/core/Player.h`
  - `playbackRate_` 注释更新为支持 16x。
  - `frameRenderCounter_` 用于高倍速固定间隔抽帧。
- `include/FluxPlayer/utils/HardwareInfo.h` / `src/utils/HardwareInfo.cpp`
  - 统一提供启动真实解码测速、硬件性能估算兜底和分辨率相关最高倍速。
- `src/ui/Controller.cpp`
  - 播放页速度菜单按当前视频分辨率裁剪。
  - 设置页默认倍速按 1080p 硬件上限裁剪。
- `src/ui/HomeScreen.cpp`
  - 初始化时启动后台 benchmark。
  - 硬件能力区显示“实测中 / 已实测吞吐 / 静态估算”状态。
- `CMakeLists.txt`
  - 安装 `source/video/video_01.mp4` 到发布版 `resources/video/`，保证启动测速素材可用。

## 8. 当前行为

速率能力和视频抽帧策略以源码为准：音频输出存在时保持音频主时钟，音频覆盖耗尽后冻结；无音频时使用外部时钟。设备排队延迟采用估计值，音频输出不足时不会用静音合成媒体时间。
