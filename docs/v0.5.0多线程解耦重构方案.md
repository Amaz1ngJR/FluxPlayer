# FluxPlayer 多线程解耦重构方案

> 目标：将「读包 + 解视频 + 解音频」单线程串行模型，重构为 ffplay 式
> 「demux 线程 + 独立 video/audio 解码线程 + PacketQueue」解耦模型，
> 根治视频帧队列满导致音频饿死的结构性死锁。

---

## 一、问题背景

### 1.1 故障现象

播放某个 mp4 文件时画面卡住不动，日志特征：

```
VClock: 0.080000s | AClock: 0.100000s   ← 两个时钟都冻结
VQueue: 4 | AQueue: 0                    ← 视频队列满、音频队列空，长期固定
Underruns: 491 (持续累加)                ← 音频欠载不断增长
Dropped: 0 | FPS: 32                     ← 渲染循环空转
```

### 1.2 根因：单解码线程自锁（deadlock）

当前线程模型（`src/core/Player.cpp`）：

| 线程 | 职责 | 关键代码 |
|------|------|---------|
| **解码线程** `decodingThread()` | `readPacket` → `sendPacket`(video+audio) → `receiveFrame` → 归一化 PTS → 入 `FrameQueue` | `Player::decodingThread()` |
| **主线程** `run()` | 消费 `videoQueue_` 渲染（GLFW context 亲和，必须主线程） | `Player::run()` / `renderVideoFrame()` |
| **平台音频线程** | `audioOutputCallback()` 消费 `audioQueue_` | `Player::audioOutputCallback()` |

死锁闭环：

1. 解码线程**优先** receive 视频帧，队列满走慢速路径
   `videoQueue_->peekWritable()`，这是 `FrameQueue` 内部的
   `notFull_.wait()` **无限阻塞**。
2. 解码线程卡死在视频入队，**再也走不到下面 receive 音频、读音频包的代码**。
3. `audioQueue_` 永远是空（`AQueue: 0`）→ 音频输出欠载 → **音频主时钟停止推进**。
   若 `AVSync::getAudioClock()` 已做实时插值，也只能在最后一次音频回调后短暂外推，
   到达保护上限后仍会停止，不能从根上解除闭环。
4. 渲染线程 `renderVideoFrame` 用主时钟决定取帧
   （`nextPTS <= masterClock + 0.005`），主时钟不动 →
   不取帧 → `videoQueue_` 永远满（`VQueue: 4`）。
5. 回到第 1 步，闭环锁死。

### 1.3 为什么偏偏这个文件触发

故障文件是 `mov/mp4`，moov 的交织顺序导致**视频包密集在前、音频包靠后**。
HW(cuda) 解码起播时视频帧突发涌出，**在读到第一个音频包之前**就把容量仅 4 的
视频队列灌满，解码线程立刻卡死，音频一帧都没解出来。交织良好的文件里音视频包
交替到达，视频满之前音频已有数据、时钟能推进，所以不卡——这是单线程模型的**固有缺陷**，
不是参数没调好。

## 二、主流播放器的做法（参考依据）

ffplay / mpv / VLC **都不会**出现这个死锁，因为它们把 demux 与各路 decode **解耦到独立线程**：

```
ffplay:
read_thread   → 只 av_read_frame，按流分发进 videoq / audioq / subtitleq (PacketQueue)
video_thread  → 只从 videoq 取包解码 → 视频 FrameQueue
audio_thread  → 只从 audioq 取包解码 → 音频 FrameQueue
主线程/SDL回调 → 消费 FrameQueue 渲染/播放
```

关键：read_thread 与解码分离，PacketQueue 用**总量阈值**控制读取节奏
（ffplay `MAX_QUEUE_SIZE = 15MB`）。即使视频帧队列满，video_thread 阻塞**只阻塞它自己**，
read_thread 照样读音频包、audio_thread 照样解音频，音频时钟正常推进，绝不互锁。

FluxPlayer 已有 `FrameQueue`（对标 ffplay FrameQueue）、HW 解码、AVSync，
**就差一层 PacketQueue + 读包/解码线程拆分**，离 ffplay 架构只有一步。

## 三、目标架构

```
demuxThread        → av_read_frame → 按流分发到 videoPktQueue_ / audioPktQueue_ / (字幕同步解码)
videoDecodeThread  → 从 videoPktQueue_ 取包 → 解码 → normalizeVideoPTS → enqueueVideoFrame → videoQueue_
audioDecodeThread  → 从 audioPktQueue_ 取包 → 解码 → normalizeAudioPTS → enqueueAudioFrame → audioQueue_
主线程 run()        → renderVideoFrame 消费 videoQueue_（不变）
平台音频线程        → audioOutputCallback 消费 audioQueue_（不变）
```

### 3.1 线程访问模型（满足开发守则「线程安全」注释要求）

重构后不要把 `FrameQueue` 理解为某个线程“独占”的对象。它本来就是
单生产者 + 单消费者 + 控制线程可 flush/abort 的同步队列。

| 资源 | 生产/写入线程 | 消费/读取线程 | 控制/flush 线程 | 规则 |
|------|--------------|--------------|----------------|------|
| `demuxer_` / `dashMerger_` | demux 线程 | demux 线程 | demux 线程 | seek、reopen、DASH 重启只在 demux 线程执行 |
| `videoDecoder_` | video decode 线程 | video decode 线程 | video decode 线程 | 只由 video decode 线程 `send/receive/flush` |
| `audioDecoder_` | audio decode 线程 | audio decode 线程 | audio decode 线程 | 只由 audio decode 线程 `send/receive/flush` |
| `videoPktQueue_` | demux 线程 | video decode 线程 | demux 线程 | `PacketQueue` 内部加锁，serial 标记 flush 边界 |
| `audioPktQueue_` | demux 线程 | audio decode 线程 | demux 线程 | `PacketQueue` 内部加锁，serial 标记 flush 边界 |
| `videoQueue_` | video decode 线程 | 主线程/渲染线程 | 控制线程可 `flush/abort/start` | 遵循 `FrameQueue` 单生产/单消费模型 |
| `audioQueue_` | audio decode 线程 | 平台音频线程 | 控制线程可 `flush/abort/start` | seek 后必须同时重置音频回调残留状态 |
| `avSync_` | 音频/视频/控制线程 | 音频/视频/渲染线程 | 控制线程 | 仅调用其线程安全公开接口 |
| PTS 归一化状态 | video/audio decode 线程 | video/audio decode 线程 | 控制线程重置 | 不能只依赖多个 atomic 拼接状态，见第七节 |

跨线程协调主要通过：`PacketQueue`（serial 序号）+ `FrameQueue` 自身锁 +
`AVSync` 线程安全接口 + 明确受保护的控制状态。禁止一个线程直接调用另一个
线程拥有的 decoder；但允许控制线程按 `FrameQueue` 既有契约执行
`flush/abort/start`。

### 3.2 为什么能消除死锁

video frame 队列（容量 4）满，只阻塞 **video decode 线程**。
audio decode 线程从独立的 `audioPktQueue_` 取包，继续产出音频帧 →
音频时钟照常推进 → 渲染线程照常取帧 → `videoQueue_` 腾空 →
video decode 线程解阻塞。**结构性死锁消除。**

## 四、PacketQueue 设计

新增 `include/FluxPlayer/core/PacketQueue.h` + `src/core/PacketQueue.cpp`。

### 4.1 接口

```cpp
class PacketQueue {
public:
    PacketQueue();
    ~PacketQueue();

    // 生产者（demux 线程）：克隆 packet 引用入队，非阻塞追加。返回当前 serial。
    bool put(AVPacket* pkt);
    // 入队 EOF 标记包（data=null），通知 decode 线程 drain 后结束
    void putNullPacket(int streamIndex);

    // 消费者（decode 线程）：取一个 packet。block=true 时队列空则阻塞等待。
    // 出参 serial 返回该包所属序号，供 decode 线程识别 flush 边界。
    // 返回值：1=取到包，0=abort，-1=非阻塞且队列空
    int get(AVPacket* pkt, bool block, int* serial);

    void flush();   // 清空所有包，serial 自增（seek/重连用）
    void abort();   // 唤醒所有等待者，停止队列
    void start();   // 重置 abort，serial 自增

    int size() const;        // 当前包数
    int64_t byteSize() const;// 当前总字节（含 AVPacket::size + 结构开销）
    int serial() const;      // 当前序号

private:
    // 链表节点 + 互斥锁 + condition_variable，仿 ffplay PacketQueue
};
```

### 4.2 背压策略（仿 ffplay）

- `put()` 正常情况下不阻塞，但 **PacketQueue 不允许无限增长**。
- demux 线程每轮读包前必须执行背压检查；decode 线程每次 `get()` 成功后
  `notify` `continueReadCond_`。
- 背压分两层：
  1. **总量硬上限**：所有 packet queue 的字节总量超过
     `kMaxQueueBytesHard` 时，demux 必须等待，不能继续读包。
  2. **平滑软上限**：总量超过 `kMaxQueueBytesSoft`，且已存在的流都达到
     `kMinPktFrames` 或 `kMinQueueDurationSec` 时，demux 等待 10ms。
- 对缺失流/交织极差的文件，允许一个短暂“找另一条流”的探测窗口，但不能无限
  缓存单路 packet；单路也要受 `kMaxSingleQueueBytes` 保护。
- 常量（具名 `constexpr`，不新增配置项，避免热加载负担）：

```cpp
constexpr int64_t kMaxQueueBytesSoft   = 15 * 1024 * 1024;  // 对齐 ffplay MAX_QUEUE_SIZE
constexpr int64_t kMaxQueueBytesHard   = 64 * 1024 * 1024;  // 防坏文件/差交织 OOM
constexpr int64_t kMaxSingleQueueBytes = 48 * 1024 * 1024;  // 单路保护
constexpr int     kMinPktFrames        = 25;                // 各流最少缓冲包数门槛
constexpr double  kMinQueueDurationSec = 1.0;               // 各流最少缓存时长门槛
constexpr int     kBackpressureWaitMs  = 10;
```

`PacketQueue` 建议额外维护 `duration()`：用队列内可用 PTS/DTS 的首尾差估算。
仅用字节数不够稳定：高码率视频 15MB 可能只够很短时间，低码率音频很多包也可能
字节很小。

### 4.3 serial 序号机制（seek 正确性核心）

- 每次 `flush()` / `start()`，serial 自增。
- decode 线程 `get()` 拿到 packet 的 serial，与「上次处理的 serial」比较：
  serial 变了 → 说明发生过 seek/flush → **decode 线程自己** flush decoder +
  flush 自己的 frame 队列 + 重置 `lastEnqueued*PTS_` 等局部状态。
- FrameQueue 中已经排队、或者渲染/音频线程已经 peek 到的旧帧也必须处理：
  - 最小实现：serial 变化时 decode 线程 `flush()` 对应 `FrameQueue`，控制线程同步
    重置音频回调和渲染缓存状态（见 5.1）。
  - 更稳实现：给 `Frame` 增加 `serial` 字段，消费者发现旧 serial 直接丢弃。
    这会扩大改动面，但可以进一步降低 seek 后旧帧泄漏风险。
- 这样跨线程的 seek 无需 demux 线程触碰 decoder；decoder 操作只回到对应 decode
  线程内执行，FrameQueue 则按其自身同步契约由生产/消费/控制线程访问。

## 五、seek / DASH / 直播重连改造

当前这些逻辑在解码线程内直接 flush decoder + frame 队列。新模型下统一改为：
**demux 线程只动 demuxer 和 packet 队列，decode 线程靠 serial 变化自行 flush。**

### 5.1 普通 seek（`processSeekRequest`，移到 demux 线程）

```
1. demuxer_->seek(ts)
2. videoPktQueue_->flush()  // serial++
3. audioPktQueue_->flush()  // serial++
4. avSync_->seekTo(seekTime)
5. 重置音频回调残留状态：
   - currentAudioFramePTS_ = seekTime
   - samplesPlayedInFrame_ = 0
   - pendingAudioOffset_ = 0
6. 重置渲染/起播状态：
   - lastRenderedPTS_ / cached render frame 状态按当前实现清理
   - prebuffering_ / sawFirstKeyframe_ / lastEnqueuedVideoPTS_ 等按现有 seek 逻辑重置
7. decodingToTarget_ / decodeTargetPTS_ / seekTargetStartTime_ 设置
   → video/audio decode 线程在下次 get() 发现 serial 变化，
     各自 videoDecoder_->flush() + videoQueue_->flush()（音频同理），
     再按 decodingToTarget_ 走既有精确跳转丢帧逻辑（enqueue*Frame 内）
```

注意：

- packet queue `flush()` 后，decode 线程可能仍卡在 `FrameQueue::peekWritable()`。
  seek/stop 控制路径必须同时唤醒对应 `FrameQueue`，避免生产者一直等旧队列空间。
- seek 请求仍通过 `seekMutex_` 保护的 `SeekRequest` 传递，避免
  `pending + target` 两个字段出现 TOCTOU。
- 连续 seek 时只保留最后一个目标；demux 线程处理 seek 前后要再次检查是否有更新的
  pending seek，避免刚 seek 完又立即喂入旧目标数据。

### 5.2 DASH seek（`restartDashMerger`）/ 直播重连（reopen）

同样移到 demux 线程：重启上游 / reopen demuxer 后，flush 两个 packet 队列
（serial++），decode 线程自行 flush。`sawFirstKeyframe_` / `lastEnqueuedVideoPTS_`
等起播追赶状态的重置规则保持不变。

DASH / pipe 输入不可 seek 时：

- `restartDashMerger(seekTime)` 仍负责用上游 `-ss` 或 HTTP Range 重新打开流。
- demux 线程必须先停止旧 `DashMerger`，再 flush packet queues，最后启动新输入；
  避免旧管道残留 packet 在新 serial 后继续进入队列。
- 切换画质 `switchQuality(formatId, seekTime)` 与 DASH seek 走同一套 serial 边界，
  不能绕过 packet queue 直接重启单一 `decodingThread`。

直播重连时：

- reopen 成功后 flush packet queues 并推进 serial。
- 不应重置长期直播 PTS 基准，除非检测到明确 discontinuity；否则会造成播放时间跳变。

## 六、EOF / 缺失流 / 单流模式

- HTTP/HTTPS VOD（如带有限 duration 的 CDN MP4）是点播，不因 URL 为网络地址而进入
  Live；EOF 后与本地文件相同地 drain 并停泊等待 seek。RTSP/RTMP/RTP 或 duration 无效
  的动态来源才进入直播重连。协议专用选项必须按 scheme 分流，禁止给 HTTP 注入
  `rtsp_transport` / `rtmp_live`。
- **HTTP 打开路由回退**：配置代理时只尝试代理一次，单次 I/O 最长 5s，不在故障代理上
  执行 0/1/3 秒指数重连；代理失败后立即直连重试一次。直连和代理均支持 Range 的 CDN
  MP4 因此不会因本地代理瞬时异常而完全打不开。
- 普通 VOD seek 必须同步暂停音频设备并 flush 音视频 frame queue；仅 flush packet queue
  不足以清除设备回调持有的旧 AClock。`postSeek` 在同一个 seekMutex 临界区原子发布 pending、
  推进 packet serial 并清 frame queue，Demuxer ready 前的残留解码输出一律丢弃。目标后的
  音频帧只有在格式转换成功并实际入队后才恢复设备，音频回调真正提交新 AClock 后才发布
  audio-aligned；音视频未全部 aligned 时 UI 使用目标/视频 PTS。macOS seek 使用
  AudioQueuePause+Reset 丢弃设备旧 PCM，恢复前重新 prime buffer。精确 seek 超时本地为 2s、
  网络 VOD 为 8s，并在 demux seek 成功后重新起算。

- demux 线程读到 EOF（本地文件 `readPacket` 返回 false）：
  只对**实际存在且启用**的 packet queue `putNullPacket()`，设 `demuxFinished_`。
- decode 线程 `get()` 到 null 包：drain decoder（循环 receiveFrame 取尽残帧入队），
  设 `videoDecodeFinished_` / `audioDecodeFinished_`，退出。
- 不存在的流，其 finished flag 初始化为 `true`；存在但初始化失败的流，要么打开失败，
  要么显式标记该流 disabled 并把对应 finished flag 设为 `true`，不能让 EOF 判定等待
  一个永远不会启动的 decode 线程。
- `run()` EOF 判定改为按启用流组合判断：

```cpp
bool videoDone = !hasVideoStream_ ||
    (videoDecodeFinished_ && (!videoQueue_ || videoQueue_->numReadable() == 0));
bool audioDone = !hasAudioStream_ ||
    (audioDecodeFinished_ && (!audioQueue_ || audioQueue_->numReadable() == 0));

if (demuxFinished_ && videoDone && audioDone) {
    shouldQuit_ = true;
}
```

- 纯音频文件：不创建 video decode 线程，`videoDone=true`。
- 纯视频文件：不创建 audio decode 线程，`audioDone=true`；主时钟应切到 video/external
  路径，不能等待音频时钟。
- 直播/DASH 的 readPacket 失败重试、退避、周期 reopen 逻辑全部保留在 demux 线程。

## 七、PTS 归一化状态

当前 `firstVideoFrameReceived_` / `firstAudioFrameReceived_` /
`firstVideoPTS_` / `firstAudioPTS_` / `liveStreamBasePTS_` /
`liveStreamBaseCalibrated_` 是多个 atomic 组合状态。拆成 video/audio 两个 decode
线程后，单个 atomic 读写安全不等于组合逻辑安全。

实现时必须二选一：

1. 新增 `PTSNormalizer` 小类，用一个 mutex 保护“首帧记录 + base 校准 + reset”；
   `normalizeVideoPTS()` / `normalizeAudioPTS()` 都通过它更新。
2. 或者把 base 选择移到 demux 线程：packet 分发前根据 stream time_base 记录首个
   packet PTS，确定统一基准后 decode 线程只做只读归一化。

推荐方案 1，改动小，能复用现有 `normalize*PTS` 中的回绕、直播基准、seek 丢帧逻辑。

## 八、字幕与录制

### 8.1 字幕

当前字幕包在 `decodingThread()` 内同步解码，并写入 `SubtitleManager`。重构后建议先
保持轻量方案：

- demux 线程识别 subtitle packet 后同步调用 `SubtitleDecoder::decode()`，结果写入
  `SubtitleManager`。
- seek / reopen / stop 时，demux 线程负责 `SubtitleDecoder::flush()`，
  `SubtitleManager::clear()`，避免旧字幕残留。
- 若后续遇到图片字幕或复杂 ASS 导致 demux 阻塞，再升级为 `subtitlePktQueue_` +
  subtitle decode 线程；本轮重构不强制引入。

### 8.2 录制

当前 `Recorder::writePacket()` 在读包后执行。重构后应跟随 demux 线程移动，但必须
明确 serial 规则：

- `videoRecorder_` / `audioRecorder_` 的 `writePacket()` 只在 demux 线程调用；
  start/stop 若来自 UI/控制线程，需要加 mutex 或投递到 demux 线程执行。
- seek / DASH 重启 / 直播 reopen 后，旧 serial packet 不得继续写入当前录制文件。
- 普通录制若跨 seek，建议结束当前片段或重置 Recorder 时间基；否则输出文件 DTS/PTS
  可能回退。
- 原始码流录制继续使用 packet path；转码录制若使用 frame path，必须分别声明由
  video/audio decode 线程调用，并保证 Recorder 内部同步。

## 十、复用与不变项

- `enqueueVideoFrame` / `enqueueAudioFrame` / `normalizeVideoPTS` /
  `normalizeAudioPTS` / `checkPrebufferComplete` 逻辑**复用**，仅调用线程从
  单解码线程变为各自的 decode 线程。
- 精确跳转丢帧、PTS 回绕检测、估算帧标记、变速丢帧、keep-last、
  音频残留偏移等既有机制全部保留，但跨线程状态必须按本方案重新声明访问线程。
- 录制 `writePacket` 保留功能语义，但调用线程改为 demux 线程，并按 8.2 增加同步/serial 规则。
- 公开接口（`open`/`play`/`pause`/`seek`/`stop`/回调等）**完全不变**。

## 十一、风险与验证

### 11.1 主要风险

- **跨线程 seek 时序**：serial 机制保证 decode 线程丢弃旧序号包；
  decoder 内部可能残留极少量旧帧，由 decoder flush、FrameQueue flush、音频/渲染残留
  状态重置和既有 `decodingToTarget_` 精确跳转丢帧共同兜底。
- **音频回调与 audio 队列 flush 的并发**：`FrameQueue::flush` 已加锁，
  flush 瞬间回调读到空队列只产生极短静音；必须同步重置 `pendingAudioOffset_`。
- **背压阈值**：软/硬上限要覆盖高码率、本地坏文件、直播长时间单路缺失三类情况。
- **录制 writePacket**：移到 demux 线程后，start/stop/seek serial 必须有明确同步规则。

### 11.2 验证要求（开发守则第八条第 4 点）

本重构涉及并发核心，macOS 可作为基础构建与本地播放验证；目标平台仍必须覆盖
**Windows + CUDA**，因为硬解线程和驱动行为可能不同。验证项：

1. 触发原 bug 的 mp4 文件正常播放，无 `Underruns` 持续累加、画面流畅。
2. 本地文件 seek（前跳/后跳/连续 seek）落点正确、无卡死。
3. 循环播放（loop）重启正常。
4. 实时流（RTSP/RTMP）起播、断流重连正常。
5. DASH（B 站等）seek、画质切换正常。
6. 纯音频文件播放正常（无 video decode 线程）。
7. 录制（视频/音频）功能正常。
8. 暂停/恢复、变速、截图正常。
9. 退出无崩溃、无线程泄漏（所有已创建线程均 join）。

## 十三、重构落地后的 seek 实战修复与提速

多线程模型落地后，在真机（本地文件 + B 站 DASH）实测 seek 时又暴露并修复了一批
问题。这些修复都建立在第四、五节的 PacketQueue + serial 架构之上，记录于此以便回溯。

### 13.1 seek 失效 —— demux 线程 EOF 后停泊

**现象**：小文件（如 8MB / 128s）播放时，seek 完全无效，进度条照常线性前进。

**根因**：demux 线程读到本地文件 EOF 后直接 `break` 退出。小文件几毫秒就被整体读进
packet 队列、撞到真 EOF，线程随即退出。之后用户每次 seek 只设置
`seekRequest_.pending = true`，但**唯一会调用 `processSeekRequest()` 的 demux 线程
已经死了**，标志永远没人消费。

**修复**：demux 线程读到 EOF 后**停泊**而非退出（对标 ffplay —— EOF 是播放状态，
不是线程终点）。仍投递一次 null 包让 decode 线程 drain（`run()` 据此正常结束播放/
循环），随后进入停泊循环每 10ms 轮询 `processSeekRequest()`：一旦命中 seek，flush
队列移除尾部 null 包并 serial++，从新位置恢复读取；仅 `shouldQuit_` 能终结停泊。
`processSeekRequest()` 返回 `bool`，停泊循环据此判断是否恢复。

### 13.2 进度条延迟/跳回 —— 即时冻结 + serial 丢弃旧帧 + demux 挂起期丢包

**现象**：网络流 seek 后进度条不立即跳到目标；倒退 seek 时进度条先跳到目标又跌回旧
位置、再缓慢爬升。

**根因链**（逐层定位，最终落到一处架构根因）：
1. DASH seek 走 `restartDashMerger`，重启上游需数秒。期间旧 packet 队列残帧继续渲染，
   每渲染一帧就把 `lastRenderedPTS_` 覆写回旧位置 → 进度条不跳。
2. 加 `decodingToTarget_` 冻结取帧后，仍被 decode 线程的 2s seek 超时中途清除 → 旧帧
   恢复渲染。把 flush 提前到 `restartDashMerger` 开头让 decode 线程阻塞在空队列，可缓解。
3. **但根因是 `flush`（serial++）滞后于 `seek()`**：`seek()` 在 UI 线程置位精确跳转，
   真正 flush 要等 demux 线程跑到 `processSeekRequest` 才发生（隔几十~几百 ms）。这个
   窗口内旧 pipe 仍在灌包，且 demux 把刚读到的旧包 put 进队列时**带的是 flush 后的新
   serial**，绕过 serial guard，触发 enqueue 里的「到达目标 / far-from-target 提前
   校准」，把 AV 时钟校到旧位置。

**修复（三层互补）**：
- **`seek()` 即时 flush**（UI 线程）：置位精确跳转的同时同步 `flush`（serial++），
  关闭「在途已解码帧」窗口。
- **enqueue serial guard**：`enqueueVideoFrame` / `enqueueAudioFrame` 开头丢弃
  `serial != pktQueue->serial()` 的在途残帧。
- **demux 挂起期丢包**（根因修复）：demux 线程 `readPacket` 成功后、put 进队列前，
  若 `seekRequest_.pending` 为真，直接丢弃该包。旧包不进队列、拿不到新 serial，
  PTS 无法区分大小幅 seek 的难题被绕开 —— serial 才是可靠判据。

三者配合后，前向/倒退 seek 进度条均即时停在目标，不再被旧位置帧拉回，且**不需要任何
PTS 阈值**（阈值无法稳健区分「旧的靠后帧」与「新的合法靠后帧」）。

### 13.3 DASH seek 健壮性 —— 瞬时网络失败重试

**现象**：seek 时偶发一次 TLS pull error 就让整个播放进入永久 ERROR，之后 15s 在
null context 上空转重试才放弃。

**修复**：`restartDashMerger` 把「启动 merger + 打开 demuxer」包成重试循环（最多 3 次），
每次失败清理本轮残留后重来，全部失败才进 ERROR。单次网络抖动不再使 seek 永久失败。

### 13.4 DASH seek 提速（实测 ~6s → ~2s）

逐段拆解 seek 耗时（远程流打开 / pipe 探测 / 解码首帧），针对性优化：

| 优化 | 位置 | 效果 |
|------|------|------|
| 视频/音频远程流**并行打开** + 远程探测调优 | `DashMerger::mergeLoop` | 两路串行打开 → 并行，墙钟约减半 |
| MKV header 写入**帧率**（`avg/r_frame_rate`） | `DashMerger` 建流 | 下游 demuxer 不必读包估算 fps |
| pipe demuxer `probesize` 2MB→256KB / `analyzeduration` 1s→500ms | `Demuxer::configureNetworkOptions` | header 自描述后读完头即返回 |
| pipe 容器头自描述时**跳过 `find_stream_info`** | `Demuxer::open`（`streamInfoReadyForPipe`） | 消除探测段从管道读包/试解码的网络等待 |
| `write_header` 后 **`avio_flush`** | `DashMerger::mergeLoop` | header 即时进管道，open 不再为等首帧阻塞 |
| 视频/音频 `av_seek_frame` **并行执行** | `DashMerger::mergeLoop` | 两路 HTTP Range 延迟不再串行叠加 |
| generation + interrupt callback | `DemuxWorker` / `DashMerger` | 连续 seek 抢占旧冷启动，仅落地最后目标 |
| seek 重建期间暂停音频设备 | `DemuxWorker` / `DecodeWorker` | 首帧新音频入队后恢复，避免 underrun 风暴和旧 AClock 推进 |
| 候选管线事务提交 | `DemuxWorker` / `DashMerger` | 独立准备新 merger+demuxer，成功后再替换；失败保留旧管线且不进 ERROR |
| generation 仅取消候选 | `DashMerger::commitPreparedStream` | 已提交流不被下一次 seek 提前截断，避免 partial file/Packet corrupt |
| 300ms seek 静默期合并 | `DemuxWorker::processSeekRequest` | 拖动/连续点击只为最终目标建立连接，避免反复取消 TLS |
| seek 网络预算 | `DashMerger` / `DemuxWorker` | 单次 open 6s、Range 8s、最多 2 次且总预算 14s，避免一次失败卡 20s |
| 自适应网络回退 | `DashMerger` / `DemuxWorker` | 候选内部 1s 内快速重连；代理首试失败后等待 150ms 改走直连，避免重复命中故障路由 |
| 自描述 pipe 专用打开 | `Demuxer::openSelfDescribingPipe` | 仅解析 Matroska Tracks，不执行 find_stream_info 的媒体包探测 |
| POSIX pipe 所有权显式转移 | `DashMerger::getPipeUrl` | 防止失败候选清理时重复 close 已被系统复用的 fd |
| 阶段耗时日志 | `DashMerger::mergeLoop` | 区分 open/probe、Range seek 与总重启耗时，定位代理/CDN 瓶颈 |

> 稳定性回退：FFmpeg 4.4 经 CONNECT 代理时，强制 `multiple_requests`、跳过
> `find_stream_info`、并发首包预取以及激进小 Cluster 会触发 `premature EOF` 或
> `partial file/Packet corrupt`，因此不作为当前实现。

**残留**：首次远跳仍可能 ~8s，根因是冷的 proxy→CDN 连接下载首个 4K 关键帧的固有网络
成本（后续 seek 因连接已热降到 1~2s）。要进一步压缩只能上 **DashMerger 原地 seek**
（保留已打开的远程 context，`av_seek_frame` 重定位而不重连），代价是需处理 MKV
muxer 的 PTS 跳变，风险较高，暂未实施。

### 13.5 网络流媒体信息提取

网络流（RTSP/RTMP/HLS/网页流）此前在 `main.cpp` 被 `isNetworkPath` 判断跳过 MediaInfo
提取，导致 UI 的 codec/分辨率等字段显示 "Unknown"。改为**复用 Player/Demuxer 已打开
的 `AVFormatContext`**（`Player::getFormatContext()` + `MediaInfo::extractFromContext`），
零额外连接开销。
