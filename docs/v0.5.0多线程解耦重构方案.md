# FluxPlayer 多线程播放数据流

## 1. 线程模型

FluxPlayer 使用一个 DemuxWorker 和独立的视频、音频 DecodeWorker，通过 packet 队列把读取与解码分开。视频帧队列满时只阻塞视频解码线程，不让同一解码线程同时承担音频生产。

```text
输入 → DemuxWorker → video PacketQueue → video DecodeWorker → video FrameQueue → 主线程渲染
                  → audio PacketQueue → audio DecodeWorker → audio FrameQueue → 音频输出
```

主线程执行控制命令和 GLFW/OpenGL 操作。平台音频回调或输出线程消费 PCM；网络准备候选有独立线程，安装仍由主线程执行。

## 2. PacketQueue 与背压

PacketQueue 保存压缩包及 serial，解码线程阻塞取包。DemuxWorker 根据队列大小和媒体类型执行背压，防止无限积压。背压和退避等待期间检查停止、Seek 和录制请求。

串行读包仍共享输入带宽，因此分离解码线程不等于所有负载下都能持续供给音频。音频覆盖耗尽时主时钟冻结，视频跟随该时钟等待。

## 3. 解码输出

DecodeWorker 将输出转换到私有 Frame，携带解码包的 serial 和帧队列 epoch 提交。FrameQueue 在锁内验证代际、容量，再交换帧引用；过期输出不进入新时间线。

视频消费者获取独立引用和 ReadToken，凭证匹配后消费，keep-last 保留最后显示帧。音频消费者在锁内直接复制 S16 并保存采样相位，不调用 FFmpeg 帧引用操作。

## 4. Seek 与 EOF

控制线程发布 Seek 请求，DemuxWorker 执行实际定位。请求目标与代际同锁获取，读包和 Seek 的中断回调观察代际变化。旧完成结果不更新新目标或恢复意图；包和帧的 serial/epoch 边界隔离旧数据。

EOF 后 demux 与解码完成状态分开管理，停泊路径仍处理控制请求。新 serial 使解码器刷新并恢复消费；正常退出则先发布取消、abort 队列，再 join 所有使用线程。

## 5. 字幕、录制与 DASH

字幕包由 demux 线程同步交给 SubtitleDecoder，文本进入带锁的 SubtitleManager；没有独立字幕 packet 队列。Seek 和输入替换清理旧字幕。

RecordingService 在 demux 所有者线程创建、写入和封口录制器，控制线程投递带输入代际的请求。音频播放禁用不影响源音轨的录制分发。

DASH 通过 DashMerger 合并分离音视频流为自描述管道输入。候选准备与安装按请求代际校验，旧资源在使用者退出后释放。管道读写观察取消，不能通过跨线程关闭活跃 Demuxer 中断 I/O。
