# FluxPlayer 命令队列与控制线程架构

本文描述 FluxPlayer 播放器核心（`core` 模块）的控制流架构：**命令队列 + 单一控制线程 + 组件化**。
它解决两类问题——**控制流并发安全**（谁来改播放管线状态）与**职责解耦**（把巨类拆成职责单一的协作组件）。

---

## 一、设计总纲

### 1.1 核心思想

把「**谁来改播放管线状态**」从「任意 UI 线程」收敛为「**唯一的控制线程**」。UI 线程不再
直接调用会改变内部状态的方法，而是**投递一条命令**到线程安全队列；控制线程（即主循环
线程）在每帧循环的固定时点**串行取出并执行**命令。

```
        投递（非阻塞，任意线程）              执行（串行，仅控制线程）
UI 线程 ───────────► CommandQueue ───────────► 控制线程主循环
  Controller            (mutex+队列)              Player::pumpCommands()
  .post(SeekCommand)                                ├─ SeekCommand     → DemuxWorker 协作
                                                    ├─ SwitchQuality   → 重提取 + 重开流
                                                    ├─ StartRecording  → RecordingService
                                                    └─ SetSpeed/...    → ClockController/解码
```

收益：

- **seek 协议显式化**：发起 seek 的「置精确跳转状态 + flush 队列 bump serial」从 UI 回调
  移到控制线程的 `SeekCommand`，并与「投递 demux 内部 seek 请求」成为同一控制线程内的
  连续事务；demux 线程仍在自己的读循环落地 `demuxer_->seek`，跨线程时序从隐式注释约定
  变为显式协议（`seekRequest_` + serial）。
- **控制与执行同线程**：所有 mutating 操作（pause/resume/stop/seek/变速/录制/画质切换）
  统一经命令队列在控制线程串行执行，消除「UI 线程伸手进播放管线内部拨开关」的并发脆弱性。
- **录制无锁**：控制线程只投递录制请求，录制器的创建/销毁/writePacket 全部归 demux 线程
  串行执行，彻底去除录制锁。

### 1.2 组件拆分

`Player` 是**门面（Facade）+ 组件持有者**，公开接口稳定，内部委托给职责单一的组件：

| 组件 | 职责 |
|------|------|
| **CommandQueue** | 线程安全命令队列：任意线程投递，控制线程批量取走串行执行 |
| **StateManager** | 状态机：原子状态量 + 统一转换协议（转换日志、回调触发） |
| **ClockController** | 持有 AVSync + seek 精确跳转状态（目标 PTS / 计时窗口 / 超时判定） |
| **QueueManager** | 统一管理 4 队列（packet×2 + frame×2）的创建/启动/abort/flush/销毁 |
| **DemuxWorker** | demux 读包线程：读包分发 + seek 协议 + DASH 重启 + 直播重连 + 背压 |
| **DecodeWorker** ×2 | video/audio 对称解码线程：取包解码 + PTS 归一化 + 帧入队 |
| **RecordingService** | 录制服务：录制器创建/销毁/writePacket 全归 demux 线程串行，query 走原子状态块 |

> **GLFW context 亲和性约束**：OpenGL context 绑定在创建它的线程（主线程）。因此**实际
> GL 调用、window swap/poll 必须留在主线程**（即控制线程 = 主线程 = 主循环所在线程）。
> 渲染不甩到独立线程——控制线程和渲染线程是同一个。命令执行时点嵌在主循环里，与渲染
> 同线程串行，天然保证「命令执行」与「取帧渲染」不会并发踩 GL 状态。

### 1.3 线程模型

```
控制线程(=主线程): 渲染循环 run()
                  + pumpCommands() 串行执行命令
                  + 持有 StateManager 状态机
demux 线程:        DemuxWorker::run()（读包分发 + seek 协议 + 录制写入）
video decode 线程: DecodeWorker::runVideo()
audio decode 线程: DecodeWorker::runAudio()
平台音频回调线程:   audioOutputCallback（RenderPipeline 之外）
```

常驻线程数：3 worker（demux + video/audio decode）+ 主线程 + 平台音频回调。画质切换时
另起一次性临时工作线程跑 yt-dlp 提取。控制并发的方式是「**单一控制线程串行执行命令**」，
而非分散的多把锁 + 注释约定。

## 二、命令队列

### 2.1 命令类型

命令是「值对象 + 行为」，用虚函数 dispatch 而非 enum + switch，每条命令把自己的执行逻辑内聚：

```cpp
// include/FluxPlayer/core/PlayerCommand.h
struct PlayerCommand {
    virtual ~PlayerCommand() = default;
    virtual void execute(Player& player) = 0;   // 控制线程取出后调用
};

struct SeekCommand          : PlayerCommand { double targetSec; ... };
struct PauseCommand         : PlayerCommand { ... };
struct ResumeCommand        : PlayerCommand { ... };
struct StopCommand          : PlayerCommand { ... };
struct SetSpeedCommand      : PlayerCommand { double speed; ... };
struct SwitchQualityCommand : PlayerCommand { std::string formatId; double seekTime; ... };
struct StartRecordingCommand: PlayerCommand { bool video; ... };
struct StopRecordingCommand : PlayerCommand { bool video; ... };
```

每条命令的 `execute()` 调用 Player 的内部执行方法（`*Internal()`）真正落地。公开方法
（`seek`/`pause`/...）只负责构造命令并投递，命令 `execute()` 调用 `*Internal()` 完成
实际工作，从而消除「公开方法 → 投递 → execute → 公开方法」的递归。

### 2.2 队列实现

```cpp
class CommandQueue {
public:
    void post(std::unique_ptr<PlayerCommand> cmd);          // 任意线程，非阻塞
    std::vector<std::unique_ptr<PlayerCommand>> drain();    // 仅控制线程，取走全部
    size_t size() const;
private:
    mutable std::mutex mutex_;
    std::vector<std::unique_ptr<PlayerCommand>> pending_;
};
```

队列只保护「投递 / 取走」这一对操作，临界区极短（`drain()` 用 swap 取走全部）。控制线程
每帧 `drain()` 一次性取走待执行命令，**锁外**串行 `execute`，避免持锁执行重活。

### 2.3 执行时点

控制线程主循环每帧固定时点泵命令：

```cpp
while (!shouldClose && !shouldQuit) {
    pumpCommands();        // ① 串行执行本帧投递的所有命令
    renderOneFrame();      // ② 取帧渲染
    renderCallback_();     // ③ UI（含 Controller，可能投递新命令）
    swapBuffers();
    pollEvents();
    checkEofAndLoop();     // ④ EOF 判定 + 循环重启
}
```

**关键时序**：`pumpCommands()` 在 `renderCallback_()`（UI）**之前**。本帧 UI 投递的命令在
**下一帧**开头执行——延迟最多一帧（~16ms），用户无感，换来「命令执行绝不与 UI 回调
交错」的强保证。

### 2.4 哪些操作走命令、哪些保留直接调用

判据：**是否改变跨线程播放管线状态 / 是否有时序依赖**。

| 操作 | 走命令？ | 理由 |
|------|---------|------|
| seek / switchQuality / stop / 录制 start/stop | 是 | 强时序、多组件协作 |
| setPlaybackSpeed | 是 | 改 AVSync 时钟基准 + 解码丢帧策略，多组件 |
| pause / resume | 是 | 与 seek/EOF 状态机交互，纳入统一更安全 |
| setVolume / setMute | 否（保留原子） | 单一原子量，平台音频回调直接读，无时序依赖 |
| getCurrentTime / getStats / isRecording 等 query | 否 | 只读快照，走原子/无锁读，不能阻塞 UI 渲染 |

> **只读 query 绝不走命令队列**：UI 每帧要读十几个状态画进度条/音量/录制时长，若都排队
> 等控制线程执行会引入延迟和死锁风险。query 继续走「原子量 / 短锁快照」直读。

### 2.5 公开接口语义

`Player` 对 `main.cpp` / `Controller.cpp` 的方法签名稳定，但区分「受理」与「完成」：

| 方法 | 返回值语义 | 完成/失败通知 |
|------|-----------|--------------|
| `seek(double)` | 参数合法且命令已受理返回 `true` | 进度条由 ClockController 立即更新；真实落点由后续帧校准 |
| `switchQuality(formatId, seekTime)` | formatId 合法、命令已受理返回 `true` | 切换中状态变化经 `stateChangeCallback_` |
| `start/stopRecording` | 命令已受理 | `is*Recording()` / time / size 每帧读原子快照 |
| `pause/resume/stop/setPlaybackSpeed` | 命令已受理或当前状态不允许 | `stateChangeCallback_` / stats 快照 |

生命周期方法分两类：

- `open()` / `open(externalWindow)` / `play()` 保持**同步语义**：通常在进入主循环前调用，
  命令泵尚未运行，直接同步执行。
- `close()` / 析构 / 自然 EOF 收尾走同步关闭路径（`joinWorkerThreads`），不依赖再投命令。

## 三、组件设计

### 3.1 DemuxWorker（demux 读包线程）

**职责**：在自己的线程 `run()` 里循环读包分发、处理 seek 请求、DASH 流重启、直播重连、背压检测、录制写包。

#### 接口

```cpp
class DemuxWorker {
public:
    explicit DemuxWorker(Player* player);
    void start();                      // 创建线程，开始 run()
    void join();                       // join 线程（`shouldQuit_` 已置 true）
    void postSeek(double targetPTS);   // 控制线程投递 seek 请求（demux 线程下一轮循环处理）
private:
    void run();                        // 主循环（读包 + seek 协议 + 录制 + 重连）
    void processSeekRequest();         // 落地 seek（demuxer_->seek + bump serial）
    void restartDashMerger(double t);  // DASH 流 seek = 停旧 merger 重启 + 重开 demuxer
    void waitForPacketSpace();         // 背压：队列满时等待
    
    Player* player_;
    std::thread thread_;
    // Seek 协议（原 Player::seekRequest_）
    struct SeekRequest {
        std::atomic<bool> pending{false};
        std::atomic<double> target{0.0};
    } seekRequest_;
};
```

#### 核心逻辑

```cpp
void DemuxWorker::run() {
    while (!player_->shouldQuit_.load()) {
        // ① 处理录制请求（RecordingService 投递，创建/销毁录制器）
        player_->recordingService_->processPendingRequests();
        
        // ② 处理 seek 请求（控制线程投递，demux 线程落地）
        if (seekRequest_.pending.load()) {
            processSeekRequest();  // → demuxer_->seek() + bump serial
        }
        
        // ③ 网络断流检测与重连
        if (isNetworkStream && 连续读包失败) {
            指数退避重连 avformat_open_input(...);
        }
        
        // ④ 读包分发（背压检测 waitForPacketSpace）
        AVPacket* pkt = av_packet_alloc();
        int ret = av_read_frame(formatCtx_, pkt);
        if (视频包) {
            videoPacketQueue->put(pkt, serial);
            if (recording) recorder->writeVideoPacket(pkt);  // 无锁写
        } else if (音频包) {
            audioPacketQueue->put(pkt, serial);
            if (recording) recorder->writeAudioPacket(pkt);
        } else if (字幕包) {
            同步解码入 subtitleManager_;
        }
    }
}
```

**Seek 协议**：

1. 控制线程执行 `SeekCommand::execute()`：
   - 置精确跳转状态（`clockController_->startSeek(targetPTS)`）
   - flush 队列（`queueManager_->flushAll()`）
   - bump serial（`serial_.fetch_add(1)`）
   - 投递 demux 内部请求（`demuxWorker_->postSeek(targetPTS)`）
2. demux 线程下一轮循环检测到 `seekRequest_.pending`：
   - DASH 流 → `restartDashMerger(target)` 重启下载器
   - 点播流 → `demuxer_->seek(target)`
   - 投 flush packet 进队列
3. decode 线程收到新 serial 的包开始解码，首帧解出时 `clockController_->checkSeekTimeout()` 清除精确跳转状态

**DASH 流 seek**：pipe 输入不可 seek，matroska 流式无 cues 索引 → 停旧 merger、用新时间参数重启从目标位置下载、重开 demuxer。重启包在重试循环（最多 3 次），B站分片经代理偶发 TLS pull error 单次失败不永久 ERROR。

### 3.2 DecodeWorker（video/audio 对称解码线程）

**职责**：从 PacketQueue 取包解码 → PTS 归一化 → 入 FrameQueue。video/audio 对称设计，共用同一套代码（`runVideo()` / `runAudio()` 传参区分）。

#### 接口

```cpp
class DecodeWorker {
public:
    DecodeWorker(Player* player, bool isVideo);
    void start();
    void join();
private:
    void runVideo();
    void runAudio();
    void enqueueVideoFrame(AVFrame*);
    void enqueueAudioFrame(AVFrame*);
    void normalizeFramePTS(AVFrame*, bool isVideo);  // PTSNormalizer 归一化
    void checkAndClearPrebuffer();
    void waitWritableSlot(FrameQueue*, const char* queueName);
    
    Player* player_;
    bool isVideo_;
    std::thread thread_;
};
```

#### 核心逻辑

```cpp
void DecodeWorker::runVideo() {
    while (!player_->shouldQuit_.load()) {
        // ① 从 PacketQueue 取包（blocking，队列被 abort 时返回 nullptr）
        auto [pkt, serial] = player_->queueManager_->videoPacketQueue()->get();
        if (!pkt) break;  // abort 或 quit
        
        // ② 喂给解码器
        player_->videoDecoder_->sendPacket(pkt);
        AVFrame* frame = player_->videoDecoder_->receiveFrame();
        if (!frame) continue;
        
        // ③ PTS 归一化（实时流校准 + 异常检测）
        normalizeFramePTS(frame, true);
        
        // ④ 等待 FrameQueue 可写槽（背压）
        waitWritableSlot(player_->queueManager_->videoFrameQueue(), "video");
        
        // ⑤ 入队
        enqueueVideoFrame(frame);  // → frameQueue->peekWritable() 填充 + next()
        
        // ⑥ 首帧清除 prebuffer 标志
        checkAndClearPrebuffer();
    }
}
```

**PTSNormalizer 互斥**：video/audio 线程共享同一个 `player_->ptsNormalizer_`（实时流基准校准 + PTS 回绕检测），用 `player_->normalizerMutex_` 保护。点播流无需归一化（PTS 本身准确），normalizer 直接透传。

**背压机制**：FrameQueue 满时 `waitWritableSlot` 等待（条件变量 / 短睡眠），避免解码线程空转 CPU 或队列无限膨胀 OOM。点播流队列深度 25/20 帧（应对抖动），实时流 3/8 帧（低延迟）。

### 3.3 ClockController（时钟与同步）

**职责**：持有 `AVSync` 实例（音视频同步），封装 seek 精确跳转状态（目标 PTS / 计时窗口 / 超时判定）。

```cpp
class ClockController {
public:
    AVSync& avSync() { return avSync_; }
    
    // Seek 精确跳转状态管理
    void startSeek(double targetPTS);                  // 控制线程调用（SeekCommand::execute）
    bool isDecodingToTarget() const;                   // decode 线程判定是否仍在跳转中
    double decodeTargetPTS() const;                    // decode 线程获取目标 PTS
    void checkSeekTimeout(double currentPTS);          // decode 线程首帧解出时清除精确跳转状态
    void resetSeekState();                             // cleanup 时归零
    
private:
    AVSync avSync_;
    std::atomic<bool> decodingToTarget_{false};        // seek 跳转中（解码器丢弃非目标帧）
    std::atomic<double> decodeTargetPTS_{0.0};         // seek 目标 PTS
    std::atomic<uint64_t> seekTargetStartNs_{0};       // seek 开始时刻（纳秒，用于超时判定）
};
```

**Seek 精确跳转状态**：

- `startSeek(targetPTS)`：置 `decodingToTarget_ = true` + `decodeTargetPTS_` + 记录当前纳秒时刻到 `seekTargetStartNs_`
- decode 线程解码循环：`if (isDecodingToTarget() && framePTS < decodeTargetPTS()) 丢弃帧;`
- decode 线程首帧入队后：`checkSeekTimeout(framePTS)` 检测已达目标或超时 5 秒，清除状态

这样 seek 不再「UI 线程抢跑设置、demux 线程竞态读」，而是控制线程 `SeekCommand` 单点设置，demux/decode 线程只读原子量。

### 3.4 QueueManager（队列生命周期）

**职责**：统一管理 4 队列（packet×2 + frame×2）的创建/启动/abort/flush/销毁，避免 Player 散落 20+ 行队列操作。

```cpp
class QueueManager {
public:
    // 访问器（返回 unique_ptr& 兼容原用法：queueManager_->videoPacketQueue()->put(...)）
    std::unique_ptr<PacketQueue>& videoPacketQueue();
    std::unique_ptr<PacketQueue>& audioPacketQueue();
    std::unique_ptr<FrameQueue>& videoFrameQueue();
    std::unique_ptr<FrameQueue>& audioFrameQueue();
    
    // 批量操作
    void createAll(bool isLiveStream);  // 创建 4 队列，点播/实时流深度不同
    void startAll();                    // 调用每个队列的 start()
    void abortAll();                    // 调用每个队列的 abort()，唤醒阻塞线程
    void flushAll();                    // 调用每个队列的 flush()，清空已缓存帧/包
    void reset();                       // reset() 全部队列（智能指针置空）
};
```

点播流队列深度：video packet 1000 / audio packet 500 / video frame 25 / audio frame 20。  
实时流队列深度：video packet 200 / audio packet 200 / video frame 3 / audio frame 8（低延迟起播）。

### 3.5 StateManager（状态机）

**职责**：封装 `std::atomic<PlayerState>` + 统一转换协议（转换日志 + 回调触发）。

```cpp
class StateManager {
public:
    explicit StateManager(PlayerState initial = PlayerState::IDLE);
    
    PlayerState current() const { return state_.load(); }   // 无锁原子读
    bool isPlaying() const;
    bool isPaused() const;
    
    void transitionTo(PlayerState newState);                // 转换到新状态，触发日志 + 回调
    void setCallback(std::function<void(PlayerState)> cb);  // 注册状态变化回调
    
private:
    std::atomic<PlayerState> state_;
    std::function<void(PlayerState)> callback_;
};
```

`transitionTo()` 实现：

```cpp
void StateManager::transitionTo(PlayerState newState) {
    PlayerState oldState = state_.exchange(newState);
    if (oldState != newState) {
        LOG_INFO("Player state changed: " + toString(oldState) + " -> " + toString(newState));
        if (callback_) callback_(newState);
    }
}
```

Player 构造时注册转发回调：`stateManager_->setCallback([this](PlayerState s) { if (stateChangeCallback_) stateChangeCallback_(s); });`，这样外部（UI）通过 `setStateChangeCallback()` 订阅的回调仍能收到通知。

### 3.6 RecordingService（无锁录制）

**职责**：录制器创建/销毁/writePacket 全归 demux 线程串行执行，query 走原子状态块，彻底去除录制锁。

```cpp
class RecordingService {
public:
    void requestStart(bool isVideo, ...);              // 控制线程投递请求（非阻塞）
    void requestStop(bool isVideo);
    void processPendingRequests();                     // demux 线程每轮循环调用（串行处理）
    
    // Query（任意线程，无锁原子读）
    bool isVideoRecording() const;
    bool isAudioRecording() const;
    std::string videoRecordingPath() const;
    double videoRecordingTime() const;
    int64_t videoRecordingSize() const;
    // ... audio 对称接口
    
    Recorder* videoRecorder() { return videoRecorder_.get(); }  // demux 线程 writePacket
    Recorder* audioRecorder() { return audioRecorder_.get(); }
    
private:
    // 请求队列（mutex 保护）
    struct Request { enum Type { StartVideo, StopVideo, StartAudio, StopAudio }; ... };
    std::mutex requestMutex_;
    std::vector<Request> pendingRequests_;
    
    // 录制器（仅 demux 线程访问，无锁）
    std::unique_ptr<Recorder> videoRecorder_;
    std::unique_ptr<Recorder> audioRecorder_;
    
    // 状态块（原子，供跨线程 query）
    struct AtomicState {
        std::atomic<bool> isRecording{false};
        std::atomic<double> recordingTime{0.0};
        std::atomic<int64_t> recordingSize{0};
        std::string path;  // 只在 demux 线程写、UI 线程读快照，race 安全（最坏读到旧路径）
    };
    AtomicState videoState_;
    AtomicState audioState_;
};
```

**时序**：

1. 控制线程：`StartRecordingCommand::execute()` → `recordingService_->requestStart(isVideo, ...)`（持锁 push 请求，立即返回）
2. demux 线程下一轮循环：`recordingService_->processPendingRequests()`（取走全部请求、锁外串行处理）
   - StartVideo → `videoRecorder_ = std::make_unique<Recorder>(...)`
   - StopVideo → `videoRecorder_->finalize(); videoRecorder_.reset();`
3. demux 线程读包循环：`if (videoRecorder_) videoRecorder_->writePacket(pkt);`（无锁，录制器归 demux 线程单线程访问）
4. UI 线程每帧：`isVideoRecording()` / `videoRecordingTime()` 原子读快照画录制时长

---

## 四、关键不变量

### 4.1 线程职责边界

| 线程 | 可以做 | 不能做 |
|------|-------|--------|
| 控制线程 | 执行命令、渲染、UI 回调、pump 命令、EOF 判定 | 不能读包、不能解码 |
| demux 线程 | 读包、seek 落地、录制写包、DASH 重启、重连 | 不能改全局状态、不能操作 GL context |
| decode 线程 | 取包解码、PTS 归一化、帧入队、背压等待 | 不能改全局状态、不能 seek |
| 平台音频回调 | 从 audioFrameQueue 取帧、更新音频时钟 | 不能阻塞、不能操作 GL、不能 seek |

### 4.2 互斥与同步原则

- **命令队列**：`CommandQueue::mutex_` 只保护投递 / drain，锁外执行命令
- **PacketQueue / FrameQueue**：内部 mutex + 条件变量，get/put 短锁，满/空时等待
- **PTSNormalizer**：`Player::normalizerMutex_` 保护 video/audio 线程共享的归一化器（实时流基准校准 + PTS 回绕检测）
- **RecordingService**：`requestMutex_` 只保护请求队列投递 / drain，录制器本身归 demux 线程单线程访问无锁
- **StateManager / ClockController 状态**：全原子量，无锁读写
- **seekRequest_**：DemuxWorker 内原子量，控制线程写、demux 线程读

### 4.3 serial 机制（PacketQueue 序号）

每次 seek，控制线程 bump `Player::serial_`（`fetch_add(1)`）。demux 线程读到的包带新 serial 入队，decode 线程检测 serial 变化时丢弃旧 serial 的残留包/帧，确保 seek 后画面立即切换。

```cpp
// 控制线程：SeekCommand::execute()
int newSerial = player.serial_.fetch_add(1);
player.queueManager_->flushAll();  // 清空旧 serial 的包/帧

// demux 线程
videoPacketQueue->put(pkt, player_->serial_.load());  // 新包带新 serial

// decode 线程
auto [pkt, serial] = packetQueue->get();
if (serial != currentSerial_) { 丢弃旧帧; currentSerial_ = serial; }
```

### 4.4 cleanup 顺序（use-after-free 防护）

```cpp
void Player::cleanup() {
    shouldQuit_.store(true);
    joinWorkerThreads(/*abortQueues=*/true);  // ① join demux/decode 三线程
    
    if (audioOutput_) {                        // ② 停音频输出
        audioOutput_->stop();
        audioOutput_.reset();
    }
    
    renderer_.reset();                         // ③ 清理渲染器
    window_.reset();                           // ④ 窗口
    audioDecoder_.reset();                     // ⑤ 解码器
    videoDecoder_.reset();
    queueManager_->videoPacketQueue().reset(); // ⑥ 队列
    queueManager_->audioPacketQueue().reset();
    // ... 字幕、帧插值、音频重采样器
    demuxer_.reset();                          // ⑦ demuxer
    
    queueManager_->videoFrameQueue()->flush(); // ⑧ 清空帧队列
    queueManager_->audioFrameQueue()->flush();
    clockController_->resetSeekState();        // ⑨ 时钟 seek 状态归零，clockController_ 保留供复用
}
```

**关键**：`audioOutput_->stop()` 必须在 `clockController_` 相关操作之前，否则音频回调线程可能访问已销毁的 AVSync（use-after-free）。

## 五、数据流（不变）

命令队列重构**只改控制流**（谁来改状态），**数据流不变**——仍是 ffplay 式三线程解耦：

```
DemuxWorker 读包
    ↓ put(pkt, serial)
PacketQueue (mutex + 条件变量，背压)
    ↓ get() blocking
DecodeWorker 解码
    ↓ 填充 peekWritable() slot
FrameQueue (环形队列，keep-last)
    ↓ peekReadable()
控制线程渲染 / 平台音频回调播放
```

关键特性：

- **video 帧队列满只阻塞 video 解码线程**，audio 解码线程从独立的 `audioPacketQueue` 持续产帧、音频时钟照常推进——彻底消除「视频队列满 → 音频饿死 → 主时钟冻结」的结构性死锁。
- **serial 机制**保证 seek 后残留包/帧立即丢弃。
- **背压机制**防止队列无限膨胀 OOM（点播流深队列应对抖动，实时流浅队列低延迟）。

## 六、总结

| 维度 | 设计 | 收益 |
|------|------|------|
| **控制流** | 命令队列 + 单一控制线程 | UI 线程不改播放管线状态，消除「伸手进内部拨开关」的并发脆弱性 |
| **组件化** | 7 个职责单一组件 | Player 从 2000+ 行巨类降为门面，易测试、易扩展 |
| **seek 协议** | 显式 SeekCommand + DemuxWorker::postSeek | 控制线程单点设置精确跳转状态，demux 线程只读原子量，无竞态 |
| **录制** | RecordingService 无锁 | 录制器创建/销毁/writePacket 全归 demux 线程串行，query 走原子块 |
| **数据流** | ffplay 式三线程解耦（不变） | 视频帧队列满不饿死音频，消除结构性死锁 |
| **GLFW context** | 控制线程 = 主线程 = 渲染线程 | 命令执行与渲染同线程串行，天然不并发踩 GL 状态 |

代码量变化：

- `Player.cpp`：2000+ 行 → 约 1700 行（demux/decode 线程函数迁出）
- 新增：`PlayerCommand.cpp`、`DemuxWorker.cpp`、`DecodeWorker.cpp`、`ClockController.cpp`、`QueueManager.cpp`、`StateManager.cpp`、`RecordingService.cpp` 共 7 个组件源文件

架构完整性：所有线程函数已从 Player 迁出，seekRequest 协议、队列管理、状态机均已组件化，无遗留债务。
