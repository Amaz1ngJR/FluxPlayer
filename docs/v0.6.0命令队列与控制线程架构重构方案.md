# FluxPlayer 命令队列与控制线程架构

## 1. 线程与组件

播放器的控制线程与 GLFW/OpenGL 主线程相同。播放循环在 UI 渲染前执行 `Player::pumpCommands()`，从命令队列取走请求并在锁外串行执行。`CommandQueue` 的投递接口使用互斥锁；Player 的公开控制入口还会访问会话状态，遵守主线程调用约束，不能据此当作任意线程接口。

| 组件 | 当前职责 |
| --- | --- |
| `Player` | 持有播放组件，调度命令、输入安装、设备、渲染和资源回收 |
| `CommandQueue` | 保存命令，批量移交控制线程执行 |
| `StateManager` | 管理播放状态及状态转换通知 |
| `ClockController` | 持有 AVSync，管理精确 Seek 目标、计时和超时状态 |
| `QueueManager` | 管理音视频 packet/frame 队列及启动、abort、flush 边界 |
| `DemuxWorker` | 读包、Seek、DASH 替换、直播重连、背压及录制分发 |
| `DecodeWorker` | 独立执行视频或音频解码，归一化时间戳并提交帧 |
| `RecordingService` | 接收录制请求，由输入所有者操作 Recorder，发布原子状态和错误通知 |

主要数据流：

```text
Demuxer → 视频 PacketQueue → 视频 DecodeWorker → 视频 FrameQueue → 主线程渲染
        → 音频 PacketQueue → 音频 DecodeWorker → 音频 FrameQueue → 设备回调
        → SubtitleDecoder → SubtitleManager → UI 字幕 Surface
        → RecordingService → Recorder
```

## 2. 控制请求

命令类型包括 Seek、Pause、Resume、Stop、SetSpeed、SwitchQuality、StartRecording 和 StopRecording。命令队列锁只保护请求容器，不覆盖网络 I/O、设备调用或文件写入。

`switchQuality()` 的返回值表示请求是否受理，不代表切换完成。请求带单调 ID，Controller 根据完成快照更新标签与媒体信息；失败保留原标签。命令泵同时消费录制错误、候选完成结果和设备异步故障。

## 3. 输入打开与画质切换

OpeningScreen 在后台执行提取、Demuxer 打开/探测和 DASH 准备，结果在工作线程退出后交给主线程安装。解码器、音频设备及 GLFW/OpenGL 资源仍由主线程建立。直接调用 `Player::open()` 的 CLI 路径同步打开输入。

画质准备采用 latest-wins：同一时刻只运行一个候选，新请求取消旧候选并保存最新目标，旧候选退出后才启动最新候选。同一待处理画质的重复请求不重启任务。准备期间旧播放管线仍响应 Pause/Resume；Seek 使旧位置候选失效，但保留画质请求及其 ID，旧候选退出后按最新位置重新准备，不发布切换失败。Stop 和关闭取消整个请求。

提取结果在当前会话内保留可用画质的 HTTP(S) 单文件流地址与请求头。切换优先复用这些地址，分离音视频仅在请求头一致时复用；地址缺失或候选打开失败时重新提取一次。分片清单和特殊协议仍走原提取路径，不持久化临时地址。

安装前检查请求身份，冻结旧流并回收旧 Worker 后取得最终播放位置，候选输入实际重新定位到该位置：普通输入执行 seek，DASH 重建两路 Range 输入及管道，不从准备起点大量解码追赶。最终定位是安装事务中的同步 I/O，可能阻塞控制线程；失败进入错误态，不复用已中断的旧协议状态。安装使用最新播放/暂停意图，封口录制后重建解码器、队列、字幕、音频格式及 GL 互操作。安装期间 Pause/Resume 更新事务意图，由安装路径统一操作设备。候选准备失败保留旧管线；冻结并回收旧 Worker 后的最终定位或安装失败进入错误处理，不提供旧管线回滚。

后台准备不等于安装无阻塞：旧 Worker 的 join 可能等待协议 I/O 返回。

## 4. 帧队列事务

生产者在私有 `Frame` 上完成转换，使用开始转换时捕获的 `Tag{serial, epoch}` 调用 `trySubmit()`。提交在队列锁内检查代际和容量，通过交换帧封装转移引用；失败不转移所有权。

视频消费者使用 `peekRef(frame, token)` 获取独立引用和 `ReadToken{epoch, itemId}`，再以 `consume(token)` 提交消费。flush 使旧凭证失效，但不释放消费者持有的独立引用。视频 keep-last 保留最后显示帧，供暂停重绘和截图读取。

音频使用专用 `renderAudio()`，在队列锁内复制 S16 并推进跨回调采样相位，不在消费路径调用 FFmpeg ref/unref。已消费槽中的引用由生产者交换后回收。flush 与复制串行，并重置采样相位。

## 5. Seek 与完成事件

1. 控制线程检查目标有效性，先门控音频并确认 `pauseAndFlush()` 成功，再发布新目标及队列代际。
2. DemuxWorker 在同一请求锁内取得目标和代际，网络 I/O 期间不持业务锁。
3. Demuxer 的中断回调观察代际变化，将旧操作标记为 `Superseded`；它不进入 EOF 或断线重连分支。
4. 完成发布时校验当前代际及退出状态，准备时钟和对齐目标后才发布 ready。
5. 音视频包提交、EOF 标记和字幕发布在请求边界校验身份；解码 EOF、超时和音频门控完成校验 serial。
6. 解码线程只发布音频恢复意图，实际 start/resume 由主线程执行。控制线程周期检查定位期限，计时不因视频先对齐而停止。只有解码 EOF、音频帧队列、待提交 PCM 和设备有效覆盖全部排空，才允许从确认位置切换外部时钟继续剩余视频；这不发布音频实际对齐成功，再次 Seek 恢复音频主时钟。未获 EOF 证据的定位超时进入错误态，取消使用者并解除队列阻塞，不用静音伪造进度。暂停中已有音频等待消费不判作缺数据，恢复后重新计时。首帧和 DASH 失败通知也由主线程校验身份后消费。

音视频解码在 send 返回 EAGAIN 时保留原 packet，取尽输出后重发，直到接受、明确失败或当前 serial 失效。空包通过 nullptr 启动 drain，只有 receive 返回 EOF 才发布 drained；drain 错误不冒充正常 EOF。

DASH 目标与代际同锁获取，候选安装在锁内检查身份、交换所有权并发布时钟/ready，旧资源在锁外回收。

## 6. 音频输出与时钟

`AudioOutput` 接受有效采样参数的 S16 PCM，缓冲按完整采样帧对齐；ALSA 拒绝设备协商出不同采样率。音量只在软件 PCM 层应用一次，静音不覆盖用户保存的音量。

设备启动前分配输出工作区、逐采样覆盖数组和 AVSync 覆盖环。设备提交成功后通知采样范围及排队延迟；AVSync 将有效 PCM 映射为媒体起止位置和预计设备播放起止时刻，仅在这些区间内插值。已提交区间保留生成时的媒体跨度，修改倍速不重新解释旧 PCM。

欠载尾部补静音，但不登记有效媒体覆盖。设备内的有效区间耗尽后，音频时钟冻结在尾端；高倍速同样不通过墙钟或回调块大小合成进度。设备位置由排队延迟估算，不是精确硬件播放游标。消费路径仍有互斥锁，不属于无锁或全栈零分配实现。

自然 EOF 同时等待音频帧队列、填充块中尚未提交的有效 PCM 和已提交覆盖区间排空。填充块与提交计数由音频回调锁保护，ALSA 分段写入按 offset 累计；暂停时按冻结锚点判断覆盖，Seek 清缓存时清除旧填充计数。

普通暂停保留设备 PCM 和覆盖记录，恢复时平移覆盖的时间锚点。Seek 清设备缓存后重建覆盖。ALSA 不支持保留式暂停时返回失败，不隐式 drop。

设备初始化、启动、恢复以及异步提交/写入失败传给 Player。修改音频拓扑前先停止设备并回收使用线程；有视频时禁用音频分支，改用外部时钟续播，纯音频无法输出则报告错误。录制按源包分发，不依赖音频播放分支是否启用。

## 7. 录制请求与封口

Player 的公开录制入口投递已有录制命令，与其他控制命令按队列顺序执行。RecordingService 忽略 Starting/Recording 状态下的重复 Start；处理时逐个取出本批请求，正常完成发布在请求锁内检查该轨道是否还有新请求，避免旧结果覆盖新 Starting/Stopping。文件 I/O 不持请求锁，无可用输入的 Start 直接发布错误。

录制请求只保存输入代际，不保存裸 `AVFormatContext` 或流索引。DemuxWorker 消费请求时提供当前输入；RecordingService 校验是否允许起录和代际是否匹配，再读取轨道索引。

Stop 在请求锁内发布独立 `readWake_`，取走请求时同锁清除。该标志只在进入协议读操作前检查；进行中的 FFmpeg 协议读和自定义管道读取不因录制 Stop 中断，避免破坏 RTMP 分块等协议状态。输入所有者在当前读返回或背压/停泊边界处理请求；Stop 封口延迟受当前 I/O 等待影响，不保证立即返回，也不通过清除 AVIO 错误假定协议可续读。

EOF 停泊、背压和退避期间也处理录制请求。EOF、Seek、重连、切流和退出封口当前录制；输入替换递增代际并清除旧 Start，不跨 Seek 连续录制。

Recorder 返回写包、trailer、缓冲刷新和关闭结果。RecordingService 保留 Error 状态，并向主线程发布一次性错误通知；显式 close 和 run 结束回收会消费通知，析构兜底不调用外部回调。

## 8. 网络取消与资源生命周期

Demuxer 在打开输入前安装稳定中断回调。open/probe/read/seek 的普通预算分别为 15/10/10/8 秒，RTMP 的 probe 预算为 30 秒，以容纳关键帧间隔和网络抖动；回调检查停止、代际、控制唤醒和单调时间。预算依赖协议检查回调，不是同步系统调用的硬退出上限。

FFmpeg 探测在触及截止时间后仍可使用已取得的参数返回成功。Demuxer 保留该成功结果，并清理该次截止探测留下的 AVIO 错误/EOF；取消或代际失效仍优先拒绝结果。探测日志分别记录 FFmpeg 原始返回值、最终结果及耗时，失败日志包含具体错误。

StreamExtractor 使用受控子进程：POSIX 使用独立进程组和非阻塞读取，Windows 使用 Job 管理进程树。取消先终止任务，再回收进程和管道，不走代理回退。

DASH 的 POSIX 写端使用 nonblocking/poll，Windows 写等待观察取消与代际；写端由写线程关闭。Demuxer 的自定义管道读端观察同一取消契约。关闭顺序为格式上下文、自定义 AVIO、管道句柄，关闭动作由输入所有者或其退出后的控制线程执行。

Player 停止时先发布退出意图并停止音频设备，再 abort 队列唤醒等待者、join Worker，最后释放它们使用的解码器、队列、Demuxer 和 merger。不能通过跨线程关闭活跃 Demuxer 来解除读阻塞。

## 9. 源码入口

- `src/core/Player.cpp`：命令泵、候选安装、音频回调、Seek 及生命周期。
- `src/core/FrameQueue.cpp`、`src/core/QueueManager.cpp`：帧事务与队列边界。
- `src/core/DemuxWorker.cpp`、`src/core/DecodeWorker.cpp`：I/O 与解码执行。
- `src/core/AVSync.cpp`、`src/audio/AudioOutput.cpp`：覆盖时钟及平台音频提交。
- `src/core/RecordingService.cpp`、`src/recorder/Recorder.cpp`：录制身份、状态与封口。
- `src/decoder/Demuxer.cpp`、`src/utils/DashMerger.cpp`、`src/utils/StreamExtractor.cpp`：网络取消和管道所有权。
