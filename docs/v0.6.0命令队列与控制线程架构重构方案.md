# FluxPlayer v0.6.0 命令队列与控制线程架构重构方案

> **状态：方案（未实现）**。本文承接 [[v0-5-1-concurrency-hardening]]（见
> `docs/v0.5.1状态控制收尾与并发加固方案.md` 第五章「后续」）。v0.5.1 把**线程边界
> 的正确性**补齐了（FrameQueue 引用持有 / seek 原子 / EOF 停泊 / 录制器锁 / AVSync
> external clock 互斥），但 `Player` 仍是 2600+ 行的多职责巨类，控制流仍以「UI 线程
> 直接调用 Player 方法 + 散布的成员变量 + 双阶段时序约定」维持。本方案把控制流也
> 拆开：**引入命令队列 + 控制线程模型**，把 Player 拆成职责单一的协作组件。

> **范围**：本方案是**结构性重构**，目标是「行为不变、结构收敛」。不新增播放功能，
> 不改用户可见体验（进度条、音画同步、录制、画质切换、循环、变速等保持一致）。
> 按 [[AI开发守则]] 第八条，公开接口（`Player` 对 UI / main 暴露的方法签名）保持稳定，
> 但部分原同步方法在内部会变成「命令已受理」语义，详见 3.5。重构分
> **五个可独立编译、可独立验证的阶段**推进，
> 每阶段都能单独 commit 并回归，避免一次性大爆炸式替换。

---

## 一、问题总览：为什么 v0.5.1 之后还要重构

v0.5.1 解决的是「**数据竞争**」（同一份数据被多线程非串行访问）。本方案解决的是
「**职责耦合 + 控制流时序脆弱**」——它们不是 UB，但是 bug 的温床和维护成本的来源。

### 1.1 Player 是多职责巨类（`Player.cpp` 2622 行）

`grep` 出的 50+ 个 `Player::` 方法横跨至少 8 类职责：

| 职责 | 代表方法 | 当前归属 |
|------|---------|---------|
| 生命周期/状态机 | `open` / `close` / `play` / `stop` / `setState` | Player |
| demux 读包分发 | `demuxThread` / `waitForPacketSpace` | Player |
| 解码 | `videoDecodeThread` / `audioDecodeThread` / `normalize*PTS` / `enqueue*Frame` | Player |
| 时钟/seek | `seek` / `processSeekRequest` / `seekTargetStartNs_` + AVSync | Player + AVSync |
| 渲染调度 | `run` / `renderVideoFrame` | Player |
| 录制 | `start*Recording` / `stop*Recording` / 6 个 query | Player + recorderMutex_ |
| 网页流/画质 | `switchQuality` / `restartDashMerger` / `setPreExtractedInfo` | Player |
| 统计/回调 | `getStats` / `updatePlaybackStats` / 6 个 callback | Player |

单一职责（[[AI开发守则]] 第五条）被严重违反，`Player.h` 有近 60 个成员变量，
线程安全约束靠注释维持（「仅 demux 线程访问」「UI 线程写、decode 线程读」散落各处）。

### 1.2 控制流：UI 线程直接改播放器内部状态

`Controller.cpp` 在 **ImGui 渲染回调内**（即主线程 `run()` 循环里 `renderCallback_()`）
直接调用：

```
player_.seek(targetTime)            Controller.cpp:496
player_.pause() / resume() / stop() Controller.cpp:626/633/656
player_.startVideoRecording()       Controller.cpp:678
player_.switchQuality(...)          Controller.cpp:1353   ← 最危险
player_.setPlaybackSpeed(...)       Controller.cpp:1290
```

这些调用**就地修改 Player 内部跨线程状态**，与 demux/decode/audio 三个 worker 线程
并发。v0.5.1 用锁和原子把每个**单点**都防住了，但调用链路本身仍是「UI 线程伸手进
播放管线内部拨开关」，每加一个新操作都要重新审计一遍它和三个 worker 的并发关系。

### 1.3 三个具体的脆弱时序

**(a) seek 双阶段**（`seek` Player.cpp:614 ↔ `processSeekRequest` Player.cpp:1511）：
UI 线程先「抢跑」——立即置 `decodingToTarget_`、`seekTargetStartNs_`、并 `flush` 两个
packet 队列 bump serial；demux 线程隔几十~几百 ms 后才真正 `demuxer_->seek`。这套
「UI 先 flush、demux 稍后处理」的双阶段逻辑，注释写了 **40+ 行**解释为什么必须这样
（Player.cpp:642–660、1141–1152），本质是在补偿「控制和执行不在同一个线程」。

**(b) switchQuality 阻塞 UI**（Player.cpp:2484）：在 UI 线程里同步跑
`StreamExtractor::extract`（yt-dlp，**10–30 秒阻塞**）+ `joinWorkerThreads` +
`demuxer_->open`（网络连接，秒级）。整个过程主线程 `run()` 循环停转，窗口卡死无响应。
对比 `open()` 的网页流提取已经通过 `OpeningScreen` 工作线程 + `setPreExtractedInfo`
绕开主线程（Player.h:100–114 注释），**但 `switchQuality` 没有享受同等待遇**。

**(c) 录制 start/stop 用锁补正确性**（v0.5.1 2.4）：start/stop 在 UI 线程把
`videoRecorder_` 置半构造态，与 demux 线程 `writePacket` 并发，v0.5.1 用
`recorderMutex_` 覆盖到位。但 v0.5.1 文档 2.4 末尾已明说：「更彻底的做法是把录制
start/stop 投递到 demux/control 线程串行执行，彻底消除锁——那依赖尚未引入的命令
队列（v0.6.0）」。**本方案就是来兑现这句话的。**

## 二、设计总纲：命令队列 + 控制线程 + 组件化

### 2.1 核心思想

把「**谁来改播放管线状态**」从「任意 UI 线程」收敛为「**唯一的控制线程**」。UI 线程
不再直接调用会改变内部状态的方法，而是**投递一条命令**到线程安全队列；控制线程
（即现有的主循环线程）在每帧循环的固定时点**串行取出并执行**命令。

```
        投递（非阻塞，任意线程）              执行（串行，仅控制线程）
UI 线程 ───────────► CommandQueue ───────────► 控制线程主循环
  Controller            (mutex+队列)              PlaybackSession::pumpCommands()
  .post(SeekCommand)                                ├─ SeekCommand    → demux 协作
                                                    ├─ SwitchQuality  → 异步提取+重开
                                                    ├─ StartRecording → 录制服务
                                                    └─ SetSpeed/...   → 时钟/解码
```

这样：
- **seek 不再靠 UI 线程抢跑**：发起 seek 的「置精确跳转 + flush bump serial」从
  UI 回调移到控制线程的 `SeekCommand`，并与「投递 demux 内部 seek 请求」成为同一
  控制线程内的连续事务；demux 线程仍在自己的读循环落地 `demuxer_->seek`，但跨线程
  时序从隐式注释约定变为显式协议（`seekSerial` / `commandId`）。
- **switchQuality 不再阻塞 UI**：命令携带回调，提取阶段甩到工作线程，完成后再投递
  「重开流」后续命令；UI 线程投递完立即返回。
- **录制锁可以去掉**：控制线程只投递录制请求，Recorder 的创建/销毁/writePacket
  全部归 demux 线程串行执行。

### 2.2 组件拆分（对标 ffplay，但保留本项目的网络流/DASH/录制特性）

`Player` 从「巨类」降级为「**门面（Facade）+ 组件持有者**」，公开接口不变，内部委托给
六个职责单一的组件：

| 组件 | 职责 | 从 Player 搬过去的内容 |
|------|------|----------------------|
| **PlaybackSession** | 生命周期 + 状态机 + 命令泵 | `state_` / `open` / `close` / `play` / `stop` / `setState` / 命令队列 |
| **DemuxWorker** | open/read/seek/reopen/分发 packet | `demuxThread` / `waitForPacketSpace` / `processSeekRequest` / `restartDashMerger` / 直播重连 |
| **DecodeWorker** ×2 | video/audio 各一，消费 packet 队列 | `videoDecodeThread` / `audioDecodeThread` / `normalize*PTS` / `enqueue*Frame` / `waitWritableSlot` |
| **ClockController** | AVSync + seek 状态封装 | `seekTargetStartNs_` / `decodingToTarget_` / `decodeTargetPTS_` / `seek` 时序 + 持有 `avSync_` |
| **RenderPipeline** | FrameQueue → GLRenderer，主线程渲染 | `renderVideoFrame` / `run` 的取帧渲染部分 / `prevVideoFrame_` / 插值 |
| **RecordingService** | 录制 start/stop/write 归属独立化 | `start*Recording` / `stop*Recording` / 6 个 query / `recorderMutex_`（去除）/ writePacket 入口 |

> **GLFW context 亲和性约束（关键，不可违反）**：OpenGL context 绑定在创建它的线程
> （主线程）。因此 **RenderPipeline 的实际 GL 调用、window swap/poll 必须留在主线程**
> （即控制线程 = 主线程 = `run()` 所在线程）。本方案**不把渲染甩到独立线程**——
> 控制线程和渲染线程是同一个。命令队列的执行时点就嵌在主循环里，与渲染同线程串行，
> 这也天然保证「命令执行」与「取帧渲染」不会并发踩 GL 状态。

### 2.3 线程模型对照

```
v0.5.1（现状）                          v0.6.0（目标）
─────────────                          ─────────────
主线程: run() 渲染循环                   控制线程(=主线程): RenderPipeline 渲染
        + 直接被 UI 回调改状态                 + pumpCommands() 串行执行命令
                                              + 持有 PlaybackSession 状态机
demux 线程: demuxThread                  demux 线程: DemuxWorker::run()
video decode 线程                        video decode 线程: DecodeWorker::run()
audio decode 线程                        audio decode 线程: DecodeWorker::run()
平台音频回调线程: audioOutputCallback     平台音频回调线程: 不变（RenderPipeline 之外）
                                        [新增] 短时工作线程: yt-dlp 提取/重开流（一次性）
```

**线程数不变**（3 常驻 worker + 主线程 + 平台音频回调），只新增 switchQuality 时的
一次性临时工作线程。控制并发的方式从「多把锁 + 原子 + 注释约定」变为「**单一控制
线程串行执行命令**」。

## 三、命令队列设计

### 3.1 命令类型

```cpp
// 新增 include/FluxPlayer/core/PlayerCommand.h
namespace FluxPlayer {

/// 命令基类：控制线程取出后调用 execute()，在控制线程上下文执行
struct PlayerCommand {
    virtual ~PlayerCommand() = default;
    virtual void execute(PlaybackSession& session) = 0;
};

struct SeekCommand        : PlayerCommand { double targetSec; ... };
struct PauseCommand       : PlayerCommand { ... };
struct ResumeCommand      : PlayerCommand { ... };
struct StopCommand        : PlayerCommand { ... };
struct SetSpeedCommand    : PlayerCommand { double speed; ... };
struct SetVolumeCommand   : PlayerCommand { float volume; ... };  // 也可保留直接原子，见 3.4
struct SwitchQualityCommand : PlayerCommand { std::string formatId; double seekTime; ... };
struct StartRecordingCommand: PlayerCommand { bool video; ... };
struct StopRecordingCommand : PlayerCommand { bool video; ... };

} // namespace FluxPlayer
```

> 命名遵循 [[AI开发守则]]：类 `PascalCase`。命令是「值对象 + 行为」，用虚函数 dispatch
> 而非 enum + switch，便于每条命令把自己的执行逻辑内聚（避免又长出一个巨型 switch）。

### 3.2 队列实现

```cpp
// PlaybackSession 内部
class CommandQueue {
public:
    void post(std::unique_ptr<PlayerCommand> cmd);   // 任意线程，非阻塞
    std::vector<std::unique_ptr<PlayerCommand>> drain();  // 仅控制线程，取走全部
private:
    std::mutex mutex_;
    std::vector<std::unique_ptr<PlayerCommand>> pending_;
};
```

队列只保护「投递 / 取走」这一对操作，临界区极短（move 指针）。控制线程每帧 `drain()`
一次性取走全部待执行命令，锁外串行 `execute`，避免持锁执行重活。

### 3.2.1 命令合并与优先级

连续 UI 操作会产生大量同类命令，尤其拖动进度条时每帧都可能 post seek。队列需要
最小合并策略：

- `SeekCommand`：只保留最后一个目标；同一 drain 批次内丢弃旧 seek。
- `SetSpeedCommand` / `SetVolumeCommand` / `SetMuteCommand`：只保留最后一个值。
- `SwitchQualityCommand`：新的切换命令应取消尚未落地的旧切换任务；已进入重开流阶段时
  需要用 `commandId` 丢弃迟到的旧 worker 结果。
- `StopCommand` / `CloseCommand`：高优先级，执行后本批次中后续普通命令直接丢弃。

实现上不要求 `CommandQueue::post()` 做复杂逻辑；可以在 `drain()` 后由
`PlaybackSession::pumpCommands()` 对批次做一次归并，再按优先级执行。

### 3.3 执行时点

控制线程主循环（原 `run()`）每帧固定时点泵命令：

```cpp
void RenderPipeline::loop() {  // 原 Player::run() 的循环体
    while (!shouldQuit) {
        session_.pumpCommands();   // ← 新增：串行执行本帧投递的所有命令
        renderOneFrame();          // 原 renderVideoFrame / audioOnly 分支
        if (renderCallback_) renderCallback_();  // UI（含 Controller，可能投递新命令）
        window_->swapBuffers();
        window_->pollEvents();
        checkEofAndLoop();         // 原 EOF 判定 + handleLoopRestart
    }
}
```

**关键时序**：`pumpCommands()` 在 `renderCallback_()`（UI）**之前**。本帧 UI 投递的
命令在**下一帧**开头执行——延迟最多一帧（~16ms），用户无感，但换来「命令执行绝不与
UI 回调交错」的强保证。

**命令执行预算**：控制线程命令必须是短任务。任何可能阻塞超过一帧的操作（yt-dlp、
网络 `demuxer_->open`、DASH merger 初始化、文件系统慢 I/O）都不能直接在
`execute()` 里同步完成，而要拆成：

1. `execute()` 只切状态、冻结旧管线、启动 worker/future；
2. worker 完成后 post 一个 `Finish*Command` 回控制线程；
3. `Finish*Command` 在控制线程做极短的状态切换和资源接管。

否则命令队列只是把「Controller 里卡 UI」移动到「pumpCommands 里卡 UI」，没有解决
v0.6.0 的核心问题。

异步 worker 生命周期规则：

- 每个异步任务携带 `commandId` / `sessionGeneration`。`Finish*Command` 执行时若发现
  generation 不匹配（用户已 close、重新 open、再次切画质），直接丢弃结果。
- worker 不持有裸 `Player*` / `PlaybackSession*` 长引用；只持有可安全投递结果的弱句柄
  或 `shared_ptr` 控制块，避免 Player 析构后回调悬空。
- `close()` / `stop()` 必须取消或失效所有 pending async 任务，并在同步收尾中等待必要的
  资源释放；不要求阻塞等待 yt-dlp 自然结束，但必须保证迟到结果不会接管新 session。

### 3.4 哪些操作走命令、哪些保留直接调用

不是所有操作都值得包成命令。判据：**是否改变跨线程播放管线状态 / 是否有时序依赖**。

| 操作 | 走命令？ | 理由 |
|------|---------|------|
| seek / switchQuality / stop / 录制 start/stop | **是** | 强时序、多组件协作、当前最脆弱 |
| setPlaybackSpeed | **是** | 改 AVSync 时钟基准 + 解码丢帧策略，多组件 |
| pause / resume | 是 | 简单，但与 seek/EOF 状态机交互，纳入统一更安全 |
| setVolume / setMute | 否（保留原子） | 单一原子量，平台音频回调直接读，无时序依赖 |
| getCurrentTime / getStats / isRecording 等 query | 否 | 只读快照，走原子/无锁读，不能阻塞 UI 渲染 |

> **只读 query 绝不走命令队列**：UI 每帧要读十几个状态画进度条/音量/录制时长，若都
> 排队等控制线程执行会引入延迟和死锁风险。query 继续走「原子量 / 短锁快照」直读，
> 与 v0.5.1 的 AVSync/RecordingService 内部锁配合即可。

### 3.5 公开接口兼容性：签名不变，但区分「受理」与「完成」

`Player` 对 `main.cpp` / `Controller.cpp` 的方法签名保持不变，但内部改成命令后，
必须明确返回值语义，避免 UI 把「命令已排队」误当成「操作已完成」。

| 方法 | v0.6.0 返回值语义 | 完成/失败通知 |
|------|------------------|--------------|
| `seek(double)` | 参数合法且命令已受理返回 `true` | 进度条由 `ClockController::beginSeek` 立即更新；真实落点仍由后续帧校准 |
| `switchQuality(formatId, seekTime)` | formatId 合法、异步切换任务已受理返回 `true`，**不表示画质已切完** | 切换中进入 `OPENING` 或专用内部状态；失败走 `errorCallback_` / `ERRORED` |
| `start/stopRecording` | 命令已受理；query 通过 RecordingService 原子快照反映最终状态 | `is*Recording()` / time / size 每帧读快照 |
| `pause/resume/stop/setPlaybackSpeed` | 命令已受理或当前状态不允许 | `stateChangeCallback_` / stats 快照 |

生命周期方法分两类：

- `open()` / `open(externalWindow)` / `play()` 仍保持同步语义。它们通常在进入主循环前
  调用，命令泵尚未运行，不能只 post 不执行。
- `close()` / 析构 / 自然 EOF 收尾必须能在命令泵停止后同步关闭 worker。实现上需要
  提供 `shutdownWorkersSync()` / `closeSync()` 这类内部路径，不能依赖再投一条命令。

执行规则：

- 当 `run()` 主循环活跃时，UI 回调中的 mutating 方法只 post 命令，本帧不执行，
  统一在下一帧 `pumpCommands()` 处理。
- 当主循环未活跃时，仅允许生命周期收尾路径同步执行；其它播放控制方法维持当前
  「状态不允许则返回 false」的行为。

## 四、逐组件方案

### 4.1 PlaybackSession：状态机 + 命令泵

把散落在 Player 的状态机收口：

```cpp
// include/FluxPlayer/core/PlaybackSession.h
class PlaybackSession {
public:
    void post(std::unique_ptr<PlayerCommand>);   // UI 投递入口
    void pumpCommands();                          // 控制线程每帧调用
    PlayerState state() const { return state_.load(); }
    void setState(PlayerState);                   // 触发 stateChangeCallback_

    // 命令通过友元/访问器操作下列组件：
    DemuxWorker&      demux();
    ClockController&  clock();
    RecordingService& recording();
    // ...
private:
    std::atomic<PlayerState> state_;
    CommandQueue commands_;
    // 持有/引用各组件
};
```

`state_` 仍是原子（query 直读），但**写状态只发生在控制线程**（命令执行 / EOF 判定），
消除「UI 线程和 worker 线程同时 setState」的可能。

### 4.2 DemuxWorker：seek 控制协议显式化

把 `demuxThread` + seek 相关搬出。**最大收益：消除 UI 线程抢跑式 seek 双阶段**。

现状（v0.5.1）：`Player::seek()`（UI 线程）抢跑 flush + 置精确跳转，
`processSeekRequest()`（demux 线程）稍后补 `demuxer_->seek`。

v0.6.0：`SeekCommand::execute()` 在**控制线程**运行，它：
1. 通过 `ClockController` 置精确跳转 + flush packet 队列 bump serial（原 UI 抢跑部分）；
2. 给 DemuxWorker 投递一个**内部 seek 标记**（DemuxWorker 自己的轻量请求，仅
   demux 线程消费），demux 线程下一轮读循环顶部执行 `demuxer_->seek`。

区别在于：现在「开始 seek 状态」和「投递给 demux」是**同一个控制线程里的一次连续
控制事务**，不再是「UI 回调直接改内部状态，同时 demux 线程稍后补动作」的散乱拼接。
但它仍然跨 control/demux 两个线程协作，因此必须显式保留两条规则：

- DemuxWorker 的内部 seek 请求要带 `seekSerial` / `commandId`，demux 线程读到旧请求时
  能丢弃，只执行最后一次 seek。
- `readPacket` 刚从旧 demuxer/pipe 返回的旧包，在 seek 请求未落地前仍要丢弃。也就是说
  Player.cpp:642–660 的「先 flush/bump serial」和 1141–1152 的「seek 挂起期丢包」逻辑
  **不是删除，而是收进 DemuxWorker/ClockController，归属更清晰**。

所以本阶段目标不是让 seek 变成单线程同步调用，而是把「谁负责发起、谁负责落地、旧包
如何判定」变成显式协议，避免继续依赖长注释解释隐含时序。

> DASH `restartDashMerger`、直播重连退避、EOF 停泊（v0.5.1 2.3 的成果）**原样搬入**
> DemuxWorker，行为不变。EOF 停泊靠 `shouldQuit_` / `abort` 唤醒的契约（v0.5.1 2.3
> 第 4、5 点）继续有效——只是 `shouldQuit_` 改由 PlaybackSession 持有。

### 4.3 DecodeWorker：video/audio 对称化

`videoDecodeThread` 和 `audioDecodeThread` 现在是两段高度相似但各自展开的代码。
抽成一个 `DecodeWorker` 类，video/audio 各实例化一个，差异（normalize / enqueue /
keep-last）通过策略或虚函数注入：

```cpp
class DecodeWorker {
public:
    DecodeWorker(StreamKind kind, PacketQueue&, FrameQueue&, Decoder&, ClockController&);
    void run();   // 线程主体：取包→serial 检测 flush→解码→normalize→enqueue
};
```

v0.5.1 的 serial 检测 flush、EOF drain 后停泊（`*DrainedEof_`）、`waitWritableSlot`
可中断轮询**全部保留**，只是从 Player 成员函数变成 DecodeWorker 方法。`normalizeVideoPTS`/
`normalizeAudioPTS` 的差异封进各自实现，消除两份近重复代码。

### 4.4 ClockController：seek 状态 + AVSync 收口

把 `seekTargetStartNs_` / `decodingToTarget_` / `decodeTargetPTS_` / `lastRenderedPTS_`
这组 seek 相关原子，连同 `avSync_`，收进一个组件。对外提供语义化方法：

```cpp
class ClockController {
public:
    void beginSeek(double targetSec);   // 置精确跳转 + 记 steady 起点（原 seek 抢跑）
    bool inSeek() const;                // 原 decodingToTarget_.load()
    void onReachedTarget();             // 原清除 decodingToTarget_
    double masterClock() const;         // 委托 avSync_->getMasterClock()
    // 封装 v0.5.1 的 external clock 互斥、纳秒化等，对外只露语义
};
```

收益：seek 状态机不再裸露在 Player 公共成员区，时序约束（哪些字段必须一起更新）
内聚到一个类，与 v0.5.1 给 AVSync 做的 external-clock 状态组打包是同一思路的延伸。

### 4.5 RenderPipeline：主线程渲染，承载命令泵

`run()` + `renderVideoFrame` 搬入。它持有主循环，每帧：泵命令 → 取帧渲染 → UI 回调 →
swap/poll → EOF/loop 判定。GL 调用全部留主线程（见 2.2 约束）。v0.5.1 的 `peekRef` /
`consume` 引用持有渲染路径**原样保留**。

### 4.6 RecordingService：去锁

把 6 个 query + start/stop + writePacket 入口收进独立服务。**去掉 `recorderMutex_`**：

- start/stop 走 `StartRecordingCommand` / `StopRecordingCommand`，在控制线程执行；
- writePacket 在 demux 线程；
- 控制线程和 demux 线程仍是两个线程，所以 start/stop 与 writePacket 的归属必须
  明确。这里有两种落地选择，**本方案选 (B)**：

  - **(A) 把 writePacket 也移到控制线程**：demux 线程把「待录制的 packet」投递给控制
    线程写。增加一次 packet 拷贝/转移和队列延迟，且录制吞吐受控制线程帧率制约，
    **不采用**。
  - **(B) 把 start/stop 也投递到 demux 线程执行**（而非控制线程）：录制器的创建/销毁/
    writePacket **全部归 demux 线程**串行，控制线程的 `StartRecordingCommand` 只是
    再投递一个「demux 内部录制请求」给 demux 线程。这样录制器的所有访问都在 demux
    单线程内，**无需任何锁**——这正是 v0.5.1 2.4 末尾指明的「投递到 demux 线程串行
    执行，彻底消除锁」。**采用 (B)。**

  query（isRecording / time / size）跨线程读 demux 线程持有的录制器状态，改为
  RecordingService 内部维护一组**原子状态块**（demux 线程写、UI 线程读），替代
  v0.5.1 的 `mutable recorderMutex_` 持锁读。

落地细节：

```cpp
enum class RecordingState {
    Idle,
    Starting,
    Recording,
    Stopping,
    Error
};

struct RecordingStatus {
    std::atomic<RecordingState> videoState;
    std::atomic<RecordingState> audioState;
    std::atomic<double> videoElapsedSec;
    std::atomic<double> audioElapsedSec;
    std::atomic<int64_t> videoFileSize;
    std::atomic<int64_t> audioFileSize;
};
```

- 控制线程收到 `StartRecordingCommand` 后，只把 `DemuxRecordingRequest` 投递给
  DemuxWorker，并把原子状态块置为 `Starting`；不要在控制线程构造 `Recorder`。
- DemuxWorker 在读包循环固定时点先处理 recording request，再处理当前 packet：
  这样 `StopRecording` 与 `writePacket` 不会交错。
- `writePacket` 只在 `RecordingState::Recording` 时执行。`Stopping` 状态下先 stop
  recorder，再把状态置 `Idle`。
- `switchQuality` / seek / reopen 时如何处理录制要显式化：本轮保持现有行为则写清
  「录制不中断但旧 serial packet 不写入」；若选择切段，则作为单独功能不在本轮做。

阶段过渡：P1 发生在 DemuxWorker 正式抽类之前，因此可以先在当前 `Player` 内新增一个
`DemuxControlQueue`，由现有 `demuxThread()` 每轮读包前消费；P3 抽 DemuxWorker 时再
把这段队列和处理逻辑整体搬过去。这样 P1 不依赖 P3，仍可单独编译和验证。

## 五、分阶段实施计划

每阶段独立可编译、可回归、可单独 commit。**顺序经过设计：先搭骨架不改行为，再逐个
迁移，最后清理。** 任何阶段失败可停在该阶段，不破坏已合入的前序成果。

| 阶段 | 内容 | 风险 | 验证重点 |
|------|------|------|---------|
| **P0** | 抽 `steadyNowNs` 等公共 helper，建 `PlayerCommand.h` / `CommandQueue`，在当前 `Player::run()` 开头接入最小 `pumpCommands()`，但暂无行为命令 | 极低 | 双构建通过；空队列 pump 不改变行为 |
| **P1** | RecordingService（含方案 B 去锁），录制 start/stop 走命令→临时 DemuxControlQueue→demux 线程串行；P3 再搬入 DemuxWorker | 中 | 录制中 seek/切画质/stop 并发无崩溃（对应 v0.5.1 验证 4） |
| **P2** | ClockController：收口 seek 状态 + AVSync，**seek 仍双阶段**（仅搬家不改时序） | 中 | 连续 seek、变速、暂停恢复无跳变（v0.5.1 验证 2/5） |
| **P3** | DemuxWorker + DecodeWorker：搬线程函数，seek 控制事务 + demux 内部请求显式协议化，SeekCommand 接入控制线程 | 高 | 全部 seek 场景 + DASH/直播 + EOF 恢复（v0.5.1 验证 1/2/3） |
| **P4** | switchQuality 异步化：提取甩工作线程，SwitchQualityCommand 分段投递；RenderPipeline 收口 run() | 高 | 画质切换不卡 UI、切换中再操作无崩溃 |

> **接口稳定性**：P0–P4 全程 `Player` 对 main.cpp / Controller 暴露的方法签名不变
> （`seek` / `switchQuality` / `startVideoRecording` 等），内部改为「构造命令 → post」。
> Controller.cpp 调用点签名基本不动，但画质切换/录制这类异步受理操作需要根据
> 3.5 的返回值语义调整 UI 文案（例如显示 Switching/Recording Pending），不能再把
> `true` 当成「操作已经完成」。这满足 [[AI开发守则]] 第八条第 3 点。

> **可中止性**：若 P3/P4 风险超预期，可在 P2 后暂停——P0–P2 已是净收益（录制去锁 +
> 时钟收口 + 命令骨架），seek 仍走 v0.5.1 的双阶段（已验证可靠），不影响发布。

## 六、需要保留的 v0.5.1 不变量（重构红线）

重构**不得破坏**以下 v0.5.1 已建立的正确性保证（见 [[v0-5-1-concurrency-hardening]]）：

1. **FrameQueue 引用持有**：`peekRef` / `consume` 语义不变，搬到 DecodeWorker /
   RenderPipeline 后消费者仍持独立 `Frame leased` 引用，绝不退回裸指针 peek。
2. **seek 原子计时**：`seekTargetStartNs_` 进 ClockController 后仍是原子 / steady ns，
   不退回普通 double。
3. **EOF 停泊契约**：decode 线程 EOF 不退出而停泊、靠 `abort` 唤醒、`shutdownWorkersForEof`
   闭合退出路径——搬入 DemuxWorker/DecodeWorker 后所有 join 路径仍 `abortQueues=true`。
4. **AVSync external clock 互斥**：base/offset/rate/paused 同一把锁快照读写，
   `extClockPaused_` 不与全局 `paused_` 混用——ClockController 封装后内部不变。
5. **录制器无半构造态访问**：v0.5.1 用锁，v0.6.0 用「单 demux 线程串行」达到同等
   保证（方案 B）——切换实现时必须保证过渡阶段（P1）任一时刻都安全。

### 7.2 回归场景（沿用 v0.5.1 验证矩阵 + 新增）

1. 本地文件正常播放到 EOF 自然结束；EOF 暂停后 seek 回中段恢复（DemuxWorker 停泊）。
2. 拖动进度条快速连续 seek（前向/后向）：无崩溃、进度条不跳回（**重点验证 P3
   seek 显式协议与 v0.5.1 双阶段行为一致**）。
3. 网络流 / DASH：seek 重启上游期间反复操作无崩溃。
4. 录制中 seek / 切画质 / stop：并发无崩溃（**重点验证 P1 去锁后正确性**）。
5. 暂停/恢复/变速反复切换：进度条与音画同步无跳变；长播 external clock 累积后 seek
   不大跳变（ClockController 封装后仍成立）。
6. **新增**：画质切换期间 UI 不卡死（窗口可响应、控制面板可点）；切换过程中再次点
   seek / 暂停，命令排队不崩溃（**验证 P4 异步化 + 命令队列串行**）。
7. **ThreadSanitizer**（可选）：`-fsanitize=thread` 跑全场景。预期比 v0.5.1 更干净——
   录制器归 demux 单线程、seek 控制协议显式化，跨线程共享面收窄。

### 7.3 行为对比基线

因本方案是「行为不变」重构，每阶段合入前应与上一 tag（v0.5.1）做**主观体验对比**：
同一组操作序列，进度条走位、音画同步、切换响应必须一致。任何可感知差异都视为回归。

  switchQuality 异步化思路一致，但 open 路径改动面更大，单列。
- PacketQueue / PTSNormalizer / seek 状态机单元测试：重构后接口更清晰，是补测试的
  好时机，作为 v0.6.x 持续项。
